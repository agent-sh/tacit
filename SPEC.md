# tacit store specification

Version 1, 2026-10-07. This file is the contract between the Go client (`client/`), the Elixir server (`server/`) and the curator. Code follows this file; when they disagree, fix the code or change this file in the same PR.

## Local mode and client configuration

`tacit init [--store DIR]` creates a standalone store with `tacit.local=true` in repository-local git configuration. A populated directory or existing non-local repository is refused. Initialization builds a complete repository in a sibling staging directory, then publishes it. A new local store starts with the evidence-based ruling marker and an empty index; this initializes an empty store, not evidence for imported facts.

Local writes use the same file format, writer names and transaction locks. They commit only named files, leave unrelated staged work alone and run the server's obvious-token/private-key shape check before committing. Agent notes still pass through scrump first. There is no remote, enrollment requirement or server authorization boundary. Sync/fetch/integration and remote-ahead checks do no network work. Follow returns the non-restarting configuration status (78; translated to 0 under launchd) with an explanation. Server clones retain their existing behavior; network failure never selects local mode.

The optional client settings file is `~/.config/tacit/config.yaml` on Unix and the user's config directory plus `tacit/config.yaml` on Windows. `TACIT_SETTINGS` or the global `--config FILE` selects another file. Fields are `store`, `projects`, `index`, `keys`, `local_overlay`, `local_layer`, `owner_names`, `hermes_db`, `verify_roots`, `runner`, `runners`, `commands`, `runner_args`, `efforts`, `profiles`, `timeouts`, `fallbacks`, `utility` (`provider`, `threshold`, `timeout`, `key_file`, `audit_dir`), and `models` (`curate`, `judge`, `dream`, `verify`, `verify_fallback`). Relative paths resolve against the file. Environment values override file values; command flags override defaults. Unknown fields or a missing explicitly selected file fail before command work. Hook configuration failures print nothing and exit 0.

`tacit install curate [--env-file FILE]` installs the daily curation/verification sequence. `tacit maintain [--env-file FILE]` runs it manually. Linux uses a user timer, macOS a launchd agent, Windows a current-user Task Scheduler definition. Windows dreaming/following also use Task Scheduler; the idle job is a second dream task every 10 minutes whose script runs `curate --quick` after `dream --idle` whatever the dream's exit code. Installers write files and print start commands without registering or starting jobs. CLI/browser app builds support Linux, macOS and Windows; native-window builds remain optional on Linux/macOS.

## Two repositories

- **Code**: this repository. Client, server, curator, eval.
- **Store**: a separate private git repository holding the facts. Its authority is the server; a push mirror and backups are the operator's choice. It never goes to a public host. Each client's clone lives at `~/.local/share/tacit/store` (`$TACIT_STORE`).

## Store layout

```
system/                    always loaded; small; reviewed by the owner
user/                      who the owner is, standards, voice
projects/<repo>/           decisions, past mistakes, history for one repo
areas/<area>/              an ongoing system or practice (ticketing, the wiki), its facts; areas/<area>/topics/<topic>/ a topic it owns
topics/<topic>/            a bounded work stream of no area
orgs/<org>/                an organization on the forge (format 2): facts that hold across its repositories (Orgs)
<project|area|topic>/_record.md    the folder's record (Folder records)
<project|area|topic>/_overview.md  the folder's cited overview (Overviews)
machines/<host>/           hardware, paths, what is dead on this box
derived/<repo>/            generated from git by the curator: hot spots with their co-change partners, module map (see Derived facts), measured results with their commit (see Results from git)
inbox/<harness>@<host>/    raw, unreviewed, append-only; subdirectories allowed
inbox/dreamer@<host>/_repos.json   generated: the repositories that machine has checkouts of (see Scopes)
keys/<harness>@<host>.pub  Ed25519 public keys of enrolled writers; written by the server at enroll
review/<date>.md           curator findings for the owner: contradictions, supersessions, stale? checks and LINK? lines (dead links in rulings), appended per run
review/<date>-rotation.md  the rotation's questions for the owner about their own facts (check? lines, Rotation)
review/folders.jsonl       the folder steps' log: area and topic proposals, their close, questions for the owner
review/statements.jsonl    the statements step's log: its model's reading of each statement and ruling it read, code's checks, every promotion, supersession and flag (Statements)
review/agent-reviews.jsonl the reviewer's ledger: its verdict on each agent's note, and the owner's answers (The reviewer)
review/<date>-statements.md  the statements step's optional items for the owner (check? lines: a check disagrees, a statement differs from a decision)
MEMORY.md                  generated flat index; never edited by hand; not generated with memory_md off (a bridge for older clients, to be dropped)
_index.md                  generated folder index, in the root and every curated folder (see Tree index); never edited by hand
review/format.json         the store's format marker (see Store format)
README.md                  optional, ignored by lint and index
```

A file whose name starts with an underscore (`_index.md`, `_repos.json`, a folder's `_record.md` and `_overview.md`) is a store file, never a fact: a fact's name is a slug and cannot start with one, and every reader of facts passes such files over, whatever their kind.

### Store format

`review/format.json` (`{"version": 1, "at": ...}`) says which store format every machine that writes the store reads. Format 1 adds folder records (`_record.md`), the `areas/` and `topics/` folders and the `last_checked` field. A binary older than a format reads such a store wrong (its frontmatter decoder is strict), so no writer writes any of them until the marker is there; the owner sets it once with `tacit format --set`, after every machine runs a binary of that format (`tacit doctor` shows the binary's format and the marker). Format 2 adds statements (type `statement`, Statements), the `orgs/` folders with records of kind `org`, and a project record's `org` and `forge` fields (Orgs, Planned renames). Format 3 adds a project record's `successor` and a status entry's `words`, `words_from` and `words_on` (Folder records: Owner words beat dates, Successors); in a store of format 2 the assessment writes the status and its why only. Format 4 adds a curated fact's `source.review` and `review_reason` (The reviewer); below it the verdict lives in the reviewer's ledger alone, which every reader applies the same way. `tacit format --set` moves a store to the binary's format. A new store (`tacit init`) starts with the marker. `records_complete` is set by `tacit format --records-complete` once every project, area and topic folder that holds facts has a record.

`<harness>` is one of `claude`, `codex`, `pi`, `hermes`, `grok`, `muse`, `agy`, `dreamer`, `import`, `curator`, `human`, `reader`. `<host>` is the short hostname. A reader key only reads (see Public path).

## Ordering

The server keeps a journal: `seq` (monotonic integer), commit `sha`, `ts`, writer key. Every accepted push appends one row under the repo lease, so `seq` is the total order of the store. The change feed carries `seq`; clients resume from the last `seq` they saw. Git history is the content; the journal is the order. The journal is also recoverable: if the server loses it, it rebuilds from the reflog of `main` (one row per push, same order, same writer) or, without a reflog, from first-parent history (same order, one row per commit), and `seq` restarts at 1 in that order. A client resumes from the last `seq` it saw. If that `seq` is past the new head, the feed sends one `event: reset` frame carrying the head and continues from there; the client then does a plain `git fetch`.

Everything outside `inbox/` is **curated** and is written only by the curator. Agents write only under their own `inbox/<harness>@<host>/`. The server enforces both at pre-receive.

The same hook refuses a push whose new blobs hold an obvious secret (`server/priv/hooks/pre-receive`): GitHub, AWS and Hugging Face token shapes, Slack webhook URLs (`hooks.slack.com/services/`, `/workflows/` or `/triggers/` and 43 or more of `[A-Za-z0-9+/]`, also with its slashes escaped as JSON writes them), Slack session cookies (`xoxd-` and 20 or more of `[A-Za-z0-9%+/=]`, URL-encoded base64) and private-key headers (`secret_re`), and three families of keys in two steps, since a fact name can start like one of them. A token is the family's prefix and a run of key characters (`<family>_token_re`); a token is a key when that run holds what a real key has (`<family>_key_re`):

- `sk` keys: `sk-` (at the start of a line or after a character that is not a letter or digit) and at least 16 key characters (`[A-Za-z0-9_-]`); a key holds an uppercase letter or underscore, a run of 20 letters and digits, or a lowercase UUID.
- `slack` tokens: `xoxa-`, `xoxb-`, `xoxc-`, `xoxd-`, `xoxe-`, `xoxo-`, `xoxp-`, `xoxr-`, `xoxs-` or `xapp-` and at least 10 key characters (`[A-Za-z0-9-]`); a key holds an uppercase letter, a run of 20 letters and digits, a run of 10 digits or two runs of 6 digits joined by a hyphen (team, user and app ids), or is a legacy workspace token: `xoxa-` or `xoxr-`, a digit, a hyphen and a run of 8 letters and digits that ends the token.
- `tskey` keys: `tskey-` and at least 10 key characters; a key holds an uppercase letter (a Tailscale key id ends in `CNTRL`, since 2021) or a run of 20 letters and digits.

A blob that holds no family's token (`any_token_re`, the union of the three token expressions) skips the six family steps: on a curator push of 2,000 facts the hook takes no longer than before the families (medians of 4.6 s against 4.9 s, and 5.1 s against 5.4 s on a busier machine; 7.6 s with the steps run on every blob). On 100,000 random keys of each shape the rule refuses all of them (`eval/secrets/token_rules.py`): Anthropic `sk-ant-api03-`, `-admin01-` and `-oat01-`, OpenAI `sk-proj-`, `sk-svcacct-`, `sk-admin-` and the legacy 48 characters, DeepSeek, OpenRouter, Langfuse, LiteLLM, unknown 20 to 48 base64url; Slack bot, user, legacy bot, legacy (ids of 6 digits or more), legacy workspace with its version digit and configuration tokens; Tailscale `tskey-auth-`, `-api-`, `-client-`, `-scim-`, `-webhook-` and the untyped key of 2021; and, which the rule before v0.9.16 let through, Slack's refresh (`xoxe-1-`), app-level (`xapp-`), `xoxo-` and client session (`xoxc-`) tokens, session cookies and webhook URLs. A random base64url `sk-` key passes only when it holds no uppercase letter or underscore, at most 1 in 6,400 for 16 characters and 1 in 172,000 for 22; a legacy Slack workspace token without its version digit passes 1 time in 230 for 10 letters and digits and 1 in 630 for 12. A fact name is lowercase letters, digits and hyphens, so `lint-cc-sk-017-only-plain-commands`, `tskey-auth-expires-in-90-days`, `slack-xoxb-token-scopes-for-the-bot` and `slack-xoxa-2-workspace-tokens-are-retired` are no keys: before v0.9.15 the rule took `sk-` and any 16 key characters for a key and refused 97% of such names, and before v0.9.16 it took `tskey-` or `xoxa-`, `xoxb-`, `xoxp-`, `xoxr-`, `xoxs-` and any 10 key characters, refusing 99.5 to 99.9% of names with such a segment; with them it refused every curator push whose `MEMORY.md`, folder index or file named one. The trade: a secret of lowercase letters, digits and hyphens with none of its family's marks passes (it cannot be told from a fact name), and a fact name whose segment is followed by a 20-character word, for Slack a 10-digit number or two 6-digit numbers, is refused. Each step runs grep on bytes (`LC_ALL=C`, `-a`): neither a byte that is not valid UTF-8 nor a NUL hides a key, and only in the C locale does GNU grep match these bracket ranges in linear time (under the server's `C.UTF-8` a 27 KB line of `sk-` runs took 15 s, with the old rule too), so a scan costs what the blob's size does. A grep that fails (any status but 0 or 1), or a token file it cannot open or write, refuses the push. `client/internal/secretscan` holds the same seven expressions for the names a derived fact may show and for the local store's check, and decides without the gate; its test holds them equal to the hook's, the gate to their union, and the two decisions equal.

One fact per file. A file is Markdown with YAML frontmatter.

```yaml

applies_to:                               # situation join key; any subset
  paths: ["tools/hooks/pre-commit"]       # repo-relative globs
  symbols: []
  repos: ["memra"]
  hosts: ["workstation"]
  commands: ["git commit", "cargo fmt"]   # prefixes
source:
  harness: claude                         # claude | codex | pi | hermes | grok | muse | agy | dreamer | import | curator | human
  host: workstation
  session: 7146f42d-...                   # optional
  kind: observed                          # user | observed | web | derived
  imported_from: ~/.claude/projects/.../x.md   # optional, import only
  original_type: feedback                 # optional, import only: the source system's own type
  owner_quote: "never push to main without a review" # kind user only: the owner's words the fact holds (see Rulings)
  owner_quote_from: claude:6f1c2a-...     # where the owner said them: claude:<session>, codex:<session>, note:<name>
  endorsed: 3f2a9c1d0e4b                  # kind user only: the decision in review/decisions.jsonl where the owner kept this fact
  owner_words: "keep the start block short" # any kind: a phrase of theirs the fact holds, too short to be a ruling (see Rulings, Their words)
  owner_words_from: claude:6f1c2a-...     # where the owner said them, as owner_quote_from
  review: correct                         # curated, store format 4: the reviewer's verdict on the agent's note it was made from (The reviewer)
  review_reason: "the owner named it ..." # with review: why
created: 2026-10-07                       # YYYY-MM-DD
updated: 2026-10-07
superseded_by: memra-precommit-path-fixed-in-hook   # optional, name of the newer fact
retired: 2026-10-12                       # optional, YYYY-MM-DD: outdated per git, no newer fact (see Staleness check)
last_checked: 2026-10-21                  # optional, YYYY-MM-DD: the curator's rotation last judged the fact (format 1 stores only); not a change to the fact
derived_from: 3f2a9c1                     # derived/ only, git sha the aggregate was built from
origin: some-inbox-note                   # curator output only: the inbox note this fact was split from
---

Body: the fact, one to a few sentences another agent can act on. Optional
**Why** and **How to apply** lines. Link other facts as [[name]].
A [[name]] inside a fenced code block (``` or ~~~), an indented code block or an inline code span is
code, not a link: `fact.LinkSpans` skips it for lint L6 and for link repair.
```

### Types

`user_standard`, `design_decision`, `past_mistake`, `machine_fact`, `code_change`, `hot_spot`, `structure`, `history`, `user` (who the owner is), `reference` (pointer to an external system), `result` (measured numbers read from a repo's git history, generated; see Results from git). `statement` (the owner's words said once, written by code only: Statements). `unclassified` is allowed only under `inbox/`; the curator assigns a real type on promotion.

Each type is documented in code (`fact.TypeDocs`), and the split prompt shows the documentation. `hot_spot`, `result` and `result_ref` are generated by code from git: a model or an agent never writes them (Metadata checks). `user` belongs in the `user` scope only.

### Scopes

`system`, `user`, `projects/<repo>`, `machines/<host>`, `derived/<repo>`, and in a store of format 1 (Store format) `areas/<area>`, `areas/<area>/topics/<topic>` and `topics/<topic>`: an area is an ongoing system or practice, a topic a bounded work stream, owned by an area or not. An area or topic scope names a folder with a record (`_record.md`, internal/record), which the curator creates from two distinct sessions' evidence or the owner creates; a topic's name is unique across both places. In a store of format 2 `orgs/<org>` names a forge organization's folder, with a record of kind `org` that code makes (Orgs). A curated file's directory must equal its scope. Inbox files carry the scope the writer believes is right; the curator may change it.

The dreamer files a note under `projects/<repo>` for the repository the session works in: the one its cwd is in (a cwd recorded as a `file://` URL is read as its path), else, when the cwd is in none (the home directory, a folder of checkouts), the repository the window's paths point at. A path names a repository only through a real git root (`client/internal/repoid`, the one identity the dreamer, the curator's checks, the hooks, the MCP server and the tree tool all use): the nearest directory up the path, symlinks resolved, with a `.git` directory or a `.git` file. A linked worktree's `.git` file points into its main repository's `.git/worktrees/<name>` (git's `commondir` file says where the main repository is), and the worktree belongs to that main repository; a `.git` file without one (a submodule) is its own repository; a `.git` file that names no git directory names nothing, as for git. The name is the base name of the main checkout's real directory, so a symlinked checkout (`~/projects/old -> new`) and every worktree of a repository have one name. A separate full clone (its own `.git` directory, in a task folder or a scratch directory) is the repository of the main checkout in the projects directory (`$TACIT_PROJECTS`, else `~/projects`, two levels) whose origin has the same normalized URL (host and path, lower case, with no scheme, user, port or `.git`): a clone `~/tasks/t1/ginza` of `~/projects/pikadon` is pikadon, and its own directory name becomes an alias. A clone whose origin matches no main checkout, or more than one, keeps its own name, and the main checkout is never renamed; the symlink's lexical name and the origin remote's name are aliases that delivery also matches, never scopes (the names of the other remotes in the repository's config are read too, for delivery's repo aliases). A folder's name never names a repository by itself: a directory with no git root above it (a folder of checkouts, a scratch directory, a non-git project folder, a directory outside home) is in no repository. The home directory itself and its dot directories (`~/.claude`, `~/.cache`) are never a repository, but a worktree kept in a dot directory belongs to its main repository. For the paths a window mentions (as opposed to its cwd), only paths under the home directory and outside its dot directories count, each for the repository its git root makes; relative and Windows paths are not read. A path the agent works in (after `cd`, `git -C`, an edit's target) counts 3 times, any other mention once, and the repository needs 3 and three quarters of the window's count: a wrong repository hides a fact from every other session, while no repository leaves it to `user`, or `machines/<host>` for machine facts. Existing facts keep their scope: a store whose notes were filed under a folder's name (`projects/workplace`) keeps them there until the curator or the owner moves them.

A checkout whose root is outside the home directory or in a temp directory (`os.TempDir`, and `/tmp` and `/var/tmp` off Windows; a temp directory that holds home does not count), and is no checkout of the projects directory, is a clone a tool or a task made until sessions show real work in it: the dreamer files a session whose cwd is there under that repository only once 2 distinct sessions with their cwd in the checkout made file edits there (an edit or write tool call on a file inside it: Claude Code's Edit, Write, MultiEdit, NotebookEdit; Codex's apply_patch; pi's edit and write; Hermes's write_file and patch) or ran a git commit there (a shell tool's `git commit` in the cwd with no `cd` before it, or `git -C` a directory inside it). Until then the window's repository is what its paths say, as for a cwd in no repository. The evidence (session, edit or commit) is kept in the registry by root, and a registry entry for such a checkout counts in the catalog only with it.

The repository the dreamer resolves each window to is recorded in this machine's registry (`repos.json` in the state directory: name, root, aliases), which the curator's checks read with a scan of the projects directory (`$TACIT_PROJECTS`, else `~/projects`, two levels): the catalog of repositories this machine has a checkout of. An entry counts only while its root is still a git root of that name.

A checkout that is no main one (a linked worktree, whose gitfile names its main repository's git directory; a separate clone, named for the main checkout with its origin, or else for the repository its origin names) is recorded in the dreamer's registry with that repository from the first window the dreamer sees in it, and git's own list of a main checkout's linked worktrees is read with the catalog. The relation outlives the checkout: a session whose cwd is a removed worktree is filed under its repository, and the assessment finds the ancestor of a folder named for the directory (Folder records, Ancestors).

The store carries every writing machine's catalog, so a note about a repository checked out only on another machine names a known repository. The dreamer commits its machine's catalog with its notes, in its own inbox folder, `inbox/dreamer@<host>/_repos.json` (the one place a dreamer writes, so no two machines write one file), whenever it differs from the one at HEAD: each repository's name, its aliases (a symlink's, a separate clone's, its origin's name), its remotes' normalized URLs, the directory names (never the paths) of its linked worktrees and separate clones the machine has seen (`checkouts`) and, for a checkout outside home or in a temp directory, how many sessions worked there. No local path and no user name is in it (a URL's user and password are dropped; a remote on the file system has no URL), it is generated by code and never edited by hand, and its name, with an underscore and no `.md`, is no fact's: no fact walk, search index, tree index or hook reads it. The metadata checks read every machine's catalog in the store with this machine's own. A machine with the local layer writes its catalog to its overlay instead (`local/inbox/dreamer@<host>/_repos.json`, Local layer), which never leaves the machine, and its checks read the store's catalogs and that one.

### Source kinds

- `user`: the owner's own words, provably: a ruling (see Rulings). Every kind user curated fact carries the evidence.
- `observed`: an agent concluded it from what happened (an error, a measurement, a path that exists).
- `web`: derived from fetched content. Never allowed under `system/`; the curator promotes web facts only after review.
- `derived`: generated by the curator from git or other deterministic sources, no model involved; must carry `derived_from`.

## Rules the linter enforces

| id | rule |
|---|---|
| L1 | frontmatter parses; `name`, `description`, `type`, `scope`, `source.harness`, `source.host`, `source.kind`, `created` present |
| L2 | `name` equals the file stem and is a slug (`[a-z0-9][a-z0-9-]*`) |
| L3 | `type` is a known type; `unclassified` only under `inbox/` |
| L4 | curated file directory equals `scope`; an inbox path is `inbox/<harness>@<host>/...` with a known harness and a slug host, and the note's `source.harness` is that harness |
| L5 | `created`, `updated`, `last_checked` are `YYYY-MM-DD` |
| L6 | every `[[link]]` in a curated fact names an existing fact (inbox links are the curator's to resolve on promotion; the curator repairs a curated fact's dead links, see Link repair) |
| L7 | `superseded_by` names an existing fact |
| L8 | no `system/` fact has `source.kind: web` |
| L9 | `derived/` facts carry `derived_from`; no other fact does |
| L10 | `MEMORY.md`, if present, equals the generated index (with the `memory_md` setting off the writers remove it instead of generating it: README, Client settings) |
| L11 | `description` is at most 200 chars; body is not empty |
| L12 | `source.kind` and `source.harness` are known values |
| L13 | `conflicts_with` names existing facts, never the fact itself |
| L14 | `retired` is `YYYY-MM-DD` and is not on an inbox fact |
| L15 | in a store the rulings audit has run on, a curated `source.kind: user` fact carries owner evidence (harness `human`, `owner_quote` with `owner_quote_from`, or `endorsed`); everywhere: `owner_quote` is in the fact's description or body (normalized, see Rulings), long enough to be looked up, and has its entry in `review/owner-quotes.jsonl`; `owner_quote_from` is a source and an id (`claude:`, `codex:` or `note:` today; any lower-case source name passes, so a ledger entry from a source no longer read stays valid); `endorsed` is a decision id that stands in `review/decisions.jsonl` as the owner's and keeps this fact; no `owner_quote` or `endorsed` on a fact that is not kind user; `owner_words` and `owner_words_from` go together, the fact holds the phrase, and the ledger has its entry marked words. Inbox notes may claim kind user without evidence: the curator decides |
| L16 | in a store with a root `_index.md`, every curated folder's `_index.md` equals the generated one (Tree index), and no folder without facts has one; in a store from before the tree, only the index files it holds are checked |
| L17 | folder records: the format marker reads; no record, no fact in `areas/`, `topics/` or `orgs/` and no `last_checked` in a store without it; no org record, no record's `org` or `forge` and no fact in `orgs/` in a store of format 1; every `_record.md` parses strictly and holds as it stands (kind for its folder, name its last part, the history newest first with the current status on top, aliases unique store-wide, `suppressed_by` a live folder of the same broad kind with no chain or loop, an area or topic of the curator's on 2 distinct sessions, the owner's words of an entry backed by the quote ledger); a fact in an area or topic folder has that folder's record; with `records_complete`, every project folder with facts has a record |
| L18 | in-place notes: a body line of a curated fact that starts `> superseded ` has the whole form `> superseded YYYY-MM-DD: <old> -> <new>`, both sides non-empty (Supersede, never delete) |
| L20 | statements: a fact of type `statement` is curated (never an inbox note), in a store of format 2 or in this machine's local layer, `source.kind: observed`, carries `owner_words` and `owner_words_from` (which L15 checks against the ledger), and its body opens with `You said once (<day>): "<their words>"`, the words being `owner_words` and the day no later than `created` |
| L21 | the reviewer: `source.review` and `review_reason` go together, only on a curated fact with an `origin`, in a store of format 4, with a verdict a curated fact carries (`correct`, `uncertain`, `nosource`, `confirmed`) that the reviewer's ledger holds on its note (the owner's answer may stand over the verdict it was stamped with); every line of `review/agent-reviews.jsonl` parses and is one code writes (`ledger.ValidReview`) |
| L19 | overviews: every `_overview.md` parses strictly, names its own folder, is at most 8 KB, and every paragraph and bullet cites `[[facts]]` the store has. That a cited fact is still live is the overview step's check (a dead citation makes the overview due again), so a retirement elsewhere never turns a write red |

The proof for the linter is that it fails on today's auto-memory directories (their `metadata` key is unknown to the strict decoder, and they carry no `scope` or `source`) and passes after `tacit import`.

## Metadata checks

The metadata a model or an agent writes is checked by code before the write (`client/internal/validate`): the curator's split and rulings entries, `tacit add` and the MCP `tacit_add`, the Hermes provider and the local layer's curator. Code supplies a value only where it derives it reliably (the repository of the session's cwd through repoid, the host, the session, a default for a field left out: `unclassified`, `user`, `observed`); a value the writer gave is accepted or refused, never replaced by a guess of code's. What code cannot check reliably (whether a fact is task-only, whether a command is right, which machines an `applies_to.hosts` names) is not checked.

- **scope**: `user`, `system`, `projects/<repo>` or `machines/<host>` (`derived/` is for generated facts). `projects/<repo>` must name a repository that exists: one this machine has a checkout of (the catalog, Scopes), one in another machine's catalog in the store (or, on a machine with the local layer, in its overlay's), or, until projects are assessed on their own, one whose `projects/<repo>` or `derived/<repo>` folder already holds facts in the store (or in the local layer, for the local curator). A checkout's alias (a symlink's name, its origin remote's) is refused as a scope with the repository's own name in the message. `machines/<host>` must name this machine, one with a key in `keys/` or an inbox directory, or one whose folder holds facts. A scope in capitals is the same scope in lower case.
- **type**: one of the defined types; never a generated one (`hot_spot`, `result`, `result_ref`) nor `statement` (code writes it from the owner's verified words); `unclassified` only on an inbox note; `user` only in the `user` scope.
- **kind**: `user`, `observed` or `web`; the split's `statement` for the owner's words said once (Statements).
- **an org's scope**: `orgs/<org>` needs format 2 and the org's live record; a fact a model or an agent files there must name two or more of the org's repositories (the project records whose `org` is it: membership comes from the forge, never from what a fact mentions), in `applies_to.repos` or as whole words, or the org itself; a fact about one repository goes to that repository.
- **applies_to.repos**: each a repository name the store or this machine knows (its own name or a checkout's alias), never a path, URL or `owner/repo`: a name no delivery can match hides the fact from every hook.
- **applies_to.paths**: each repo-relative (no leading `/`, `~` or drive letter, no `..`, no URL, no backslash) and a glob that parses. Code makes an absolute or `~` path relative where that is reliable: one inside this machine's checkout of the fact's repository (its `projects/<repo>` scope, else its one `applies_to.repos` name), the checkout being repoid's for the path (symlinks resolved on both sides; a worktree or a separate clone of the repository is its checkout). Any other absolute path is refused. A `machines/<host>` fact may keep absolute paths: they are that machine's.
- **attribution**: a fact that is not the owner's verified words (an owner ruling with a verified quote of theirs; for stored facts also a statement, or words of theirs the ledger backs) may not claim their authority in its description or body: say the owner ruled, said, decided or wants something (`owner ruling`, `owner rule(s)`, `owner ruled`, `owner's rule`, `the owner said`/`says`, `the owner decided`, `the owner wants`/`wanted`), except right after a negation ("not an owner ruling"). An inbox note that claims kind user may: the curator decides. It is one check (`validate.Attribution`): new writes are refused on it, and delivery holds back a stored fact that fails it (Delivery, Provenance).

A note whose own scope is a `projects/<repo>` that names neither a known repository nor an alias of one waits in the inbox instead of being curated: its repository may be checked out only on a machine whose catalog has not reached the store yet. The curator records the day it first held the note back (`deferred_repo` in `curator.json`, `curator-local.json` for the local layer) and passes it over, full run and quick, for up to 14 days; once its repository is known it is curated at the next run and leaves the record, and after 14 days it is curated like any other note (its entries face the checks, the model's one retry and the failure strikes). The report line counts the notes waiting (`deferred_repo_notes`). Only the note's own scope waits: a split entry that names an unknown repository is refused as before.

A refused `tacit add` or `tacit_add` returns the reasons and writes nothing. The curator checks each entry as it would be written (after the ruling evidence decides its kind) and sends a refused answer back to the model once, with every problem and the value it refused (`curate.SplitChecked`); the rulings pass sends back the same way an answer that is no JSON array at all (a sentence before it, a code fence after one) or one that does not parse, with the parser's reason, while the split pass splits its batch for one, as before (its answers are long, and no such refusal of one was measured). The model's second answer is taken or refused as it is, and a refused second answer is an invalid answer as before (the batch is split, a note that fails alone is counted). The rulings pass is told that its empty answer is `[]` and nothing else: asked only for "a JSON array (possibly empty)", Opus 5.5 put a sentence before 44 of 90 answers for 30 recent notes drawn at random (and 8 of 20 for the note the quick runs failed on), each alone in its batch as a quick run's split ends, and every one came back clean when sent back; with the empty answer spelled out none of the 110 had one, and of 20 notes of the owner's words 18 got as many answers with an entry quoting them, the other two quoting an agent's instruction, not the owner (eval/VALUE.md, "The rulings answer"). Before v0.9.16 such an answer was not sent back: a batch was split for it and a note alone failed the run, every quick run, until the full run took it. The model's safety filter refusing the prompt (Claude's `safeguards flagged this session` notice) is the notes' too, not the route's: the same notes are refused every time, so the batch is split the same way, a note refused alone is counted as failing alone (and set aside after its strikes), and the route is not backed off for it. Before v0.9.14 a refusal was a route failure: the run backed off and the next run sent the same batch, so its notes were never curated (the Mac's rebuild, 2026-10-29: 94 notes held, two full runs writing nothing). The report line counts the answers sent back (`validation_retries`), and `invalid_entries` logs each refusal by entry, field and rule (an answer refused whole, by the parser's reason), never the value.

## Folder records

In a store of format 1 (Store format) a project, area or topic folder (`projects/<name>`, `areas/<name>`, `areas/<area>/topics/<name>`, `topics/<name>`) has a record, `_record.md` (client/internal/record): strict frontmatter, not a fact. It says the folder's `kind` (`repo`, `folder` for a project folder that is no git repository, `area`, `topic`), `name` (the folder's last part), a one-line `description`, its `status` (`active`, `dormant`, `dead`, `shipped`, `needs-review`) and `was`, every status it had, newest first and the current one on top, each with its day, who decided (`opus`: the curator's model or an agent's command; `owner`) and why. `evidence` is what code gathered for the decision and is written by code only; `created` and `created_by`; `aliases`, other names of the folder, unique store-wide; `suppressed_by`, the folder that replaces it (the same project under another name); a dead project's `successor`, another project that took its place (Successors); an area's `tools` (globs on MCP tool names, `mcp__<server>__<tool>`) and `commands` (prefixes); a topic's `repos`; a project folder's `roots`.

**What code checks** (`record.Validate`, at every write and as lint L17): the kind matches the folder and the name is its last part; the history only grows, by at most one entry per write, dated that day, written by the writer, with a why; an agent's entry cites a session, note or commit code can find (`session:<id>`, `claude:<id>`, `codex:<id>`, `note:<name>`: the dreamer's registry, a note's `source.session`, the quote ledger; `commit:<sha>`: one of the folder's own commits under this machine's git identity that its evidence listed), and a git date alone is no reason (an active or dormant status code set from the folder's dates is code's own evidence: Status from dates); an entry is the owner's only from their channel (the Folders page of `tacit review` and `tacit app`, an owner commit) or from their own words that the quote ledger backs and that name the folder (an owner quote beats the model's judgement when it is about that folder; one that only mentions it is evidence); an owner's status is never replaced by an agent, only flagged `needs-review`, the owner's value kept in `was`; aliases are slugs no other folder has; `suppressed_by` names a live folder of the same broad kind (project to project, area or topic to area or topic), never itself and never into a chain; a `successor` is only a dead project's (not a suppressed one's) and names a live project folder with a record, never itself; an entry's `words`, `words_from` (a note or quote code can find) and `words_on` (a day no later than the entry's) go together; an area's new tool patterns name MCP tools (they start `mcp__`: a new pattern for a harness's own tool, `Bash`, is refused; one a record already holds stays, lint included), and an agent's new pattern matched a tool call of a session it cites (the dreamer's tool usage, `tools.json` in the state directory, names only); an area or topic the model creates rests on 2 distinct sessions, which code counts.

**Assessment.** `tacit assess`, also a step of the full `tacit curate` after the batches: every repository of the catalog (this machine's and the other machines' `_repos.json`) and every project folder with facts that has no record, and every record whose evidence changed since its decision (new work after a dormant or dead status, its checkout gone), go to the curator's model in batches of 10 with the evidence code gathered: the git root and remotes, commits under this machine's git identity with their first and last day, the sessions that edited or committed there (the dreamer keeps them per root, `repos.json`), the sessions whose notes are filed there, other machines' catalog entries, the names repoid proves are one checkout, the folder's newest facts, the owner's words that name it (redacted), and the checkable evidence of its life (Status from dates): the forge's record of its repository and code's status from the owner's activity days. The model answers kind (or `none`: not a project, recorded `dead` with the reason, so it is not asked again), status, why, description and optionally aliases, suppression and roots; a refused answer goes back once with the problems, and a second refusal waits for the next run. A repository's own name is decided before a folder that is another name of one, and a name that exists before one that exists nowhere; folders whose names follow one pattern (digits as `#`: `kv-013-g1`, `kv-140-g2`) come together, and each batch is shown the decisions already made on folders alike (that pattern, or this run's folders with the same evidence shape). A name that exists nowhere and follows a pattern is also proposed the repositories its folders alike were folded into. `needs-review` is not a parking state: the owner may review a folder, but nothing waits on it ("Need review is not something that will surely happen, its what better happen, but nobody promise, the agents need to still try to fix it", 2026-10-22). A folder the model leaves `needs-review`, and one whose decision was refused, comes back on later runs with extra evidence code gathers for it, wider with each attempt (up to 6 items of each kind per attempt, times the attempt, at most 4): the live facts in other folders that name it (its name, aliases, other names of its checkout, its forge name, as a whole word or as a path; a plain word of under 8 letters such as `run` counts as a word only while it is in at most 20 facts) or list it in `applies_to.repos`; the sessions behind those facts; the decisions on folders with near names and on the other repositories of the same forge owner; the owner's turns that name it, the newest first, at most 2 of one session, each with its day (`owner's turn (claude:<id>, <day>): ...`; what they said last decides a folder, and v0.9.9 showed each session's first such turn only, so a session's deciding words late in it never reached the prompt). The prompt marks each item new since the last attempt. Such a folder waits only when that wider search found nothing new (each item has a key, and the keys are in the hash of what the model reads of it), and even then it is asked again 7 days after its last decision: the forge's answers on names are kept 7 days, so each retry reads them fresh, and a daily retry on the same evidence would pay for the same answer. A folder refused in 2 runs on the same evidence, the wider search included, waits the same way. Every attempt, with its items, the new ones and its outcome, is a line of `assess-attempts.jsonl` in the state directory, and `assess-held.json` keeps each folder's last fingerprint, day, attempts and items. Each batch is one curator commit (`curator: assess: ...`). Every dry claim of a decision is checked (Checked claims).

**Status from dates.** Whether a folder is active or dormant is a question of dates, and dates are checkable, so code answers it, the same for every run (the owner, 2026-10-23: "why would different runs see different dates? last commit is last commit"; v0.9.2 showed the forge's commits only on a re-attempt, so whether a run saw a folder's newest commit depended on how its first ask went, and 17 of the 19 statuses that differed between three v0.9.3 shadow runs were active against dormant on dates). Before a project folder's first model call code gathers the owner's activity days (`assess.Activity`): the days of its commits under this machine's git identity in a checkout here (the commit evidence, cached by HEAD), other machines' catalogs' first and last own commit and work day, the sessions that worked in it here (the dreamer's registry) and each session that filed a note there on its newest day there, a session's day never later than the owner's last turn in it when their history here has one (a rebuild dreams and files months of sessions on the days it runs; on the rig's rebuild a session that ended on 2026-09-28 counted as the owner's activity on 2026-10-25), and the days of the forge's newest 100 commits of its default branch made by the owner's forge account (bots' and others' commits are listed, not counted). The forge's record of its repository (last push, archived, latest release, the newest commits with their authors' accounts, those by the owner's account citable as `commit:<sha>`; cached a day) is shown with them; a repository a remote names that the forge has under no name and renamed under none is deleted. Code's status: days in a row are one stretch of work; the folder's typical gap is the median of the gaps between its stretches when it has 3 or more, else 8 days; it is active while the days since its last activity are at most twice its typical gap, never less than 7 days nor more than 32, and an archived repository, or one the forge has deleted, is never active. The bounds come from the Mac shadow copies (108 project folders with owner activity): 3 gaps make a median a middle value, and 63 of the 108 have them; 8 days is the median of those 63 folders' own medians (quartiles 5.5, 8, 10.5); half of all 622 gaps are 7 days or less, so a shorter pause is the owner's ordinary break; 80% end within 32 days, past which nobody is on it lately whatever the rhythm. The prompt shows the days, the measure and the status (`status (code's): ...`). The model still decides the kind, the ancestor or independence, and dead or shipped on explicit evidence, which code checks: `dead` stands when the forge has the repository archived or deleted and code found no successor for it (no ancestor candidate, no candidate repository: one with a successor folds into it), or the why cites a note shown for the folder; `shipped` when a release the forge lists or a cited note shown goes with the owner's words shown for the folder, cited by their ref; an answer of active, dormant, an unbacked dead or shipped, or `needs-review` for a folder with the owner's own commits (git says what it is, the dates whether it is worked) takes code's status, its why code's sentence (`code: <status> from its dates: ...`, citing the newest citable day) followed by the model's words on what the folder is; such an entry needs no other citation (`record.Env.CodeStatus`). `needs-review` stands for a folder dated by sessions alone, and a fold, kind `none` and the owner's quote stand as answered; an owner's status is never replaced. A folder with no activity day keeps the model's status, from the owner's words and the notes. When the dates move a record of the model's across its window, code writes the new status itself (a code decision, no model call). Dates never make a folder dead or shipped.

**Owner words beat dates.** The owner's word on a folder's status is stronger than its dates, unless the owner seems to have changed their mind (the owner, 2026-10-23: "quote of me is stronger than dates, beside if its seems like i changed my mind or so"). Before a project folder's first model call code also gathers the store's notes in other folders that name it (its name, aliases, other names of its checkout or its forge name, as a word, a path or in `applies_to.repos`, as the re-attempts' store search finds them), the owner's rulings first, then their statements, facts holding their words, decisions (type `design_decision`), and other notes, newest first within each, at most 8 shown (`notes in other folders that name it`). A note that claims the owner's authority without their words (delivery's check, `search.FactClaims`: "Owner decided ...", "the owner wants ..." on a fact that is not their ruling and holds no words of theirs the store backs; Provenance) is one of the other notes whatever its type, shown as an agent's note that claims their authority: it is never an `owner_status` item, and no dead or shipped answer rests on it against the dates. Before it gathers anything the assessment runs the rulings audit's promotion, code only: a curated store fact that claims their authority and whose quoted or attributed phrase is found in the owner's history (their turns, their app notes, a quote the ledger holds) becomes their ruling, or holds their words when the phrase is too short to prove the rule, with its quote ledger entry, in one curator commit (`curator: rulings promotion before assess`; nothing is demoted and the audit marker is not touched; a store the audit has not run on is left alone, and the local layer's runs leave the store's clone alone). The owner's notes are shown with their text, the others by their description, each with the other project folders its text names (a name with a dash or of 8 letters or more as words, dashes read as spaces; a short plain word only when the note lists it in `applies_to.repos`) and where each leads now (`gishra (renamed: tower-crane)`, `x (suppressed into projects/y)`). v0.9.4 showed them only on a re-attempt, and a folder whose dates settled it was never re-attempted, so a folder the owner had declared dead stayed active by its dates. The model reads them and, for each note of the owner's four tiers that states this folder's status, answers an `owner_status` item: `says` (`dead` for obsolete, abandoned, removed, to be deleted or replaced; `shipped`; `dormant` for paused), the note's words copied exactly, `from` (`note:<name>`) and, for dead, the `successor` its words name. Code checks each like a statement: the note is one shown for this folder and of the owner's tiers, the words are in its text, and a successor is named in the cited words themselves together with this folder (its name or another name code found for it: an alias, its forge name, another name of its checkout), so the answer does not turn on which sentence of the note is cited (dashes read as spaces: "Tower Crane" names tower-crane), not elsewhere in the note, and is not listed with this folder in one enumeration of the things the words retire ("deslop, sync-docs, drift-detect ... fold into one lint-first cleanup tool" names no successor of sync-docs; `assess.coListed`: an item of at most four words between commas, "and", "or", one that names both being no item of such a list); a successor inferred from the rest of a note or a related plan is refused, and words that name none say dead with no successor. A refused item goes back with the problem. The day of the words is code's: a statement's own day, else the first date in the words, then in the note's description, then in its body (none later than the note), else the note's day. The newest item supersedes the older ones. Its status stands over the dates unless the owner really worked on the folder after that day; activity before it never counts. Real work is code's to classify, never the model's: a session that worked in the folder's checkout or folder (the dreamer's registry here, another machine's catalog's last work day), or a commit of the owner's (under this machine's git identity in a checkout here, or by the owner's forge account among the forge's newest 100 commits) whose diff changes more than maintenance files. Maintenance is dependency manifests and lockfiles (`package.json`, `go.mod`, `go.sum`, `Cargo.lock`, `requirements*.txt`, ...), CI and workflow configuration (`.github/`, `.gitlab-ci.yml`, ...), version and changelog files (`VERSION`, `CHANGELOG.md`, a plugin manifest in a hidden directory), and any commit a bot authored (an account or name with `[bot]`, dependabot, renovate, github-actions); a merge's diff is its first parent's, so merging a bot's bump is maintenance, and a security fix that only bumps a dependency is maintenance. Code reads the files from git here (`git log --name-only`, merges against their first parent) or from the forge (`gh api repos/<owner>/<name>/commits/<sha>`, at most 12 per folder and day, newest first, stopping at the first real one, kept for good in the forge cache); another machine's commit day neither shows proves nothing either way. With no real work after the words, the record takes their status (`code: dead on the owner's words of <day>, note:<name> (<day>): "<words>"; replaced by projects/<x>; <what code found after that day> (its dates alone say active; ...)`), and its entry keeps the words, where they are and their day (`words`, `words_from`, `words_on`; store format 3). With real work after them the dates stand, and the why says `Owner activity after the <day> statement (...)`, citing the words and the work; `review/<date>-assess.md` gets an optional `check?` item on the note (`outcome=activity`): nothing waits on the owner's answer. A status resting on the owner's words is never moved by the dates (no drift); each run asks it again only once real work after their day appears. A dead or shipped answer that rests on a note it cites (with no `owner_status`; never a note that claims the owner's authority without their words) is the note's word against the dates the same way: code takes it only while there is no real work after the note's day, and keeps the note as the entry's words. A record whose last decision did not see a note of the owner's tiers that names it (`assess-held.json` keeps the notes each decision saw, by their text, so a note moved to another folder is the same note) is asked again once. A ruling's or a fact's words of theirs are dated the same way, by the day they said them (the quote ledger's `said`, else their turn in the history here; Statements), never by the day the fact was filed: a rebuild files every note on the days it runs. Words that stop, bank or pause work, or put it off "for now", say dormant, never dead: the prompt says so, the model flags words of an item that limit it in time (`temporal`, copied from the words), and code refuses dead on them. Work after words that say dead does not revive a folder whose repository the forge has deleted or archived since: no commit can follow that, so it came after the work, and the words stand (the why says so); such a record is not asked again for that work.

**The owner's quote on its status.** A decision whose `owner_quote` (their words in one of their turns, checked as before: Rulings) gives the folder's status goes through the same checks as the owner's words on a note. What the words say of the status is the model's reading, and code holds it to what it can check: the model copies from the quote the words that limit it in time (`owner_quote_temporal`: "for now", "until the release") and, for dead, the words that make an end of the folder (`owner_quote_final`: drop it, kill it, delete it, replace it with another); code refuses dead on flagged words, and dead with no final words unless the forge has the repository deleted or archived ("we are stoping development of memra. bank what you have in one branch, take down all servers" is dormant: the owner can take it up again). The words are dated by the day the owner said them (their turn's day in the history here, else the quote ledger's `said` for the same words; the ledger line the decision writes records it), and a dead, shipped or dormant status on them stands over the dates unless the owner really worked on the folder after that day (Owner words beat dates: the same classification of sessions and diffs); with such work the dates stand, the entry is code's (`Owner activity after the <day> words (...)`, no quote), and `review/<date>-assess.md` gets the optional `check?` item. With no real work after them the entry is the owner's, with the quote, and its why is `code: <status> on the owner's words of <day>, <ref> (<day>): "<words>"; ...`; like a note's words it is not moved by the dates and is asked again once real work after that day appears. An owner's status that rests on a quote of theirs is the only one an agent's entry may replace with a status other than `needs-review`: code's status from its dates, on that work. An active status on their words stands as answered. `tacit assess --recheck-quoted` asks again about every record whose status rests on the owner's words (a quote, or their words on a note), with these checks.

**Successors.** When the owner's words say another project replaced a dead one ("X replaces Y", "Y is replaced by X"), Y's record keeps status `dead` and gets `successor: projects/X` (store format 3). Code resolves the name to the live project folder that holds it now (its folder, a folder whose name or alias it is, through suppression, the forge's current name of a renamed one) and checks it: a project with a record, not suppressed, not this folder and no folder that is no project; a successor this run decides later makes the decision wait to the end of the run (no model call), and one with no record yet that is a project all the same (a repository by its check, a folder with facts) is linked by code once it has one (`assess-held.json` keeps the pending links; the why says `linked once it has a record`). A successor is not a suppression. `suppressed_by` says the folder is the same project under another name, or a part of one: its facts move to the winner and a session in either reads both. A successor is another project that took this one's place: Y stays, its facts stay as its history and are quiet (dead), and nothing moves. The tree shows `Replaced by: projects/X` on Y's record and `dead, replaced by projects/X` in its folder list; `tacit_search` adds `# projects/Y is dead, replaced by projects/X: its facts are its history` under a page with Y's facts. A session in Y's checkout gets X's rules and standards lightly at SessionStart (at most 2, as an org's), and its title says `Y (dead, replaced by X)`. A successor goes with the status that names it: any other status drops it.

**Names code proves.** Each assessment's last code step, with the forge's names and orgs, adds to a live project record the other names code proves its repository goes by: the catalogs' other names of its checkout (a symlink's, the origin remote's) and clones with its origin (`check.Checker.Same`), and the forge's current name when it differs from the folder's. A name another folder has (as its folder, name or alias) or that holds facts is left out: that folder gets its own record, suppressed into this one. The checks go into the record's evidence. The model's aliases stay as before; code no longer depends on the model to add a name a check proves.

**Suppression.** A folder whose record has `suppressed_by` is read as the folder replacing it: a write to its scope goes to the winner (the metadata checks redirect it), `tacit_tree` shows the winner and then what is left, `tacit_search` with its scope searches both, a session in either repository reads both. The migrate step (`tacit migrate`, a step of curate after assess) moves its live facts, bounded per commit (`curator: migrate: <loser> -> <winner> (n fact(s): ...)`): each gets a copy in the winner's folder under a new name (names are unique store-wide), keeping its dates, source, text and applies_to with the loser's names in `applies_to.repos` mapped to the winner's and `origin` naming the old fact; a copy that only restates a live fact of the winner is not written and the old fact points at that fact; the old fact gets `superseded_by` and `updated` only, and a fact that pointed at it points at where it went. Rulings and facts with the owner's words move the same way under any suppression, their quote ledger lines copied for the new name; one waits for the owner only for a reason code can state (an open contradiction with a fact of the winner, an endorsement bound to the old name, evidence the store does not back), as an `ask` line in `review/folders.jsonl`. A held fact is planned again on every run: once its reason no longer holds (the verifier settled the contradiction) it moves and its question gets a `close` line, and a quote the ledger holds under another fact's name (a copy, a rename) with the same words from the same place backs it as its own line would. `tacit rescope --plan FILE` moves the facts a plan names the same way. The live facts of a folder whose record says it is no project (assess's `none`) move the same way where their own evidence puts them: the one repository their paths and forge URLs name, read as for an org's migration (Orgs), else the one the session that wrote them worked in (the dreamer's registry), when its folder is a live project that is not quiet; with no such evidence, or two repositories, they stay, quiet. `tacit_fact` on a replaced fact shows the live end of its chain first.

**Areas and topics.** The split prompt lists the live areas and topics an entry may take as its scope, and an entry may carry `propose: {kind, name, area?, description}` when none fits; the entry is filed as it would be anyway and code appends a `propose` line to `review/folders.jsonl`. The assessment counts the distinct sessions behind each proposed name and asks the model only at 2 or more, with the tools those sessions shared; the model makes the area or topic (its facts move into it), folds it into an existing one (an alias) or rejects it, and a `close` line ends the proposals. The owner makes one on the Folders page whenever they like.

**Delivery.** Dead and shipped folders are quiet: hooks deliver nothing from them (the search index marks their facts; the SessionStart block, the prompt's search and the PreToolUse push leave them out), and search and the tree still find them. A session reads by default the areas and topics whose record is active or needs review (a topic tied to repositories only in their sessions); the others are listed and read when named. An area's facts reach a session before it uses the area's tools, a topic's when the prompt names it (Delivery, "Areas and topics"). Every hook takes the names the records give the session's repository from the index: a folder suppressed into it, the folder it is suppressed into, the winner's aliases. A session outside any git repository, in a place the `roots` of a live project folder of kind `folder` name for this machine (the longest such root; code fills `roots` in from its evidence, the folders of that name sessions worked in, and checks any the model gives exist here), reads that folder's facts as a repository's at SessionStart, at the prompt and in `tacit_tree`/`tacit_search`.

**Orgs.** A forge organization (GitHub: `gh api users/<name>` answers type `Organization`; a personal account, type `User`, has no org folder) whose repositories the catalogs' remotes hold has a folder `orgs/<org>` (format 2) with a record of kind `org`, made by code from that check (its evidence keeps it; no session needs citing). Code makes one for a project folder named for an org (`projects/agent-sh`): that folder becomes the org's, recorded dead as no project and `suppressed_by: orgs/<org>`, and never goes to the model; and one for an org two or more live project records belong to. Each live project record carries `org`, the owner of its forge URL (the origin of this machine's checkout, else its one remote on the forge, else the one under the gh account) when the forge says that owner is an organization, and `forge`, the repository's current forge name (Planned renames); code maintains both on every assessment, with the checks in the evidence. An org folder is never folded into another folder, and only the project folder named for an org folds into it (`record.OrgFolds`). The migration moves each live fact of the folded project folder to the one repository its own evidence names (the paths it names: each `~` or absolute path that starts the text or follows whitespace, a parenthesis, a quote or a backtick, read once, the places Ancestors reads first, at most 40, none under `/proc`, `/sys`, `/dev` or `/net` (a process's own view, another host's export); a path in a checkout here names the repository repoid makes of it when the catalog takes that checkout (Scopes: one outside home or in a temp directory, and no checkout of the projects directory, needs work from 2 sessions) or lists a repository of its name that shares a remote with it (the same repository by another path, such as a bind mount or a clone of a fork), and nothing otherwise, a checkout whose name is no slug (a submodule or a vendored clone such as `third_party/llama.cpp`) being read as the checkout holding it; so a checkout under `/tmp`, `/data` or `/workspace` is read as one under `~` is and counts once the catalog takes it, a task's scratch clone the catalog does not take names nothing, and a route such as `/v1/messages` has no git root and names nothing; a path with no checkout here, another machine's, under a home's projects directory (`~/projects`, `/root/projects`, `/home/<user>/projects`, `/Users/<user>/projects`, so never a tool's `~/.claude/projects` or a route such as `/api/projects/<name>`), names the checkout that projects directory path names in some machine's catalog (the first level by its name or another name of it, the second, below a folder of checkouts, by its own name), or the live folder a project record of that name resolves to, such as an old name the forge renamed; the forge URLs it names; else the checkouts its session worked in) when that repository's folder is a live project; a fact that names none, or two or more, stays in the org as an org-wide fact. A model files a new fact in an org only when code verifies it names two of the org's repositories or the org (Metadata checks); the split lists the orgs of a batch's repositories with their members. Delivery: a session in a member repository reads the org's folder by default in `tacit_tree` and `tacit_search`; its SessionStart block adds the org's rules and standards lightly (at most 2, after the repository's own), and the prompt's search takes the org's folder as a scope, so its rules, standards and decisions reach the prompt by match. The tree lists an org's member projects. With the local layer the same holds in the overlay (a work org lives only there).

**Planned renames.** A record's name is its folder's: the intended name. Its `forge` field is the current forge name (a normalized URL, `github.com/<owner>/<name>`), from the forge's answer for its forge URL, which follows renames, so a rename on the forge updates it and leaves the folder. Every reader shows a project whose forge name differs as `<intended> (GitHub: <current>)`: the tree's folder line and record (`Name: pikadon (GitHub: ginza), https://github.com/...`), the SessionStart title. Among the names one repository goes by (another name of its checkout, a symlink's or the origin's; clones with one origin; the forge's current name of a renamed one), the canonical folder name is code's, in this order: the owner's decision (a decision code made of their statements, or a ruling the statements step read, whose canonical claim names one of them: Statements), else the main checkout's directory when every name a catalog has is one directory's (repoid; two main checkouts settle nothing), else the forge's current name. The prompt shows it as `check: the canonical name of this repository is <name> (<evidence>)`; a decision that keeps another name live, or folds the canonical one into another, is refused with that output.

**Code's folds.** Two kinds of project folder are decided by code, its decision checked like the model's (a refused one goes to the model): a name the forge says was renamed folds into the current name when that exists by its check and has a live folder; a name that exists nowhere (Checked claims) folds into the one repository at least half of its live facts point at by their own evidence, none pointing at another (the paths and forge URLs they name as for the org's migration; the repository-relative paths they name, a file path with a folder in it or a folder `<dir>/**`, that of two or more proposed repositories checked exist only in that one, at HEAD of its checkout here or else at the forge's default branch (`gh api repos/<owner>/<name>/contents/<path>`, cached); else their sessions' checkouts), recorded dead with the checks in its why. A candidate whose repository is decided later in the run waits to the end of the run; code's decisions are a commit of their own before the model reads the rest of the batch.

**Ancestors.** A folder clearly related to another is presumed part of it (the owner, 2026-10-23: "when building an index of content each piece that clearly related to another should tried to find it ancestor"); the assessment's job is to find which. Code finds a project folder's ancestor candidates, best first: **git**, the folder's name is the directory of a recorded linked worktree or separate clone of a repository (Scopes); **path**, paths in facts about it (its own, the repository's own, or its sessions'; a path under `~` or a system root, `/Users`, `/home`, `/opt`, `/etc`, `/var`, `/usr`, `/srv`, `/mnt` or `/Library`, so a forge route such as `/repos/<owner>/<name>/pulls` is none) put a directory of its name inside a known repository's tree or its worktrees directory (`<repo>-worktrees`); **name**, its name holds a known repository's name as whole dash-separated words, four letters or more, unless two or more repositories of their own (a checkout with a remote of its own name) hold that name too, a family's name; and, for a name that is no repository by its check, **sessions**, the sessions behind its facts (their own or their inbox note's) filed facts in a repository's folder too, half of its sessions or with a quarter of its facts read pointing at that repository, or **facts**, half of the facts read point at it, by their own paths and forge URLs (read as for the org's migration, Orgs) or repository-relative paths checked at the repository's checkout or forge. Once a folder is related, code's proposed repositories and the repositories its facts name as words join the ranking. Code also lists the folder's **independence** evidence against them, each item with a key: its own commits in a checkout of its name (`commits`), a remote of that checkout no ancestor has (`remote:<url>`), a forge repository of its own name that is no ancestor's, by its name check or a URL or `owner/name` its facts name (`forge:<owner>/<name>`), two or more sessions that worked in a checkout or folder of its name (`work`), or facts of two or more sessions that name paths in a folder of its name in a projects directory (`work:paths`). A related folder stands alone (no `suppressed_by`: a status of its own, `needs-review` or `none`) only when its decision cites one of those keys in `independent`, or rests on the owner's quote; `assess.Enforce` refuses it otherwise, naming the best ancestor, and with no independence item it must fold. The other way, a related folder whose independence shows its own commits and a remote or forge repository of its own is another repository than its ancestors (a checked fact): a fold into one of them is refused; it folds only into a folder code proved is the same repository. A folder whose first candidate is git's and that has no independence item is folded by code (dead, the relation in its why).

**The ancestor graph.** The ancestors are found for every project folder at once, before any decision of a run, and again after each batch's records are written, so the same evidence gives the same answer whatever order the folders, facts or runs come in. The graph is over every project folder of the store and the catalogs: a folder with a record stands as its record says (its live folder, or none for a folder that is no project); one with no record yet stands in as a project folder of its own (it gets a record this run), with the ancestors its own evidence finds. In a path, a checkout's directory starts its own tree and any other known name the outermost one, outside a tool's hidden tree (`~/.claude/projects/...` names no project). One more kind of evidence relates a folder whose name is no repository by its check: **mentions**, one project folder holds at least three and at least half of the facts of other project folders that name it as a word (pieces with a slash, paths and URLs, left out), more than the folder's own live facts, and four times or more that folder's share of those folders' facts (a common word such as worktree is spread as the facts are; a name is not). Each folder's best ancestor with no record of its own is followed to the end of the chain (a part of b, b part of c: a's ancestor is c, shown "by way of b"); a cycle of best ancestors is broken by code, its member with the strongest identity of its own (a checkout on some machine, then a remote, then the most own commits, then the first name) keeping no ancestor in the cycle. A candidate's ancestors are its own, each resolved so, the folder itself and folders presumed part of it left out. The candidates whose first ancestor is one folder, with that folder when it is a candidate, are one group: the group sorts and is cut as one (a run's limit never splits it), the ancestor first and then by how many candidates stand between a folder and it, into one batch (up to twice the batch size).

**No evidence, no guess.** A project folder with no ancestor candidate, no candidate real repository, no independence item, no checkout on any machine and no session that worked in it or filed its notes has nothing that says what it is or whether it is worked. Its decision is `needs-review`: any other answer (a status of its own, kind `none`, a fold) stands only when it rests on the owner's quote or its why cites a `note:<name>` its evidence shows (`[[name]]`); otherwise code writes `needs-review` with the rule in its why (`assess.NoEvidenceOutcome`), and the folder is asked again with wider evidence like any folder left for review.

**Never out of the Mac.** Every writer of records refuses on a read-only clone; with the local layer the assessment, the migration, the overview step and the rotation write this machine's overlay instead (`local/curated/<folder>/_record.md`, `_overview.md`, its folder log, decisions and quote ledger) and never the clone. The store's records come in with the clone (sync in, never out), and this machine consolidates them with its own view: its assessment puts a store project record to the model once this machine has a checkout of the folder or work in it, and again on a material change of that work, and writes the answer into the overlay as the store's record with this machine's status, history and evidence and every other field the store's (`record.AsOverride`). It is checked like any decision, so an owner's status is only ever flagged `needs-review`. What this machine reads (the search index's records, the quiet flag, the hooks, the tree's session) takes that status over the store's for this folder and nothing else (`record.MergeLocal`): kind, name, aliases, suppression, tools and repos stay the store's.

## Checked claims

A dry claim has one source of truth code can read, so it is checked, never judged (client/internal/check). Code checks: a **repository's existence and current name** against every machine's catalog of checkouts (this one's and the store's `_repos.json`, names and other names repoid proves), the checkouts' remotes (normalized URLs) and the forge when one answers (GitHub through `gh api repos/<owner>/<name>` when gh is installed and logged in, `TACIT_FORGE=off` for none; it follows renames, and a 404 under every owner the catalogs' remotes and the gh account name is absence); a **path** in a checkout at HEAD (tracked as written, or as the end of a tracked path); a **version** (`v1.2.3`) against the checkout's tags and the version its manifest at HEAD declares (package.json, Cargo.toml, pyproject.toml, VERSION). A source that cannot answer gives `unknown`, which refutes nothing: no forge, no forge verdict. URL reachability is not checked (it depends on the network and the moment). The forge's answers are cached in the state directory (`forge-cache.json`): a found repository 7 days, a missing one a day, a failure never.

Every check is one result with its kind, the claim, the source, the inputs, the source's output, the verdict (`holds`, `fails`, `unknown`), the source's own value where it has one (the current owner/name, the manifest's version) and the time; a record's `evidence` keeps the checks of its name, and prompts show them as `check:` or `checked:` lines.

**Enforced.** A decision a check refutes is refused with the check's output, sent back once as every refusal is:

- **Assessment.** A project folder whose name exists nowhere (no checkout or other name of one on any machine, no remote, the forge has none; and no folder of that name on any machine) gets no status of its own under that name: it is suppressed into a real repository, or `needs-review`, or (when code finds no candidate) `none`. Code proposes the candidates, each existing by its check, with what names it: the forge's current name of a renamed one, the checkouts the sessions that filed its notes worked in, the repositories whose paths, remotes or `applies_to.repos` its facts name, near names; and shows the facts elsewhere that name the folder. The model picks among them. A name the forge says was renamed is an old name: it folds into the current one, never the current one into it. Nothing folds into a name that exists nowhere. Names code proves are one repository (another name of a checkout: a symlink's or the origin remote's; checkouts whose origins have one normalized URL) get one live folder: the others are suppressed into it or `needs-review`, which name it goes by being the model's decision from the evidence; they are batched together (a batch grows to keep them, up to twice its size), a decision that folds into a folder of its batch is checked after the others, and when one of them is refused a live decision for another waits with it.
- **The conflict judge.** Each pair shows both facts' checked references (forge repository URLs, backticked paths and versions in their repository's checkout). A `supersedes` that keeps the new fact whose checked references of a kind (repositories or paths) all fail over one whose references hold goes back to the judge once with the checks; a second one is a `CHECKED` line in `review/<date>.md` and retires nothing. A contradiction the checks settle says so on its review line. Versions never refute here: a planned version is no tag yet.
- **The rotation.** Each fact's checks are proof items (kind `check`); a `fix` whose new value is a dry value code can check (a forge repository, a path or a version of the fact's repository, a repository name replacing one) and that the check refutes is refused.
- **Dedupe and the absorber.** A copy whose checked references hold is never retired into, or absorbed by, a fact whose references the checks refute.
- **Statements.** A statement's dry claims (a canonical name, a repository that exists or not, a rename, a path, a version) are checked: one that holds makes it a decision, one that fails flags it (Statements). A canonical claim holds when the name is the main checkout's directory on the machines that have one and the other name another name of it, and fails when the main checkout's directory is the other name or the two are two repositories.
- **Orgs and forge names.** Whether an account is an organization (`gh api users/<name>`; only an owner some catalog's remote lives under, or the gh account, is asked) and a repository's current forge name (`gh api repos/<owner>/<name>`) are checks, cached as the repositories are (Orgs, Planned renames).

## Overviews

A live project, area or topic folder with a record and at least 3 live facts gets a cited overview, `_overview.md` (client/internal/overview), from the overview step of the full `tacit curate` (after assess and migrate): a few short paragraphs or bullets on what the folder holds and what matters most in it, written by the curator's model from the folder's live facts and, for a project, the live facts tied to it from elsewhere (`applies_to.repos`), at most 400, the owner's rules first, then standards, decisions and past mistakes, newest first, redacted. It is not a fact and no hook delivers it: `tacit_tree` and `tacit tree` print it under the folder's index at depth 0 only, so the 64 KB answer holds.

**What code checks.** Every paragraph and every bullet ends with at least one `[[fact-name]]` citation; every citation is a live fact of the folder or tied to it (not superseded, not retired); the body is at most 8 KB. A refused overview goes back to the model once with the problems, and a second refusal leaves the folder for the next run. Code writes the frontmatter: `folder`, `written`, `facts` and `basis` (the count and the sha256 of the sorted name and `updated` of the live facts it was written on), `rulings` (the sha256 of the owner's rules' names), `status` (the record's then) and `by`. Lint L19 checks the file's form.

**When it is written again.** Only on a material change, which code reads against the frontmatter: the share of the folder's facts added, replaced or retired since `written` (by their dates, over the larger of the counts then and now) reaches 20% (`TACIT_OVERVIEW_CHANGE_PCT`; not measured on a replay yet), or the record's status changed, or a rule of the owner's was added or removed, or a cited fact is no longer live. At most 10 a run (`TACIT_OVERVIEW_MAX`), an overview lint L19 holds red (it cites a fact the store no longer has, such as a removed derived fact) first, then a forced change, then a folder with none, then the largest share; one commit each, `curator: overview: <folder> (<n> facts, <why>)`. **When it is removed.** An overview is generated, like the folder index, so one that is no longer due is removed, not kept red: its folder has no live facts, fewer than 3, or no live record (none, or redirected). The step removes these first, with no model call, at most 50 a run in one commit, `curator: overview: removed <n> stale overview(s): <folder> (<why>), ...`, after checking each again on the fresh clone under the lock. An overview lint holds red whose rewrite code refused twice is removed too, in its own commit, and the folder gets a new one on a later run. The curator's locked write removes only a folder's `_overview.md` or `_index.md` under a scope root and refuses any other removal (a fact, a record) before it writes anything; git history keeps every removed overview. Nothing is written before the store format marker; with the local layer it writes overviews of this machine's own folders into the overlay.

## Supersede, never delete

A fact that turns out wrong or outdated gets a newer fact and `superseded_by` pointing at it. The old file stays. Retrieval excludes superseded facts by default; history queries include them.

A fact that git shows is outdated, with no newer fact to point at, gets `retired: <date>` (set by a staleness verdict, see Staleness check). Retired facts are treated like superseded ones everywhere: not indexed, not delivered, not searched by default, not counted as a live scope.

A fact that still holds while one detail of it changed keeps its words and gets an **in-place note**, one line appended to its body, and `updated` (`fact.AppendNote`):

```
> superseded 2026-10-21: v0.7.17 -> v0.7.19
```

Code checks that the file as it was is a byte prefix of the new one, that the frontmatter reads the same, and the line's form (lint L18). The stale verifier's `fix` and the rotation's `fix` write one when the fact holds the replaced detail word for word; an agent never writes one into a ruling (the owner is asked instead). Several facts that say one thing may be **compressed**: one new fact, written by the curator's model, cites each of them as `[[name]]` and lives in their folder, and every old one gets `superseded_by` the new one; code checks the citations and the folder, and a ruling or a fact with the owner's words is never compressed. Only facts of the layer being written are compressed with it: on this machine's layer an agent's note or a store fact the model names is left alone, and a fact gone since it was read (deduped, superseded) is nothing to change. Stale (`retired`), compress and redirect (`superseded_by`, a record's `suppressed_by`) are the only ways a fact leaves delivery.

One exception: generated `derived/<repo>/` facts are removed, not superseded, when their repo leaves (see Derived facts). They hold no judgment, only a function of a checkout, and git history keeps the files.

## Curator runs

`tacit curate` (the full run, in the curator's daily unit before `tacit verify`) splits the pending inbox notes in batches, checks the rulings among them against the owner's words (Rulings), judges each new fact against its closest curated facts (Contradictions), writes the index and pushes each batch (a batch the server refuses ends the batches, and the run prints the server's lines: `curate: the batch was refused: tacit: <path> looks like it contains a secret; files set aside: [...]`; a local store's check names the file the same way), and then runs the assessment, migrate and overview steps (Folder records, Overviews; from the store format marker on) and the derive, results, disowned, links and staleness steps, building the search index at its HEAD for the hooks before the staleness step. `tacit maintain`, the daily unit, runs `tacit curate`, then the rotation (Rotation), then `tacit verify`. `tacit curate --quick [--min-interval D]` (the idle job's second step, every 10 minutes after the idle dream) runs only the batches: the notes a commit added to the clone in the last 24 hours, newest first (a note not committed yet has not reached the server), at most 2 batches (about 170 dreamer notes) started within 20 minutes unless `--max-batches` or `--budget` says otherwise, through the same split, rulings evidence check, conflict judge and its splits of an invalid answer, `MEMORY.md`, lint, commit and push, and the search index built at the new HEAD for the hooks. It runs no derive, results, disowned, links or staleness step and nothing of the verifier, and older pending notes are the full run's. Its report line in `curator.log` has `quick: true`. A quick run counts no failure strike against a note that fails alone (`curator.json` `failed`, `maxNoteFailures`): only the full run does, since a quick run every 10 minutes would set a note aside within the hour. Owner notes it leaves pending because this machine has no owner history are no failure of a quick run (exit 0); the full run still exits 1 for them. On a read-only clone or a machine that cannot write as curator (Writer keys) a quick run exits 0 with no line, since the idle job runs it every 10 minutes on every machine that dreams; a full run refuses (exit 2). A read-only clone with the local layer on curates its overlay instead (Local layer).

**One curate at a time.** A real run holds `curator.lock` in the state directory (an OS file lock) from before its sync to its exit. A quick run that finds it held prints `curate: busy` and exits 0 having done nothing; a full run waits for the holder (it says so once), up to an hour (a quick run ends within its 20-minute budget and 10-minute tail), and its own deadline (`--budget` plus 75 minutes) starts once it holds the lock. A quick run then reads `curate-quick.json` (`last_run`): one within `--min-interval` (default 30 minutes) of the last quick run exits 0 doing nothing, without a sync. Otherwise it records its start there before it syncs, so a run that fails also waits out the interval and a failing model is not asked every 10 minutes. `--dry-run` takes no lock, reads no interval and records none. `--env-file F` loads the runner's variables before any model call, for launchd and Task Scheduler, which have no `EnvironmentFile`; an explicit `--model` still wins.

**Failed runs back off.** A run that paid for model calls and completed no batch, for a failure that is not one note's own (a provider, authentication, quota or runner error on the split, rulings or judge route; an invalid answer it could not split further; the conflict index), is a failed run; so is a run that stopped paying because its route failed (below). A lone note's invalid or refused answer is the note's (its strikes count it), and a run with nothing pending changes nothing. After a failed run the next run that may pay waits 30 minutes, then 1, 2 and 4 hours, at most 4 hours (the quick interval doubling to the full dream's cadence), and first sends a probe on the failing route (`tacit curate` sends a one-line "reply OK" prompt through the route and its fallback; $0.002 on Opus 5.5 via Bedrock): a failed probe is a failed run and the wait doubles; a passed one lets the run go on. A quick run before the next try pays for nothing (`curate: backing off ...`, exit 0); the daily run does not wait for it but still probes, and runs its steps after the batches either way. Inside a run, a batch whose split, rulings pass or judge failed on its route is followed by a probe before the next batch pays; a failed probe, or a third such batch, ends the batches, and the rest wait for the next run. A completed batch ends the backoff. The state is `curate-backoff.json` in the state directory (`curate-local-backoff.json` for the local layer): failures in a row, the first and last, the next try, the reason, the route the probe calls, skipped runs and probes with their cost; `tacit doctor` shows it, and the report line has `probes` and `backed_off`. Measured on the rig's `curator.log` of 2026-10-21 to 28 (eval/VALUE.md, "Failed runs"): 57 runs wrote nothing for a failure and cost $122.40 of $336.88, most of them the quick run paying the split again every 30 minutes for 27 hours while the judge route was down; under this schedule $3.31 is paid in their first batches and 21 probes, and 42 runs are skipped.

**A failed run's paid answers are kept.** A batch whose rulings pass or conflict judge failed was split again, and paid for again, by every later run. The split's entries, per note, and the rulings pass's once it answered, are kept in `curate-splits.json` (`curate-local-splits.json`): the next run takes a batch whose every note has its answer, unchanged since (the note's scope, kind, description, body and owner words), as its own batch and first, checks the entries again (an entry the checks refuse now sends the batch to the split), and pays only for the step that failed (`splits_reused` in the report). A note's answers go when its batch completes, when the note changes, after 14 days, and all of them when the split or rulings prompt changes. A dry run neither reads nor writes them.

## Contradictions

The curator checks every new fact against its closest existing curated fact and against same-scope facts of the same run in one batched judge call. A `supersedes` verdict is applied automatically only when the two facts come from the same inbox note or share most of their terms, and never against a ruling; every other verdict, and every `contradicts`, is a line in `review/<date>.md`. The owner answers with `tacit resolve`, which sets `superseded_by` or `conflicts_with` (frontmatter, lint L13, indexed; retrieval never delivers both sides of a `conflicts_with` pair). A second judge pass per batch lists owner rulings in the notes that the split did not produce as `kind: user` entries and adds them. Every `kind: user` entry of either pass goes through the ruling check (Rulings, The curator) before it is written. Nothing is deleted or silently merged; an entry that only restates a curated fact is not written at all (Near-duplicates). A batch whose conflict check cannot run (the index cannot be opened, or a query fails again after the index is opened anew) is not written: its notes stay pending and the run stops with a non-zero exit. The judge is asked about at most 25 pairs per call. An invalid answer (the wrong number of verdicts, an unknown label) splits the chunk in two and asks again; a pair that gets no valid verdict alone is written unchecked with a `CONTRADICTION?` line in `review/<date>.md` that says so (the owner decides it like a contradiction), and the run exits non-zero. A judge that gives no valid verdict for any pair of a chunk it split fails the check as above, and a model or transport error stops it. `tacit curate --recheck-conflicts --since D [--until D]` runs the check again, alone, for the curated facts the split made in those days, each against its closest curated fact that is not newer than it, with the same verdict routes.

## Near-duplicates

The curator writes one copy of a fact. No model decides it: a fact restates another when both are in the same scope, the two descriptions share at least 0.6 of their search terms (Jaccard, `curate.RestateOverlap`), its own description and body hold no number, path, dotted name or `code span` (a command an agent marked as code, compared whole) the other's text does not cover, no name joined with `@` or `_` (a plugin id, a profile) the other lacks, the two descriptions hold the same words of change or negation (not, no longer, now, moved, removed, instead), and it holds no owner quote or owner words unless the other holds the same phrase exactly. A path covers its spelling with the home directory written out (`/Users/<name>/` is `~/`) and with a trailing slash, and a path or dotted name without a digit is covered by a longer one that holds it at a separator (`/v1/rgstr` in `https://host/v1/rgstr`); a token with a digit is covered only whole, so port 778 is not 7781. Only the closest fact in the scope decides.

**At the split.** Pending notes that only restate a curated fact or an earlier note are set aside before the split (`curate.Restated`; the note's body must be its description). After the split, each entry is checked against the live curated facts and the entries of its batch already kept (`curate.Absorber`). An entry that restates one is not written, gets no conflict check and no ledger line, and the report counts it (`absorbed`). A note whose every entry was absorbed is recorded in `curator.json` under `restated` (note -> the fact), as a note set aside before the split is. A ruling is absorbed only by a ruling with the same quote. An observation that restates a ruling is absorbed by it; a ruling that restates an observation is written. Facts the run superseded absorb nothing after their batch.

The absorber has two rules. The description rule is `restatesFact`'s (above). The content rule (`curate/content.go`) catches the paraphrase whose description shares too few terms: an entry is absorbed when every claim it makes, each sentence of its description and body with three terms or more (a code span is never cut, home directories read as `~`), is in a curated fact it can see: 80 percent of the claim's terms (`curate.ContentCover`), every specific token and every name with `@` or `_` of the claim in that fact, and the same words of change or negation as that fact's sentences that hold half the claim's terms or more (never and not read as one). Each claim may be covered by another fact; the entry's specific tokens must be in its covers as a whole, and code's checks must not refute a cover where the entry's references hold. Visible covers: the entry's scope, `user`, `system`, and the scope of the note it came from (the session's repository). Never absorbed by content: a ruling, an entry with the owner's words, and any entry of a note in their words (kind user or statement, owner evidence or words, written by the owner, a quoted span of six words or more) or of a reviewer's trim. Never a cover: a folder file (`_overview.md`, `_record.md`, `_index.md`), a result or hot spot, a fact over 1,200 characters. Specific tokens (both rules, and `Restated`) include whole paths with their placeholders and globs (`/run/user/1000/<id>/apps/*.stderr.log`), so a path that differs only past a `<...>` or `*` is new. Every absorption is in the run's report: `absorbed_by` lists the note, the entry's description, the fact that covers it (name and path), the rule and, for content, the least share of a claim covered. Measured in eval/VALUE.md ("The absorber's content rule"): on the 5,340 facts the rig's curator wrote 2026-10-21 to 28, against the live facts each curation saw, the content rule absorbs 40 at 0.8, every one a copy by a hand label per fact (22 before the rebuild switch, the tuning set; 18 after, held out).

**The store.** `tacit dedupe [--dry-run] [--json FILE]` finds the curated facts that already restate another and retires each with `superseded_by` the fact kept, which says everything it says. Facts are taken best first: a ruling, then a fact with owner evidence or words, then the one whose `applies_to` names the most entries, then the newest (`updated`, else `created`), then by name. Each is checked against the facts kept so far, so a kept fact is never a copy and no chain forms; every replaced fact whose successor is itself replaced (a copy retired now, a fact a migration moved, an earlier supersede) is pointed at the live end of its chain, so a chain ends at the live fact in one step (a run with no copies still does this). Never a copy: a ruling, a fact with owner evidence or words of theirs, a `system` fact, a fact with `conflicts_with`, a generated `derived/` fact, a fact a standing decision of the owner keeps, and a fact whose pair with the fact it restates the owner already answered. Only `superseded_by` and `updated` change (`fact.PatchRelations`); the write is the curator's locked write (`curatorWrite`: lock, sync, plan on the fresh clone, lint gate, one named commit `curator: dedupe: ...` listing each copy and the fact kept, files put back on any failure). The dry run reads the clone as it is and never syncs. A second run finds nothing. The command writes no review lines: the rule is mechanical, and a review page with one open item per copy would bury the real findings; `tacit resolve clear <copy>` undoes one. It is not a step of `tacit curate`, which absorbs new copies at the split. Numbers in `eval/VALUE.md` (Near-duplicates).

## Dreamer sources

`tacit dream` reads what is new since its last run in these sources (`dream.DefaultSources`, the top-level sources of the one list, `harnesses.Sources`; Session events):

- Claude Code transcripts, `~/.claude/projects/*/*.jsonl` (top-level sessions only).
- Codex sessions, `~/.codex/sessions/*/*/*/*.jsonl` and `~/.codex/sessions/*/*.jsonl`, and the ones Codex archived, `~/.codex/archived_sessions/*.jsonl`.
- pi sessions, `~/.pi/agent/sessions/*/*.jsonl`, or the sessions directory of `$PI_CODING_AGENT_DIR`, or `$PI_CODING_AGENT_SESSION_DIR/*.jsonl` (pi's own variables, read as pi reads them). A subagent's session is one level down (`<session>/tasks/`, with `parentSession` in its header), where the glob does not reach; a session that names its `parentSession` is an agent's anyway (Who typed a turn).
- Hermes, the SQLite store `~/.hermes/state.db` when it exists (`hermes_db` or `TACIT_HERMES_DB` names another; `off` reads none).

**Compressed transcripts.** Codex rolls an old session into a compressed copy, `rollout-<time>-<id>.jsonl.zst`, and removes the `.jsonl` (on the rig, 2026-10-27: 2,935 such files, 7.7 GB, 36.5 GB of JSONL, every one in a single zstd frame that records its size; 155 on the Mac). Each glob above takes the compressed copies of its transcripts too (`transcript.Glob`): one path per session, the plain file when both are there. A transcript is named by its plain path whichever file holds it, and its offsets are positions in its JSONL bytes, the decompressed stream of a compressed copy; a path recorded while the session was plain reads its compressed copy once the plain file is gone (`transcript.Resolve`). A compressed copy is read as a stream (pure-Go zstd, a window of at most 128 MiB, one decoder at a time), never held whole; reading from an offset decompresses and passes over what comes before it. Its size is read from its frame headers. The dreamer, the owner's turns, the reviewer and `Locate` read them. No harness writes a gzip copy (none on the rig or the Mac), so none is read.

A transcript's cursor is a byte offset in `dreamer.json` `offsets`, keyed by its plain path, so it holds when the harness compresses the file. When a session's file moves (Codex moves an archived session from `sessions/` to `archived_sessions/`, and back), its one cursor of the same format and session id whose file is gone moves to the new path, with its done windows and failure time; a cursor whose file still exists is another copy of the session (an import, a fork) and keeps its own. A compressed copy's size is kept in `dreamer.json` `packed` by its file's size and time, so the 10-minute idle run does not read thousands of frames again. Compressed copies are a root of their own (`<glob>.zst` in `sources`): a dreamer from before v0.9.11 records the copies it has no cursor for at their end, as for any new source, so months of Codex history are not replayed on upgrade; a compressed session new after that is read from its start. A Hermes session's cursor is the id of its last message read, under `hermes:<store path>#<session id>`; a cursor past the session's last id (the store was restored from a backup) restarts at its current end, as a truncated transcript's does. A fresh state records every cursor at the current end and dreams nothing; so does a source the state has no cursor for yet (listed in `dreamer.json` `sources` once recorded), so a source added to a running dreamer is not replayed. A window is at most 60,000 characters of digest; a source reads at most 4 MiB per transcript or session per run, and a seen one waits for 4,000 bytes of new content.

**When a transcript is dreamed.** Four triggers read the same cursors, and every run reads a transcript from its saved cursor, never from its start (a transcript with no cursor in a source the state holds is a session begun since the last run, read from its start). In the order they usually come:

1. A full window (the prompt hook, Delivery): the transcript's undreamed part has reached about one dream window, and the hook starts `tacit dream --session T`. Dreaming does not wait for a compaction.
2. Before a compaction (the PreCompact hook, Delivery): the same `tacit dream --session T`, so what the compaction is about to drop reaches the store for other and later sessions. Nothing is given back to the same session: the compaction's summary carries its content.
3. Idle (the idle job every 10 minutes, `tacit dream --idle D`; `--idle` alone is 20 minutes, the job passes `20m`): of the transcripts with new content past the 4,000 bytes, those that went quiet, no write for D (the file's mtime; a Hermes session's newest message), which catches a session ended by Ctrl-C or a crash, or whose new content holds a compaction, which it takes at once: Claude Code's summary turn (`isCompactSummary: true`) or the system entry before it (`subtype: compact_boundary`), Codex's `type: compacted` entry, pi's `type: compaction` entry, each read on the entry itself and never in text inside one (`digest.Compacted`); a Hermes session compacts by ending (`end_reason` `compression` or `session_reset`) and going on in a child, so a session that ended so is taken at once (`hermes.Continued`). A transcript still being written waits, its cursor unmoved.
4. The 4-hour timer (`tacit dream`), the backstop: every transcript with new content past the 4,000 bytes.

A session run (`--session T`) takes one transcript (its path) or Hermes session (its id) and moves no other cursor; a source with no cursors yet is not read, and on a machine with no cursors at all it records none and exits 0, since one recorded cursor would make every other transcript look new to the next run. A selecting run (`--idle`, `--session`) that finds nothing to take saves the cursors it moved past deltas with nothing to extract and exits 0 without a sync, a note recovery or a `dreamer.log` line; one that takes something recovers pending notes first, as the timer's run always does, and its meter line carries `mode` (`idle` or `session`). Without `--idle` and `--session` a run is as before.

**Failed windows wait.** When a window of a transcript fails (the model's answer, redaction or the push), its cursor stays and `dreamer.json` `failed_at` records the time under the transcript's cursor key. Idle and session runs pass over that transcript for 4 hours (`dream.FailureBackoff`, the full run's cadence; the run says how many it passed over), so a window the model cannot answer is sent at most once per 4 hours by them, not every 10 minutes or at every prompt; the 4-hour run retries it as before, and a cursor that moves clears the record. On a read-only clone or a machine without the dreamer's key (Writer keys) idle and session runs exit 0 with no line, before any sync or cursor read; the full run refuses (exit 2). A read-only clone with the local layer on dreams into its overlay instead (Local layer).

**Failed runs back off.** A dream run that sent windows and completed none because the route failed (a provider, authentication, quota or runner error, not an answer that does not parse, which the transcript's own wait covers) or because redaction failed is a failed run, and the dreamer backs off on the curator's schedule (The curator, "Failed runs back off"; `dream-backoff.json`): an idle or session run before the next try sends nothing and writes no `dreamer.log` line; the 4-hour run does not wait but first probes the dream route, and a failed probe is a `dreamer.log` line with `backed_off`; inside a run, a window that failed on its route is followed by a probe before the next window is sent, and the run stops (`pause_reason: route`) when it fails or after the third such window. Cursors of windows not sent stay. A completed window ends the backoff; `tacit doctor` shows the state.

**One dream at a time.** A real run holds an exclusive lock on `dreamer.lock` in the state directory (an OS file lock, released when the process ends however it ends) from before it reads the cursor file to its exit. An idle or session run that finds the lock held prints `dream: busy` and exits 0 before any sync, model call, cursor read or write: the state is the first run's. The 4-hour run waits for the holder (it says so once) up to 45 minutes, then exits 0 the same way. `--dry-run` takes no lock and writes no state.

The digest is one dialect for every source: `U:` the owner's words, `P:` a prompt another agent or a program wrote (Who typed a turn, below), `H:` text a harness or a program put in a user turn (Claude Code's compaction summary, a user turn marked `isCompactSummary`, among them), `A:` agent text, `T:` a tool call, `E:` a tool error. An agent's session is dreamed like the owner's (a window needs a `U:`, `P:` or `E:` line and agent text): what its agent found out is an agent's note all the same. A window's lines are redacted before any model sees them (`digest.Finish`): masked as one text and line by line, a byte masked when either masks it, so a hit that starts on one line cannot keep the next line's secret, and a keyword at the end of one line still masks the token that starts the next. The prompt (v7) says a `P:` line is never the owner's words, and code checks what the model returns: a ruling or statement from a window with no `U:` line, or whose quote is in a `P:`, `H:` or `A:` line and in no `U:` line, is filed as an observation, its words kept as another agent's (`Another agent's prompt in the session said: "..."`; `dream.CheckOwnerWords`). Any other quote is left to the curator's check against all of their turns.

**Who typed a turn.** One function decides it for the dreamer and for the owner's turns (Rulings): `digest.SessionWho` per session, from the transcript's path and first 256 KiB, and `digest.ClaudeTyped` per Claude Code turn (`digest.ClaudeQueued` for a message typed while the agent worked). A turn is the owner's only when what its format records proves a person typed it.

**What in a turn is theirs.** A turn a person typed can still hold text they did not write, so its text is split by who wrote each part, by one function for the dreamer's digest, the owner corpus and the reviewer (`digest.TurnPieces`), for Claude Code, Codex and pi alike (a Codex session Relay moved from Claude Code holds Claude Code's frames and notices as user messages):

- every whole `<system-reminder>` block is the harness's: Claude Code puts one in front of a message the person typed (a background task they started, the scratch folder of a desktop session with no project folder), and their words after it are theirs (v0.9.9 dropped such a turn whole: on the rig 4 turns, one of them "no more memra work for now");
- every whole paste the desktop app framed (`<pasted_content ...>...</pasted_content>`, `digest.PastedContent`) is pasted text, an agent's (`P:` in the digest, a `NOTE` for the reviewer), and what they typed around it is decided on its own: what a person pastes is often an agent's output they pass along. The corpus cut such a paste out before; the digest kept it as their words (on the rig, 2026-10-30: 22 typed Claude Code turns in 13 sessions hold one);
- a note a side agent offers: Claude Code delivers it as a typed turn of the person's (`origin.kind: human`, `promptSource: typed`, `turnOrigin: human`), "Here is a note offered by a side agent:" and the note's body quoted line by line with `> ` (a copy pasted from the terminal opens with its `❯ ` and keeps the quote's indent); the header and the quoted lines are that agent's (`P:` in the digest, not in the corpus), and what the person typed below the quote is theirs (in the rig's rebuild selection 180 such turns in 18 owner sessions, 21 of them with a reply below the note, and 223 copies in Claude Code's prompt history);
- a slash command's echo is the harness's, its `<command-args>` the person's (`U:` in the digest too), unless Claude Code ran the command itself: a local command (`/model`, `/effort`, `/plugin`, the desktop app's `/auto-mode-setup` wizard) is a `<local-command-caveat>` meta line, the echo and its `<local-command-stdout>`, all of one prompt (`promptId`), and its arguments are input to Claude Code, not words to the agent, some filled in by the app (`--expect-sha256 <hash> --apply-file <path>`); its echo is the harness's whole (`digest.ClaudeCommands`, which the digest, the corpus and the reviewer follow line by line). A command whose text goes to the agent has no caveat: `/goal`'s condition and a skill's arguments are the person's when they typed the turn, and the skill's own text that Claude Code fills them into ("ARGUMENTS: ...") is a meta line, the harness's. On the rig's Claude Code transcripts (2026-10-27): 27 echoes with arguments, 14 local commands, 13 not (`/goal` 10, a skill typed in the desktop app, a skill run twice by `claude -p`);
- a Codex question reply (`<send_user_message_question_reply>`, a JSON list) holds the person's answers in its `answer` fields; an answer that is one of the options the agent's `request_user_input` call offered for that question is the person's choice among the model's words, not words of theirs (as an accepted suggestion; `H: the person chose the option offered: ...`); the questions are the agent's;
- any other text that opens with a tag, a harness heading (Claude Code's, Codex's), a compaction summary, a front end's status prompt, an interruption mark, an automation (a wake loop's prompt, which a program types into a person's Codex session, opens with `Wake nonce=`: 310 in 30 days of the owner's turns, 2026-10-30), or a Relay hand-off ("The user moved this existing Relay conversation to you") is the harness's, `H:`; an orchestrator's role prompt ("You are ...") is an agent's;
- the rest is theirs.

In a turn that is not a person's the digest keeps its old rule: harness text `H:`, the rest `P:`, whole. An interruption mark is harness text in every session (`digest.HarnessText`): Claude Code writes `[Request interrupted by user]` into the transcript the person interrupted, a subagent's too, and a Codex rollout that holds a Claude Code conversation keeps it.

**Mid-turn messages.** What the owner types while the agent is working is a turn of theirs like any other, in the place it was delivered. Claude Code does not record it as a user line: it is an attachment line, `{"type":"attachment","attachment":{"type":"queued_command","prompt":...,"commandMode":"prompt","origin":{"kind":"human"},"humanTurn":true}}`, after the tool result it waited for (`humanTurn` since 2.1.296; `origin` since 2.1.19x; older versions record only `commandMode: prompt`, and the line's `entrypoint` decides as it does for a user line). Not a person's: a sidechain's, a meta attachment, a `commandMode` other than `prompt` (a task notification) and an `origin.kind` other than `human` (`task-notification`, `peer`, `coordinator`). Codex records a message steered into a running turn as an ordinary user message of the turn (`response_item`, role `user`), pi a steering or follow-up message as an ordinary `user` message, and Hermes a `/steer` as a user row of `display_kind: steer` with its words in the out-of-band frame (below), so those are read as every other turn of theirs. Measured 2026-10-24 (counts only): 448 messages typed mid-turn in 51 of the rig's 5,634 Claude Code sessions and 289 in 16 of the Mac's 47; the dreamer read none of them before, and 220 of the 551 dream windows of those rig sessions change (16 of them had no owner line at all). The owner corpus already held most of them through the prompt history (`~/.claude/history.jsonl`): 67 of the rig's 428 and 12 of the Mac's 282 were in no turn of theirs. Codex (50 steered messages on the rig), pi (25) and Hermes (87 steers) were read already.

- All formats: a session whose working directory only agents use is an agent's (`/tmp` itself and below it, the macOS temporary directories, `/.claude/jobs/`, `/.cache/`, a scratchpad, an e2e driver, a runner's `/.local/runners/` checkout; a directory inside the home directory is never taken for a temporary one by its prefix).
- Claude Code: a subagent's transcript (`<session>/subagents/`) is an agent's, and so is a session whose lines in the head name no person's `entrypoint` (`cli`, `claude-desktop`): `claude -p` is `sdk-cli`, an Agent SDK lane `sdk-ts`. In every other session each user line is decided on its own marks. Not a person's: a meta line, a compaction summary, a transcript-only line, a sidechain (a subagent's turn inside the session), a scheduled task's prompt (`scheduledTaskId`), and an accepted suggestion (`promptSource: suggestion_accepted`: the model wrote the words). Then the first mark the line has decides: `origin.kind` (`human` is a person; `task-notification`, `peer`, `plugin` and the rest are not), else `turnOrigin` (`human`; not `task_notification`, `scheduled`, `peer`, `sdk`, `system`), else `promptSource` (`typed`, `queued`; not `system`, `sdk`), else, from a version that marks none, the line's own `entrypoint`. The desktop app sends a person's turn through its SDK (`promptSource: sdk`) with `origin.kind: human`. A session resumed by `claude -p` holds both: the person's lines stay theirs, the lane's are `P:`. A message typed mid-turn is decided the same way (Mid-turn messages, above).
- Codex: `session_meta` decides. A subagent spawned by a parent thread reports the person's front end (`originator: codex-tui`) with `source: {"subagent": ...}`, `thread_source: subagent` and `parent_thread_id`; any of the three makes it an agent's, and so do `source: exec` (`codex exec`), a `thread_source` other than `user` (a guardian review) and an `originator` that is not a person's front end (`Codex Desktop`, `codex-tui`, `codex_cli_rs`, `codex_vscode`). A session with no `session_meta` first line is unknown, and not the owner's.
- pi: a subagent's session (a file directly in a `<session>/tasks/` folder, under pi's sessions directory or `$PI_CODING_AGENT_SESSION_DIR`, `digest.PiTask`; or one naming its `parentSession`) and a headless one (below) are an agent's.
- Hermes: the session row decides (below).

**Owner windows and agent windows.** Owner content or agent content is decided per window, not per session. A session of the owner's can run on its own for weeks while they step in now and then, and in Hermes they write almost every other message. A window with at least one turn of theirs (a `U:` line, as Who typed a turn decides it, mid-turn messages included) is an owner window. A window with none is an agent window, also inside an owner's session. `dream_agent_windows` (`TACIT_DREAM_AGENT_WINDOWS`, `tacit dream --agent-windows`, the flag first) decides what the dreamer does with an agent window: `all` (the default, as before the option) dreams it; `recent:<days>` dreams it when its newest line is at most that many days old (by the entries' `timestamp`, a Hermes row's time; a window with no time is taken); `none` never dreams it. A window not dreamed is passed over: when every window of a delta is passed over, the cursor moves to the delta's end, as for a delta with nothing to extract; otherwise it moves when the dreamed windows of the delta are done, past the passed-over ones too. An owner window whose agent content the policy would not take (always with `none`; with `recent` when the window is older) is cut to the owner's turns, each with the 12 digest lines before and after it, and a line `H: [tacit: N line(s) of the agent's own work left out]` for each gap; the window keeps its identity (its completed key is its whole content). The run's meter line and summary count the windows passed over and the owner windows cut, with the characters each left out. Measured 2026-10-24 on the rig's rebuild selection (158 owner transcripts, 158 Hermes sessions of owner sources, of which 94 are owner sessions by `hermes.Session.Owner` and the only ones dreamed; 912 windows, 4,359 owner turns): 708 windows hold an owner turn and 204 do not; 12 lines reach the agent's text before the turn for 93% of the turns (every turn whose window holds one), its first text after for 91% and its second for 73%, and keep 38% of the owner windows' characters (8 lines: 31%, 16: 44%).

**Facts already held (off by default).** With `dream_held_chars` on (`TACIT_DREAM_HELD_CHARS`: `on` is 4,000 characters, or a size; unset or `off`, no list), a window's prompt lists, before its digest, the curated facts already held for it, and tells the dreamer not to write one again unless the window adds to it or contradicts it (prompt v9; with no list the prompt is v8's, byte for byte). Code picks them (`dream.Held`): live curated facts an agent observed (never a ruling, a statement or a fact with the owner's words, which the dreamer writes whenever they are said again, repetition being their evidence; no folder file, result or generated fact) in the scopes delivery would show in the session, the window's repository (by scope, or `applies_to.repos`), the machine, the user and the system; of these, the ones whose terms, each weighted by its rarity in the pool, the window holds at least half of, most first, as many descriptions as fit the size. The run's `dreamer.log` line counts them (`held`, `held_chars`). Measured on 14 windows of the rig's sessions (eval/VALUE.md, "Facts already held"), each with the store as it was before the window's first line: 131 notes without the list and 120 with it, copies of held facts 20 and 14 by a blind judge, the owner's words the same, for 13 percent more input and 11 percent more dreamer cost; the difference is within what two runs of the same prompt differ by, so the list is off until a larger replay shows it pays.

**pi.** pi records no mode: `pi -p`, an RPC or SDK driver and an interactive session write the same file. A session whose first user turn came less than 1 s after pi's last startup entry (the header, `model_change`, `thinking_level_change`, `session_info`) is a program's, and its user turns are `P:` lines. Measured 2026-10-20 on 131 sessions: 84 headless first turns came at most 0.18 s after, 47 typed ones 1.3 s and more. `pi "prompt"` on the command line looks headless; the error is on the safe side. Blocks: `text`, `toolCall` (a `T:`), `thinking` (dropped); `toolResult` with `isError`, a provider's `errorMessage` and a `!command` with a nonzero exit code are `E:`; `custom`, `custom_message` and summaries of compacted branches are `H:`. A user turn that opens with a tag (an attached file) is `H:`.

**Hermes.** The store belongs to a running gateway: it is opened with `mode=ro`, `query_only` and a 2-second busy timeout, and never written. Only the owner's sessions are read: source `mobile`, `telegram`, `desktop`, `cli`, `tui` or `webui`; `created_source` empty or one of those (a `cli` session only with `created_source` `cli`: earlier ones are scripted `hermes chat -q` runs); no delegation mark (`$._delegate_from` in the `model_config` JSON, which Hermes sets on every delegation, with or without a parent; a `model_config` that is not JSON has none); not one of several sessions of those sources started within 2 s of each other (a delegation's fan-out); and, with a parent, only the continuation of an owner session whose parent ended by `compression` or `session_reset`. Every other source is automation and never read: `cron`, `oneshot` (tacit's own Hermes runner), `subagent`, `grok-cli`, `kanban`, `llm-wiki-lint`. A row that repeats an earlier row of its session (same role, timestamp and content) is a compaction copy and is passed over. The repo is the session's `git_repo_root` or `cwd` when recorded, else the window's paths (Scopes). A tool row is `E:` when its JSON has a non-empty `error`, a nonzero `exit_code`, `success: false` or `ok: false`, or its text opens with "Error". A user row is cut to the owner's words (`digest.HermesOwnerText`):

- Dropped whole: a compaction summary (`_compressed_summary`); `display_kind` `internal_notification`, `async_delegation_complete`, `model_switch` or `process_complete`; a row opening with `[CONTEXT COMPACTION`, `[ASYNC DELEGATION`, `[IMPORTANT:`, `[STILL IN PROGRESS`, `[INTERNAL NOTIFICATION`, `[Cron delivery:`, `[Your active task list`, `[SKILL PRUNED`, "You've reached the maximum number of tool-calling iterations", "Session turn lease could not be refreshed", a kanban result (`✔ [`, `✖ [`) or the file-mutation verifier's warning; any row holding `[INTERNAL NOTIFICATION — generated by the Hermes gateway`.
- Attached context cut: from a line `--- Attached Context ---` to the end of the row (the file or page Hermes appends for an `@file:` or `@url:` reference), and a desktop paste's reference (`@file:…composer-pastes/…`), so a paste alone leaves nothing of theirs.
- Wrapper cut, the rest theirs: `[OUT-OF-BAND USER MESSAGE …]` (`display_kind` `steer`) and a "Gateway message origin" block, up to "Do not guess a reply destination…"; `[Replying to: "<agent's message>"]`, up to its last `"]`.
- A voice message, `[The user sent a voice message~ Here's what they said: "…"]`: the quoted transcript is theirs.
- Notes cut: `[Note: …]` (a model switch), `[System note: …]`, `[System: …]`, `[Workspace::…]` and other `[The user sent a …]` attachment notes.
- What still opens with `[` once the frames are cut is an unknown notice, or a pasted chat log, and is not theirs (fail closed).

## Session events

`client/pkg/evidence` is tacit's exported reader of agent session history, for other Go programs on the machine: one stream of structured events per session, read by the rules the dreamer, the owner corpus and the reviewer decide with. It is a facade of aliases and wrappers over `client/internal/events`, `internal/harnesses` and the packages below; every rule stays in its package, so a reader of the facade and tacit decide the same way. It imports neither the dreamer nor the store packages (a test lists what it compiles; `internal/ledger` comes in only for the turn hash the corpus names a turn by).

**Sources.** `harnesses.Sources(home)` is the one list of where sessions are, in this order: Claude Code's top-level transcripts (`~/.claude/projects/*/*.jsonl`) and its subagents' (`~/.claude/projects/*/*/subagents/*.jsonl`); Codex's three globs (Dreamer sources); pi's sessions (`digest.PiSessionGlob`) and their tasks (`<session>/tasks/*.jsonl`, in the folder named after the session's file); the Hermes store (`hermes.DefaultDB`). Each names its harness and whether it holds subagents' transcripts. The dreamer, the corpus and the reviewer read its top-level sources (`harnesses.TopLevel`): the same globs as before the list, in the same order. `Files(source)` lists a source's transcripts by their plain paths (`transcript.Plain`), one per session whichever file holds it, so a session Codex compresses between two reads keeps its path; `ReadFile` reads the compressed copy.

**Events.** `ReadFile(path, format, from, emit)` reads a Claude Code, Codex or pi transcript, plain or compressed, from a byte offset and calls `emit` for each event in order; `ReadHermes(ctx, db, session, after, emit)` reads a Hermes session's rows after a message id (the session a row of `db.Sessions`, whose `Owner` decides its turns). An event has: harness; path (the plain path, or the store); offset and next (the line's first byte and the next line's, in the JSONL bytes, a compressed copy's decompressed stream; for Hermes both the message id); index (its place among its line's events: path, offset and index name an event); session, subagent and parent; time; cwd; model; kind (`owner_text`, `agent_text`, `harness_text`, `tool_call`, `tool_result`, `compaction`); role (`user`, `assistant`, `tool`, `developer`, `system`); who (`owner`, `agent`, `harness`, `unknown`) and why; input kind; prior; text; tool id, tool name, tool input and tool output; an error flag.

- Session is the id the harness gives the item: Claude Code's `sessionId` (a subagent's lines carry their parent session's), the Codex thread, the pi session, the Hermes session. Subagent is Claude Code's `agentId`, a Codex subagent thread's own id, a pi task's own id, a Hermes delegation's or subagent's id; empty in a session of its own. Parent is Codex's `parent_thread_id`, pi's `parentSession` as an id, Hermes's parent session. Cwd is the session's working directory as last recorded; model the model of the agent's last reply (Codex: the turn's `turn_context`; Hermes: the session's `model`).
- Who and why come from the rules of Who typed a turn and What in a turn is theirs, never a copy: per session `digest.SessionWho` (Hermes: `hermes.Session.Owner`), per Claude Code line `digest.ClaudeTyped` and `digest.ClaudeQueued`, per piece `digest.TurnPieces` (an answer to a Codex question that is one of the options it offered is the harness's, `digest.CodexAsked.Offered`, with its text as recorded), a turn no person typed by `digest.UntypedWho` (the digest's rule for it), and the owner's own words as the corpus reads a turn (`ownerwords.TurnReader`, with the corpus's `Pastes`, the texts the prompt history under the reading user's home directory records they pasted, `ownerwords.ClaudePastes`; a read of an owner's session fails when that history cannot be read): an `owner_text` holds what the corpus counts as theirs, in the place of the turn's first piece of theirs, and what the corpus cut from their pieces, each part as it was (a pasted table or log, a paste the prompt history records, a line of agent text they relayed, a part their pieces' own split finds not theirs; `TurnReader.PartsCut`, `HermesCut`), is an `agent_text` after it ("cut from the owner's turn"), never their words around a cut. In a Hermes row the gateway's frames around their words (a quoted reply, origin data, attached context, a paste's reference) are in no event; the row holds them. A turn in a session no person types into is an agent's, or the harness's when it is harness text, whole, as in the digest; unknown in a Codex session with no `session_meta`. A message Claude Code delivered mid-turn with a command mode other than `prompt` is the harness's. Why is the rule's reason: the session's verdict (`entrypoint cli`, `codex subagent`, `pi headless`, `hermes owner session`, ...), a line's mark (`accepted suggestion`, `origin peer`, `commandMode task-notification`, ...), or the piece's (`harness text`, `agent text in the owner's turn`, `an option the question offered`). The agent's reply and its tool calls are the agent's; a tool result, a hook's output, a compaction, a Codex developer message and an error message the harness wrote in the agent's place (Claude Code's `<synthetic>` reply, flagged as an error when it is `isApiErrorMessage`; pi's `errorMessage`) are the harness's; a pi `!command` in a person's session is the owner's call.
- Input kind, on the events of a user turn: `typed`; `queued`, typed while the agent worked (Claude Code's queued message or `promptSource: queued`; a Codex user message after the agent acted in the running turn, between `task_started` and its end; a pi user message after a tool result or a reply that asked for tools; a Hermes `steer`); `slash` (a command's echo and its arguments, a local command); `shell` (Claude Code's `<bash-input>` and the output it records, pi's `bashExecution`); `answer` (a Codex question reply; the result of Claude Code's `AskUserQuestion`); `suggestion` (`promptSource: suggestion_accepted`, an agent's words the person sent). Empty on events of no turn a person put in.
- Prior, on the events of a user turn: the harness's record of what happened since the item before it. Claude Code: the subtype of the last `system` line (`turn_duration` when the agent had stopped, `stop_hook_summary`, `api_error`, `away_summary`, `local_command`, `compact_boundary`, `informational`, ...); a meta line and a compaction's summary do not end it. Codex: the last of `task_complete`, `turn_aborted`, `error`, `stream_error`, `context_compacted`, `thread_rolled_back` and a `compacted` entry. pi: the stop reason of the agent's reply before the turn (`stop`, `toolUse`, `error`, `aborted`, `length`), or a `compaction` or `branch_summary` after it. Hermes: the finish reason of the reply before it. Empty when nothing was recorded.
- A tool call and its result pair by tool id: Claude Code's `tool_use.id` and `tool_result.tool_use_id`, Codex's `call_id` (a web search's `id`), pi's `toolCall.id` and `toolCallId` (a `!command`'s entry id), Hermes's `tool_calls` ids and `tool_call_id`. A result names its tool by its call. A Codex tool in a namespace is named as Claude Code names an MCP server's: `<namespace>__<name>` (`mcp__tacit__tacit_search`). Tool input is the call's arguments as recorded (JSON; a Codex custom tool's raw input), tool output what the agent got (text blocks joined, `[image]` for an image). The error flag is the harness's own record: Claude Code's `is_error`; pi's `isError`, and a `!command`'s nonzero `exitCode`; for Codex, the end it writes before an output (an `item_completed` event whose item, by the call's id, has `status: failed`, a nonzero `exit_code` or an `error`; in older versions `patch_apply_end` with `success: false`, `mcp_tool_call_end` with an `Err` or `isError`, `exec_command_end` with a nonzero exit code), the exit code in the header it writes above a command's output (`Exit code: N`, `Process exited with code N`, above the line `Output:`; never the command's own text), the first line of its script tool's output (`exec`, `wait`: `Script failed`, `aborted by user ...`, `unsupported custom tool call`), and an older tool's `metadata.exit_code`; an end Codex writes after the output does not flag it (on the rig, 3 of the 24 `exec_command` ends in 60 recent rollouts, Codex 0.163 to 0.165). A Hermes tool row by the digest's rule (`digest.HermesToolError`); a Hermes reply of `display_kind` `failed_turn`.
- What is read. Claude Code: user lines (text and tool results; a compaction's summary is the compaction), assistant lines (text and tool calls; thinking is not), `system` lines (each a prior, the compaction's boundary among them), attachments that are a queued message or a hook's output that reached the agent (its `content`, with the `toolUseID` of the call a tool hook ran for); other attachments (reminders, listings, file snapshots) are not. Codex: messages (developer ones too; reasoning is not), `agent_message` items (another agent's message to the thread), calls and outputs, `compacted` entries, `turn_context` and the events above. pi: messages (a system prompt is not), `compaction`, `branch_summary`, `custom_message` and `model_change` entries. Hermes: user, assistant and tool rows, of a session of any source; a compaction copy is passed over, a `_compressed_summary` row is a compaction, and a row's tool call id and finish reason and the session's model are read when the store has those columns (an older Hermes has not). opencode is not read.
- Lines that do not parse. A transcript line whose record the reader cannot decode, or whose message holds no text it can take, is counted (`State.Unparsed`).
  - What counts. A line that is not JSON (one a crash cut short, which the next write joined; stray bytes), or whose JSON is not the record its format writes: a list, a string or a number where the record goes; a field the line's kind reads, of another type (for a Claude Code attachment, by its type: a queued message's command mode, a hook's event and tool use id; for Codex, a field of a `response_item`, `event_msg`, `turn_context` or `compacted` payload, by the payload's type, an end event's call id and what says its call failed, `success`, `exit_code`, `result` or `item`, among them; for pi, of a `message` entry's message, by its role, and the entry's id, which only a `!command` reads); or a message's content that is neither a string nor a list (also a pi reply's that is not a list, a Claude Code queued message's prompt and hook's output, a Codex compaction's summary), which holds no text the reader can take, so the whole message would be gone. Only what a line's kind reads is checked: a field of another type in a kind the reader passes over (a new kind, an attachment type it does not read, a reasoning item, a token count, a label), or in a field the line's kind does not read, counts nothing, and the line is read as if that field were not there. A counted line gives none of the events its record holds, but what it left still holds: a Codex `compacted` entry marks its compaction, with no summary; what decoded of a Codex `event_msg` still marks the turn, and a call's failure under a call id that decoded (an end whose id did not decode marks none); a Codex question's options are noted by the rule the digest follows (`digest.CodexAsked`), whatever the reader decodes; a line whose content is of another shape still gives its session's ids and cwd, a reply's model and the record before the next turn, and a pi reply its provider error. Not counted: a line that holds nothing (blank, or `null`); a last line without its newline that is not whole JSON yet, which is not read (once a write ends it, it is read, and counted if it still does not parse); a part inside a message's content, decoded as far as it goes (a block of another shape, a tool's output, a time). In a Hermes session the count is of the assistant rows the reader reads (not a compaction copy or a summary) whose `tool_calls` do not decode (not JSON, or calls of another shape): their text is read, their calls are not.
  - The count. A `State` counts these lines (rows) before its cursor, from the session's start, however the read came there: a read that starts at a `State`'s cursor adds the ones it reads to that `State`'s count, and any other read (a bare cursor's, or a `State`'s whose items changed) counts the ones before the cursor in its pass. So a session read in parts ends with the count one read from the start gives, unless a harness wrote its next record on the same line as one a read took whole before its newline: that read gave the line's events, and a read from the start counts the joined line instead. At the end of a session a `State` a read returned is returned as it is, with its count; a bare cursor there (one a caller makes, one saved before the count, a damaged one) is read with the pass, so the `State` returned holds the count. So a program that follows finished transcripts keeps the `State` a read returns, a compressed copy's too: from it a read at the end costs nothing, from a bare cursor the pass, a whole decompression for a compressed copy. `ReadFile` and `ReadHermes` return no count and read nothing at the end. A read that fails on I/O or the store before it reached the cursor returns a cursor with `from`'s count. The count holds nothing of the lines it counts.
  - Measured 2026-10-30 on the rig (counts only): the newest transcripts of each source, up to 400 a source and until 1.5 GiB of JSONL was read (1,371 transcripts, 5.8 GiB), and the newest 400 Hermes sessions hold none, so a count above 0 points at a line a crash cut or a format the reader does not know.
- Cursors. A read returns where the next one resumes: the offset after the last line read, or the last message id. A last line without its newline is read once it holds whole JSON. A cursor past a transcript's end is an error (`ErrPastEnd`: the file was cut or replaced), and so is one past a Hermes session's last id (the store went back). A read from a cursor gives exactly the events a read from the start gives from there: what a line's events depend on in the lines before it (the call a result names, the options a Codex question offered, a local command's caveat, the end event of a call, a turn under way, the record before a turn, the model and cwd) is rebuilt from those lines, whose events are not emitted, so path, offset and index name one event however a session is read, as long as the prompt history's pastes are the same (a paste recorded later cuts an older turn too, as it does in the corpus) and the transcript has its first 256 KiB (who wrote the session is decided on them). A read from a cursor costs a pass over the lines (rows) before it, and `ReadFile` or `ReadHermes` at the end none (on the rig's largest rollout, 2.4 GiB of JSONL: 14.4 s from the start, 13.4 s from its middle, 19 µs at its end). When `emit` returns an error the read stops and returns the offset of the line it stopped in (the id before the row's); a read from there gives that line's events again.
- Saved state. `ReadFileState(path, format, from, limit, emit)` and `ReadHermesState(ctx, db, session, from, emit)` read from a `State` and return the `State` after the last line (row) read: its cursor, `Offset`, what the reader kept from the items before it, and the count of those that did not parse (`Unparsed`).
  - What is kept. For a transcript: the session's ids, cwd and model, the calls a later result names, the record before the next turn, a Codex turn under way and the calls whose end event reported a failure before their output, pi's agent mid-turn, and the lines that changed what a rule of another package follows across lines (a local command's caveat, `digest.ClaudeCommands`; a Codex question's options, `digest.CodexAsked`), which a new reader reads again. For a Hermes session: the record before the next turn and the calls; its other fields are its row's. Every `State` a read returns, a cursor too, holds the count of lines (rows) before its cursor that did not parse, as Lines that do not parse says. A test lists every field a reader or a `State` carries across lines and where it goes, and pins `keptVersion` (2 since the count), so the two change together.
  - What a read checks. A read from a `State` that kept them starts at its cursor and gives exactly the events a read from the start gives from there, without the pass, as long as the items before the cursor are the ones it was kept from. It checks a transcript's first 256 KiB (every byte before the cursor when that is less) and the line before the cursor, and every field of a Hermes session's row at the cursor, which Hermes writes again on /retry, /undo and /compress. When they changed (a file replaced or rewritten, rows written again) the read is a cursor's, with the pass. A change further inside a transcript, or to a Hermes row before the one at the cursor, is not seen.
  - Cost. A program that follows a growing session pays only for what was added. On the rig's largest plain transcript (0.38 GiB of JSONL) the last MiB took 1.39 s from a cursor and 18 ms from the `State` saved there, its load and the next one's save included (medians of 3); that `State` was 0.8 MB, and the `State`s at the ends of all 10,701 of the rig's transcripts (42 GiB of JSONL) total 52 MiB. A compressed copy is still decompressed up to the cursor (a zstd frame cannot be entered in the middle), but its lines are not read: on the 2.4 GiB rollout, 1.50 s against 11.5 s.
  - Form. The zero `State` is the start, and a read that ends there (a first line still being written) returns it: what the readers take from a first line comes from the head. For the same reason a read that ends past the head it began with (the transcript grew during the read) returns a cursor. `State{Offset: n}` is a cursor. `MarshalBinary` and `UnmarshalBinary` save and load one as JSON, its count with it, as do `MarshalJSON` and `UnmarshalJSON` inside a caller's JSON; a `State` saved in another format loads as a cursor. One saved before the count (version 1) does too, and one whose count is damaged (below 0, or no whole number), so its next read passes over the lines before its cursor once and counts them. A `State` is as private as its transcript: it holds whole lines of it, the cwd and tool names, unredacted. Keep it where the transcript may be kept, and never send it.
  - `limit` above 0 stops a read at the end of the first line that ends at least that many bytes past the cursor, so a long transcript can be read and saved in parts; each part of a compressed copy is decompressed from its start again. When `emit` returns an error at the first event of a read that started at its `State`'s cursor, the read returns that `State`; otherwise a cursor at the line it stopped in (the id before the row's). `ReadFile` and `ReadHermes` are these reads from a cursor.
- Events hold the text as recorded, unredacted. `RedactEvents` masks their text, tool input and tool output with scrump's text profile, each text masked as it would be alone, and fails closed: on any failure it returns no events and the error. One stream would let a hit that starts in one text run into the next and keep its secret (a quoted value a cut left open, a candidate a rule's filter rejects, a keyword rule's reach across lines), so the texts go in one call as records, each scanned on its own (`scrump --records`, scrump 0.2.0 and later). The first records call of a process carries #84's repro ahead of the texts; a scrump that refuses the flag, or keeps the repro's password, is not asked for records again in that process, and the texts go joined by a boundary instead: `\n#'"\n`, 1,024 newlines, `#\n`, the record separator, `\n`. Its quotes close a value a cut left open and its newlines outreach every rule's reach across lines; a hit that masks any of it halves the batch until every part comes back whole. Any other failure fails closed. A text holding a record separator is masked in a call of its own. `tacit doctor` sends the same repro as two records and reports `scrump records`: ok when scrump keeps them apart, a warning when it has no records mode (the boundary keeps the texts apart), a failure when its answer is neither, since every batched redaction then fails. Its `scrump` check fails a scrump that leaves a quoted value a cut left open, as scrump before 0.2.0 does.

Measured 2026-10-30 on a sample of the rig's sessions (counts only): 2.2 GiB of transcripts (217 sessions, compressed Codex rollouts among them) read in 12.8 s; 91,512 of 91,710 tool results paired with a call read before them; 1,828 of 75,742 Codex results flagged as errors; of 62 Claude Code owner turns 42 came after `turn_duration` and 7 after `away_summary`; of 1,031 Codex owner turns 645 came after `task_complete` and 317 were steered into a running turn; 303 owner turns in 40 of the 109 Hermes owner sessions, 20 of them steers.

**The facade** (`client/pkg/evidence`) exports:

- events: `Event`, `Kind` (`KindOwnerText`, `KindAgentText`, `KindHarnessText`, `KindToolCall`, `KindToolResult`, `KindCompaction`), `InputKind` (`InputTyped`, `InputQueued`, `InputSlash`, `InputShell`, `InputAnswer`, `InputSuggestion`), `ErrPastEnd`, `ReadFile`, `ReadHermes`, `State` (`Offset`, `Kept`, `Unparsed`), `ReadFileState`, `ReadHermesState`, `RedactEvents`;
- sources: `Source`, `Sources`, `TopLevel`, `Files`; transcripts: `Glob`, `Open`, `OpenAt`, `Head`, `Stat`, `Resolve`, `Plain`, `Name`;
- who wrote it: `Format` (`Claude`, `Codex`, `Pi`, `Hermes`), `Who` (`Owner`, `Agent`, `Unknown`, `Harness`), `Verdict`, `Piece`, `ClaudeMarks`, `ClaudeCommands`, `CodexAsked`, `TurnReader` (`Parts`, `PartsCut`, `Hermes`, `HermesCut`, `Pastes`), `SessionWho`, `ClaudeMarksOf`, `ClaudeTyped`, `ClaudeQueuedLine`, `TurnPieces`, `OwnerPieces`, `UntypedWho`, `HermesOwnerText`, `HarnessText`, `Compacted`, `AgentCwd`, `PiTask`, `OwnerPart`, `PastedBlob`, `ClaudePastes`, `LineTime`;
- the Hermes store, read-only: `HermesDB`, `HermesSession`, `HermesMessage`, `OpenHermes`, `DefaultHermesDB`, `HermesContinued`;
- repository identity: `Repo`, `RepoCache`, `RepoResolver`, `RepoMains`, `RepoOf`, `RepoOfMachine`, `NewRepoCache`, `NewRepoResolver`, `ProjectsDir`, `LoadRepoMains`, `RepoCounts`, `DominantRepo`;
- redaction, the forms that return an error (fail closed): `RedactErr`, `RedactAllContext`, `RedactionReady`, and `RedactRecordsContext`, records mode with no fallback, whose `ErrNoRecords` says the installed scrump has none;
- model runs: `Route`, `Result`, `Trace`, `CallRecord`, `ErrInvalidResult`, `Run`, `RunWithFallback`, `WithRoute`, `WithJSONSchema`, `WithTrace`, `Preflight`, and the dreamer's exclude list, which a prompt holding the owner's evidence must go on so it never comes back as their work: `NewSessionID`, `Exclude` (`modelrun.ExcludeFile`, `~/.local/state/tacit/dream-exclude`; the dreamer reads it through `modelrun.Excluded`; an error when a write fails), and `RunExcluded`, which lists its session before the call and the session the runner reports after it, and makes no call when it cannot write the list.

The module is `github.com/agent-sh/tacit/client`; a program outside tacit requires it at a commit of `main` (a pseudo-version) until releases are tagged `client/v<version>` as well.

## The reviewer

Every note an agent writes, and every note imported from an agent's own memory, is judged before it is trusted (the owner, 2026-10-24: "agents can misinterpret"): a note of harness `claude`, `codex`, `pi`, `hermes`, `grok`, `muse`, `agy` (`tacit add`, the MCP `tacit_add`, the Hermes provider's memory writes) or `import` (`tacit import`, an agent's memory file), in the store's inbox or, on a read-only clone with the local layer, this machine's overlay (`local/<harness>@<host>/`). Dreamer notes are not reviewed: the dreamer reads the owner's sessions and the curator checks their words. It is on by default; `reviewer: off` in the settings file or `TACIT_REVIEWER=off` turns it off (`client/internal/agentreview`, `client/cmd/tacit/reviewer.go`).

**The session.** `tacit add` and `tacit_add` record the session a note is written in as `source.session`, from what the harness gives a tool it runs, never a guess: `CLAUDE_CODE_SESSION_ID` (Claude Code's Bash tool and MCP servers), `CODEX_THREAD_ID` (Codex), `PI_SESSION_ID` (pi's bash tool), or `TACIT_SESSION=<harness>:<id>` from an integration that knows it (the Hermes provider sets it for its memory writes). An id with characters that could name a path is not recorded. An imported Claude memory carries its own `originSessionId`; the harness of an imported note is where its file was read from. The session's conversation is its transcript on this machine (the dreamer's sources: `~/.claude/projects/*/<id>.jsonl`, a Codex rollout or a pi session whose name ends in the id) or its rows of the Hermes store.

**The judgement.** The deciding model (role `review`, Opus) reads the conversation as rulebook's reviewer does (the Claude mod `~/.claude/mods/rulebook`, whose prompt and digest these are): every message the owner typed as `OWNER`, any other incoming message (a side agent's note, a task report, another session, a hook, and the paste the desktop app framed inside a turn of theirs) as `NOTE`, the agent's replies as `AGENT`, the tools of the last 60 messages, at most 160,000 characters (the oldest agent and note lines go first, then the oldest owner lines), up to 20 messages after the tool call that saved the note (the owner's reaction is evidence too). What the owner typed is decided in one place (`agentreview.OwnerTurn`: `digest.SessionWho` on the session's path and first bytes, then the line's turn by the rules of Who typed a turn, read as the corpus reads it, `ownerwords.TurnTexts`; a message the owner typed while the agent worked is theirs, Mid-turn messages), so an agent's prompt in a headless session, a subagent's brief or an agent relaying "the owner says yes" is never the owner. The conversation is redacted with scrump before the model reads it (fail closed: no review). It answers `correct`, `uncertain` or `wrong` with one or two sentences of reason; any other reply is no verdict and the note waits for the next run. A note with no session, or whose session is not on this machine, gets `nosource` with no model call: a low-weight agent's note, never trusted.

**Rulebook's verdicts are honoured.** On a machine whose Claude Code runs rulebook, its log (`~/.local/state/rulebook/reviews.jsonl`, or `TACIT_RULEBOOK_LOG`; `off` for none) already holds a verdict on many saves, made before they ran: a memory file's by its path and description, a tacit add's by its name (with tacit's suffix for a taken name) and its description or session. Its newest verdict on a note is taken as the note's (`by: rulebook`), with no model call; a failed review is none. A mod with the owner-decision patch also logs the owner's approve and discard of a held rule (`owner-approved`, `owner-discarded`, `by: owner`), which stand as their `confirmed` and `rejected`.

**The ledger.** Each verdict is a line of `review/agent-reviews.jsonl` (the curator's, merged by union like the quote ledger), or `local/curated/review/agent-reviews.jsonl` with the local layer: the note's path and name, a hash of its text, the verdict, the reason, who gave it (`tacit`, `rulebook`, `owner`), the model, the session it was judged against (`claude:<id>`), the time and the cost; an owner's line adds where they answered and a hash of their turn, their words and the statement that holds a correction; a reviewer's uncertain line adds what is in doubt and what the note's core is (`doubt`, `kind`: Questions), and a trim's lines what it kept and removed (Trims). The first run writes a start line; a note created before that day is not judged unless `tacit reviewer --backfill` is asked (the store's earlier notes stay as they were); the report line counts them (`N older than the reviewer`). The verdict that stands on a note is the owner's newest, else the newest; it holds for every curated fact made from the note (its `origin`). `fact.Fact.Review` is read from the ledger only; a field is a claim.

**What it changes.** On a writer clone the step runs in every curate, full (at most 40 model reviews) and quick (at most 6), before the batches, as one curator commit (`curator: review: ...`). An agent's note with no verdict yet waits up to 3 days (`curator.json` `review_wait`), then is curated unreviewed. `wrong`: not curated; it stays in the inbox, its reason in the ledger (`review_refused` in the report). `correct`, `uncertain`, `nosource`: curated as before, and in a store of format 4 the fact carries the verdict (`source.review`, `review_reason`). With the local layer the step runs in the layer's curate on this machine's agents' notes, which are never edited: their verdict is applied from the local ledger. Delivery reads the verdict (index schema 15, the `review` column): a note checked against its session is `agent note (<day>; checked against its session)` and weighs 1.25 times its score, one the owner confirmed `you confirmed (<day>)` at 1.4 (below their rules, which have their own slot), one `unconfirmed` or `unchecked: no session` at 0.7; one judged `wrong`, replaced by its trim, or that the owner said no to or corrected, no hook delivers, and search and the tree show it marked; a trimmed note is `agent note (<day>; trimmed to what its session supports)` and weighs as a checked one. A fact with no verdict keeps its score, so a store the reviewer has not run on is delivered as before.

## Trims

Most uncertain notes are a true core plus one overreach (the rig's rebuild, 2026-10-25: 127 of 192 judged notes were uncertain, mostly a one-off remark widened into a standing rule, a side agent's claim given as the owner's, or a detail later contradicted). The owner, 2026-10-25: "not everything I say needs to become a rule". So the reviewer cuts such a note down instead of asking about it (`client/internal/agentreview/trim.go`, `client/cmd/tacit/reviewer_trim.go`).

**What the reviewer returns.** The digest numbers each message (`[n] OWNER: ...`). For an uncertain note the reviewer also says what is in doubt, `doubt`: `core` (the main point itself) or `overreach` (a true core and claims that go further), and what the core is, `kind`: `rule`, `decision`, `mistake` or `fact`. With an overreach it returns the trim: the claims kept, in the note's own words, each citing the messages that support it; the claims removed, each with why; a narrower scope when what is kept belongs to one; and, when what is kept is a rule or a choice resting on the owner's words in this conversation, their remark (`one_off`: their words copied from one `OWNER` line, its number, a line of what was being worked on, and its `relevance`, see Statements). Each removed claim has a `basis`: `unsupported` (nothing the reviewer read supports it), `contradicted`, `widens` or `not_owner`.

**What the digest left out.** Over its 160,000 characters the digest leaves the oldest messages out, cuts long messages short and shows the tools of only the last 60 messages; the reviewer is told how many messages were left out and where (spans of their numbers) and how many were cut short (`agentreview.Omission`; the line's `omitted`). For each claim a trim removed as unsupported (or with no basis), code searches what was not shown (`agentreview.Hidden`: the left-out messages, the rest of each message cut short, older tools' input, never the tool call that saved the note) for the claim's distinctive words: words of four letters or more and tokens with a digit, in at most one message in twenty. A message matches when it holds half of them, two at least, one of them in at most three messages or with a digit. The reviewer then reads those parts (at most 4 a claim, 12 in all) and judges each claim again (`agentreview.SecondLooks`, the line's `looked`): kept, citing the messages, it goes back among the kept claims; removed on another basis, the removal stands. A claim is never removed as unsupported while code finds its words there: removed so again, or not answered, the trim is refused and the note stays uncertain (the hand check of 15 trims, 2026-10-25: 7 had removed a claim whose support was in what the reviewer was not shown).

**Code checks it only removes or narrows** (`agentreview.CheckTrim`): every kept claim cites messages the reviewer was shown; each of its content words is the note's, or one of at most three narrowing words found in a message it cites; the trim is no longer than the note, those words aside; a claim that gives the owner's authority (the owner said, wants, ruled) cites a message they typed, and the trim says so only where the note did; the scope stays or narrows (a project, machine, org, area or topic for a note of the owner's or the system's scope; a topic under its area). A rule or a choice kept on the owner's words, by the reviewer's `kind` or worded as a standing rule (always, never, must, ...) on a message of theirs, must come as their remark, whose words must be verbatim in an `OWNER` message. A trim that fails any check is refused, with its problems in the step's report (`trim_problems`); the note stays uncertain. The trim's text and the owner's words are masked with scrump (fail closed).

**What it writes.** The note stays where it is (never deleted) with the verdict `replaced`: its kept claims with their citations, its removed claims with their reasons, and what stands in its place (`into`). That is:

- a trimmed note, `<name>-trimmed.md` in the note's folder: the note's own metadata (harness, host, session, kind), its description the first kept claim, its body the kept claims, its scope the narrower one when given, with its own ledger line, verdict `trimmed` (`of`: the note). The curator writes nothing else in the inbox: an agent's note is never edited. The trimmed note is curated in the note's place, a trusted agent's note (weighted as one checked against its session; `source.review: trimmed` in a store of format 4), and the replaced note is not curated, like a wrong one;
- or, with the owner's remark, their statement (Statements: their words verbatim, the day of the message they typed, the session, the reviewer's line of context, the kept claims that cite their messages as the gloss) in the trim's scope or the note's, with a words line in the quote ledger; the kept claims that cite none of their messages stay a trimmed note beside it (`also`). Never a rule: only the statements step's ladder promotes it. A store whose format predates statements keeps such a note uncertain.

The note's curated facts get `superseded_by` what stands in its place. On a read-only clone with the local layer, the trimmed note and the statement are the overlay's: the trimmed note beside its note in the agent's folder (`local/<harness>@<host>/...`; `overlay.WriteNote` writes there and nowhere else), the statement under `local/curated/`. A file the step cannot write is an error of the step, and its verdicts are written to the local ledger all the same (before v0.9.14 a trimmed note of an imported memory was refused as outside the layer, and the step's verdicts were lost with it). `tacit reviewer --retrim` judges again, for their trim, the notes whose uncertain verdict is from before trims (no `doubt` recorded, rulebook's included, in the session rulebook judged them in); a verdict other than uncertain from that second reading is counted and not written. In every run, a note rulebook judged uncertain is also read by tacit's reviewer for its trim; rulebook's verdict stands.

## Questions

An `uncertain` note is a question for the owner only where it matters, asked in the session they are already in (the owner, 2026-10-24: "switching to another location is not comfortable and I will probably not do it"). Code decides it (`agentreview.Gate`): its core is in doubt (`doubt: core`; an overreach is trimmed instead), it is a rule, a decision or a past mistake, it is about a project whose record says `active` (the winner when its folder is suppressed; the local layer's status on this machine), and neither the owner's words nor a check settle it: no live statement, ruling or fact they confirmed in its scope shares three of its content words, and no check refutes one of its dry references (a repository, a path, a version). Fewer than 12 questions must wait when it is queued. Everything else stays a silent low-weight agent's note, which the rotation checks before other facts of its age (Rotation); the step's report counts them by why (`silent`). Questions live in this machine's state directory (`questions.json`), where the reviewer adds them and applies the answers; nothing waits on them, and agents keep resolving notes themselves (a note the owner never answers stays a low-weight agent's note).

**Asked where it belongs.** At the prompt (Claude Code's and Codex's UserPromptSubmit, the Hermes provider's prefetch; pi's extension, which `tacit install pi` writes into pi's `extensions/` and which runs `tacit hook questions`), in a session a person types into (`ownerwords.Who` on the transcript's first bytes; a Hermes owner session), the hook puts at most one open question that belongs there, by code: the note's repository (its `projects/<repo>` scope or its one `applies_to.repos`) is the session's under any of its names; for a note of no repository, the session runs in the folder the note's session ran in, or the prompt shares three of the note's content words (two with one a specific identifier). The block tells the agent to end its reply with the question, word for word: `[tacit q-<id>] On <day> an agent saved this in a <harness> session <id> in <repo>: "<description>". Right? yes / no / correct it: <your words>`. A session is asked at most 2 questions, one at a time, and a question at most 3 sessions; at most 12 wait (a 13th is not queued), and every question expires after 30 days. A question is settled when later evidence decides the note: a verdict other than uncertain stands on it (its trim, too), the note is gone, every fact made from it was replaced, or a second reading (`--retrim`) puts it outside the gate. With no question waiting the hook reads nothing but the queue's file and prints nothing.

**Answered only by the owner's own turn.** The answer is read by code from the session's transcript after the question was put (from where the transcript stood then): the first agent message that holds the question's tag, then the owner's own next turn (`agentreview.OwnerTurn`). Another agent's message, a task notification, a hook's text or an agent relaying "the owner says yes" is never the answer; a turn of theirs that answers something else passes the question over. `yes` (right, correct, ...) makes the note theirs to keep: `confirmed`, and in a store of format 4 its curated facts carry it. `no`, with an optional reason, retires it: its curated facts get `retired` (with the local layer the note is held back). A correction (`correct it: ...`, `no, it's ...`, `yes but ...`) is a statement in their words (Statements: their words verbatim and dated, the agent's note as the context, a words line in the quote ledger), and the note's curated facts are superseded by it; in a store whose format predates statements their words are the reason it is retired. The prompt hook reads the answers of its own session; the reviewer step reads every session's and applies them. In Claude Code the open questions also wait in the rulebook mod's pane, with the patch to the mod: its approve, discard and edit are logged with the question's id, and tacit takes them as the owner's yes, no and correction.

## Rulings

A ruling is the owner's own words, provably. Everything else, however it was filed, is an agent's statement: it is not labelled "your rule", and the verifier treats it like any observation (one that holds a few words of theirs is weighed by them: Their words, below). `fact.IsRuling` is the one definition for the store's facts, used by the hooks' `RULE` lines (less the rulings in their task, below), the app and the audit, and the guard the verifier, the staleness check, the results step, the link repair and the curator's supersede check use. Nothing about rulings waits on the owner: the audit asks them nothing. A fact of a machine's overlay is never a ruling by this definition (`fact.OwnerWrote` is false for every `local/` path); a fact of a read-only machine's local curator is judged by its own rule, `overlay.IsRuling`, against that machine's quote ledger (Local layer).

**The switch.** A store keeps its old definition (`source.kind: user`, or `type: user_standard`) until the rulings audit has run on it: the audit writes `review/rulings-audit.json` (version, the HEAD it audited, when; no list of facts) in its own commit, and `fact.Walk` reads it. With the marker a ruling is `source.kind: user` and one piece of evidence that the words are theirs:

- **Written by them**: `source.harness: human` on a curated fact (New rule in tacit app; only the app writes harness human facts and only the curator key writes curated ones), or a note in their `inbox/human@<host>/` that the app added: the commit that added it is one of the app's owner commits (`owner: ...`). The field and the directory alone are claims: `tacit add` and `tacit mcp` refuse harness `human` and `curator`, and lint L4 refuses an inbox note whose `source.harness` is not its directory's.
- **The owner's words, quoted**: `source.owner_quote` is a phrase the fact holds, found as a statement of theirs (below) in one of their turns or app notes, and `source.owner_quote_from` says where (`claude:<session>`, `codex:<session>`, `pi:<session>`, `hermes:<session>`, `note:<name>`). The curator's quote ledger `review/owner-quotes.jsonl` records each (name, quote, where, a hash of their turn, the day); lint L15 requires the entry, so a claim the store does not back fails even after the transcript is gone.
- **Kept by them**: `source.endorsed` is the id of their standing decision in `review/decisions.jsonl` that keeps this fact: a pair the owner answered keep this one (`left` keeps A, `right` keeps B; a reopen clears it; an agent's record, `by: agent`, never counts), or `mine`, their "This is mine" in the app. L15 checks the decision stands and keeps this fact.

A field is only a claim: `fact.Walk` (and `fact.WithStore` for a fact read on its own) reads the ledger and the decision log, and a quote or an endorsement counts only when the store backs it. A forged `owner_quote` is no ruling and prints no `RULE`, whether or not anyone has linted. A marker that exists but cannot be read is an error (`fact.ErrMarker`): `Walk`, `WithStore` and lint fail rather than fall back to the old definition, which would turn every `user_standard` an agent filed into a rule no agent may touch, and every caller refuses to act (`tacit resolve` changes nothing, the link repair edits no fact). Evidence fields in a store with no marker are an L15 finding (only the audit writes them).

The type does not make a ruling: a `user_standard` with no evidence is the agents' reading of their preference.

**The owner's turns.** `internal/ownerwords` reads what the owner wrote themself on this machine:

- Claude Code transcripts, turn by turn: a user turn a person typed, and a message they typed while the agent worked (Who typed a turn and Mid-turn messages, in Dreamer sources), its text split by who wrote each part (What in a turn is theirs). A scheduled task's prompt, a teammate's or a background task's turn, an accepted suggestion, a line from a headless entrypoint (`sdk-cli`, `sdk-ts`), a compaction summary, a sidechain, harness text and a side agent's note are not theirs; a slash command's arguments (not a local command's) and what they typed below a note or after a reminder are.
- Codex sessions a person started (Who typed a turn), plain or compressed and archived ones too (Compressed transcripts): a person's front end, and not a subagent, an exec run or a guardian review; their messages split the same way (their answers to an agent's questions are theirs, an option they chose is not).
- pi sessions a person started (not headless, not a subagent's; Who typed a turn), their text blocks, less a turn that opens with a tag and a pasted table or log, under `pi:<session id>`.
- Hermes owner sessions (Dreamer sources), each user row cut to the owner's words, compaction copies passed over, less a turn that opens with a tag and a pasted table or log (as for pi), under `hermes:<session id>`. A store that exists and cannot be read is an error, as an unreadable transcript is.
- The prompts the owner typed (`~/.claude/history.jsonl`, `~/.codex/history.jsonl`), which outlive the transcripts, less those of a session whose transcript is an agent's (a lane a program types into through a terminal, a Codex subagent) and, for Claude Code, those whose `project` is a directory only agents use.
- The session digests of `eval/mine/digest.py` (`~/.cache/tacit-mine`). The session is decided from its transcript (`src`) while that exists, else from the header's `entry`; without its transcript a Codex digest that names a person's front end is skipped, since a Codex subagent names one too. A subagent's digest (`--sub-`) is skipped.

Left out everywhere: sessions started where only agents start them (`/tmp` itself and below it, `/.claude/jobs/`, `/.cache/`, a scratchpad, an e2e driver, a runner's `/.local/runners/` checkout), a Codex message that is mostly a pasted table or log (six lines or more, half of them table rows or log lines; Codex keeps no record of pastes), text the owner pasted (the history's `pastedContents`, removed from the transcript's copy of the turn), a message that opens with a tag (`<task-notification>`, `<codex_delegation>`, `<synthetic>`, ...), Claude Code's notices, and an orchestrator's role prompt (a turn opening "You are ..."; the filters assume the owner writes in lower case). Inside their turns, agent text the owner relayed without a paste record is left out line by line: a markdown header, a line with a backtick or `**`, a bullet or numbered item opening with a capital, a backtick, `*` or `[`, and every line of a block of three or more capitalized prose lines (eight words or more, ending in `.`, `:` or `;`). The filter assumes the owner types plain lowercase lines in a terminal. On 2026-10-11 it dropped 982 distinct lines from 214 of 17,241 owner turns, and a random sample of 20 was all agent text. Agent prose the owner relays as plain lowercase lines is a known gap.

**Verbatim, and a statement.** Text is normalized before it is compared: lower case, apostrophes dropped (the owner writes "dont", an agent quoting them writes "don't"), every other character that is not a letter or a digit a space. A phrase is looked up from three words and 18 characters, on word boundaries; an ellipsis splits it into parts that must all be in one turn, in order. Quoted phrases are taken from double, typographic and guillemet quotes, single quotes at word edges, blockquote lines, and a clause the fact attributes to them without quote marks ("Owner 2026-09-05: <clause>.", or a name in `$TACIT_OWNER_NAMES` in place of "Owner"); a quoted command, path, flag or agent markdown is not one, and neither is such an attributed clause (`codeQuote`). A phrase is code when it holds a backtick, `**` or an assignment (`KEY=value`); when two code-like words (`--x`, `-x`, a path, `=`, `$`, `#tag`, `|`, `&&`) sit side by side; when it opens with a command (a sentence opening with "dont", "never" or "always" that names a command stays prose) (`gh`, `git`, `export`, `nice`, ...; after "run", "use" or "try" too), or a command is followed within three words by a code-like word, and it holds one; when a shell operator or loop runs through it (every word after `|`, `&&`, `#`, `; do` is code); or when it has fewer than six plain words, or fewer than two for each code-like one. So a sentence of theirs that ends "if the review passes you can merge with --squash" is a quote, and "run tacit rulings audit --recheck --push on the live store now" is not. One tolerance, because agents quoting them fix their typing: the same words in the same order where at most one word in four differs by one edit, a swap of two letters counting as one (two edits in a word of eight letters or more), never in a word under four letters, a number, a negation or a changed first letter, and never a word added, dropped or moved (`--strict` turns it off). A match counts only as a statement of theirs: not inside a question the owner asked (its sentence ends in a question mark and opens with a question word or with the words themselves) and not right after a negation of theirs ("never", "not", "dont" ... within three words, same sentence).

**Enough to be the rule.** A quote proves the fact is their ruling when it holds most (three fifths) of the content words of the fact's description, or has six words or more and shares one content word with the description or the fact's name (stopwords out, words cut to four letters; `ownerwords.ProvesRuling`). Length alone proves nothing. Six words of theirs with none of the rule's words ("this is not the place for old history" under an agent's cleanup checklist) are their words in the fact, not its rule. On 2026-10-11 this sent 7 of 29 paraphrased rulings of theirs to observed, with their words recorded: their quotes share no word with the rule as the agent wrote it, so no overlap gate keeps them and keeps an agent's lesson off. A request is never a rule (`ownerwords.Request`): a quote that opens with "can/could/would you", "please", "show me" or "give me", or with "i need/want" and a thing to be done ("i need the dashboard to show errors"), and holds no rule word (never, always, dont, only, must, should, every) and no condition (not, before, after, until, unless, any, if ...: "i need the tests to pass before any merge" is a standing condition, not a task). A quote the ledger holds that no longer passes stays their words, also once their transcript is gone. A shorter phrase of theirs ("what should we try next", a session's name) is theirs but may not be the rule the fact states, and so is a run of six of their words inside a quote whose rest an agent reworded: those facts carry their words as evidence (Their words) and stay agents' statements.

**The owner's words.** A fact with words of theirs too few to prove a ruling is `source.kind: observed` with `source.owner_words` (the phrase, which the fact holds) and `source.owner_words_from` (where, as for a quote), and a quote ledger entry marked `"words": true`. A words entry never backs an `owner_quote` (its key differs), so moving the phrase into `owner_quote` makes no ruling; L15 requires the entry, that the fact holds the phrase, and the pair. The words count (`fact.OwnerWordsOf`) only when the store backs them and no standing Not mine of theirs answers the fact. The verifier gets them as `owner_words` on the fact with the rule that they are strong evidence: it judges the fact like any other but never retires it against them; when the sources truly conflict with their words it asks them (mark `owner`), and their words alone are never a reason to ask. A mark that would retire such a fact (keep the other side of a pair, retire on a stale check) becomes a question for them ("You said "...". An agent reads B as the current one; do your words still hold?"), and so does `query` on a pair with such a fact (conflicts_with lets delivery drop one side); a mark that neither retires it nor marks it conflicting lands. No other agent path retires it without them: the curator's judge never supersedes it (its "supersedes" becomes a `supersedes? ... owner decides` line; the index carries a `words` column for this), and `tacit resolve` refuses to supersede, mark or clear it. A fact taken off kind user with no words of theirs found is a plain observation, guarded by nothing. `tacit resolve`, which agents can run, refuses to supersede, mark or clear a ruling or a fact with words of theirs: only the owner changes those, in tacit app or the review page.

**In their task.** A ruling proved by a quote that is an instruction inside the task at hand ("lets create the bucket as a draft", "set the cli to run on the staging region", "1. drop it 3. fix it") is still their ruling: kind user, their words, guarded by everything above, and lint L15 and the verifier treat it as before. Only delivery treats it differently (Delivery): at the prompt it is an ordinary fact (no `RULE` label, no rule slot), and at session start it comes after the owner rules and before repo and machine facts. The quote is in its task (`ownerwords.InTask`) when it opens with a task verb or a reply (yes, yea, yeah, ok, okay, lets, first, now, do, check, open, update, remove, try, use, go, continue, run, fix, push, merge, add, make, create, set, change, clean, empty, review, scan, solve, or "you can", "i approve"; a leading so, and or plus is skipped), is a numbered answer (one item such as "1. ", "2) " or "3- " at its start, two such items anywhere, or two single digits), holds a question mark or the word "im", and holds no word that generalizes it (if, when, whenever, before, after, unless, until, any, every, some, something, anything, problem, way, general, always, never, dont or "do not", ever, instead, rather, better, prefer). The words are read normalized (Verbatim, above). A rule they wrote in tacit app (`source.harness: human`) is never in its task. The index stores the mark (`intask`, index schema 8). The lists were derived on half of 283 rulings the curator kept on the author's store, labelled by a judge; on the other half the rule marks 25 of 89 one-off instructions and 2 of 51 standing rules (eval/VALUE.md, "In-task rulings").

**The audit.** `tacit rulings audit [--dry-run] [--strict] [--recheck] [--digests DIR] [--digests-only] [--sample N] [--json FILE]` reads every curated fact the old definition treated as a ruling (`source.kind: user` or `type: user_standard`) and every fact that carries evidence (their words included), except a statement, and decides it, no model: written by them, kept; a quote that proves the rule, kept with `owner_quote` and `owner_quote_from` (and `endorsed` when the owner also kept it) and a ledger entry; their decision found, kept with `endorsed`; a short quote, `source.kind: observed` with `owner_words` and a words ledger entry; otherwise `source.kind: observed`, type unchanged, evidence fields cleared. It puts nothing to them: the report says "put to them: 0; pending: 0", and the marker lists no facts. A marker an older audit wrote with a pending list is carried forward, then rewritten without it: every fact on the list is a candidate again whatever its type, and a short quote it recorded (the quote and where) becomes the fact's `owner_words` with a words ledger entry (turn hash `pending-list`) when no other words of theirs are found, since it is the only record once their transcript is gone. An observed standard with their words becomes kind user. Only the `source` block changes (`fact.PatchSource`), so `updated` and the body stay. A real run writes the facts, the ledger and the marker through the curator's locked write (`curatorWrite`: lock, sync, plan on the fresh clone, refuse a file with uncommitted changes, lint, write, `MEMORY.md` without facts the clone does not track, lint again, one named commit as curator, files put back on any failure, a lost push race plans again); a dry run reads the clone as it is and never syncs. A quote (or words) the ledger holds stands without a new lookup; `--recheck` looks it up again. The ledger merges by union (`.gitattributes`, each union line checked on its own by `ensureAttributes`), like the decision log. A second run changes nothing. It never runs on an empty corpus: when none of their turns can be read, it refuses (fail closed). A statement (Statements) is never a candidate: code wrote it from their verified words with its words line, and it is their words said once, never a ruling. Its body quotes those words, so as a candidate they proved it a ruling (kind user, `owner_quote` in place of `owner_words`), which lint L20 refuses, and the audit wrote nothing; only the statements step's ladder promotes a statement, into a new fact.

**The curator.** The split and the rulings pass ask for `owner_quote`, their words exactly as the note gives them (at least six words), and say that an agent's reading is observed. A dreamed ruling carries their words for this check: the dreamer returns the owner's exact words from the `U:` line (`quote`), and the note's body ends with `Quoted from the session: "..."` (a list of parts is joined with ellipses, a quote over 700 bytes is cut at a word, a double quote inside becomes ”): the dreamer's claim, not an attribution, until the check below; a quote the model made up is still found in no turn of theirs and the ruling is filed as observed. The window is redacted before the model sees it, so a quote can only repeat redacted text; a quote that holds a redaction mask matches no raw turn of theirs, and that ruling is filed as observed by design. The client keeps a `kind: user` entry only when a quote (the entry's, or a phrase of its text) is in the note it came from, proves the rule, and is theirs: a note the app added for them (their blockquoted lines; the app's template around them is not theirs), or a statement in their turns (the note's session first). The quote goes into the fact's text if the model left it out, and into the ledger. Anything else is written as observed (`not_owner_words` in the run's report). When their words cannot be read (no transcripts on this machine, a source that fails to load), the run curates no note: it fails and leaves them pending.

**Repos a fact is tied to.** The curator does not rewrite a fact's repos itself. A dreamer note is filed only under a repository repoid finds (a real git root, Scopes), so a notes or memory directory a session ran in is no project scope; and an entry whose `applies_to.repos` names something that is no repository (a folder name, a path, a URL, `org/name`) or whose scope names no known repository is refused by the metadata checks and sent back to the model once with the problem (Metadata checks), which fixes it or leaves the batch to be split as for any invalid answer.

**Invalid answers.** A batch whose split or rulings answer is malformed or invalid (an entry that fails validation, an origin outside the batch, an unbacked ruling on a machine with no owner history) is split in two, and both halves are curated in the same run; a runner or transport error is not split. Each entry that fails validation is logged, one line per entry and field, on stderr and in the run's report line in `curator.log` (`invalid_entries`: `split: entry 11: scope: has upper-case letters`): the field and the rule it broke, never the entry's text; an `applies_to` key other than `paths`, `symbols`, `repos`, `hosts` and `commands` is named `<unknown key>`. A scope whose repo or host is in capitals (`projects/ElmoRipData`) is not a failure: the curator lower-cases it (A-Z only, so no other letter can turn into a slug), as the dreamer and delivery do (Scopes), since delivery asks only for `projects/<lower-case repo>`. A note that fails alone stays pending. It counts against the note in `~/.local/state/tacit/curator.json` (`failed`, per note) only in a run where another batch got a valid answer, and never for an unbacked ruling with no owner history; a run with no valid answer after 8 splits stops splitting and counts nothing (the model or the runner is failing, not the notes). A note counted in 3 runs is set aside: it is not batched again until `tacit curate --retry-set-aside`, and the run's report says how many (`set_aside`). A note the model answers clears its count. `--max-batches` caps the batches a run starts; the halves of a split batch do not count against it, and a run makes at most 8 splits per batch it may start. A note that is the only one pending and fails is not counted (no other batch answered), so it costs one call per run (two when the answer goes back once); an unbacked ruling with no owner history is isolated again in each run until the history is here.

**The owner's notes that disown facts.** An owner note the app added whose own words say a fact is not theirs ("not owner wording", "non owner rulings", "not my rule", "interpretation of agents"; not when a negation of theirs comes right before the phrase: "these are my words, not an interpretation of agents") is not split into facts. It is about one fact, or the facts its finding marks: the facts their words name; else the one fact of a single finding (a stale check, a dead link); else, on a pair, the side their answer marked (keep A, retire B: B; neither, conflicting or both true: both); a note with no answer on a pair names no side. Each curator run, before the link step, sets those facts to `source.kind: observed` and clears their evidence, their words included (`curateDisowned`, the same locked write, commit `curator: N fact(s) the owner says are not their words ...`). The later of their words wins: a note over an older keep or This is mine, a keep or This is mine over an older note (the note's time is its adding commit's). A fact the owner wrote themself stays theirs.

**Rollout.** Install this client on every machine first: an older client decodes frontmatter strictly and drops every fact that carries `owner_quote`, `owner_quote_from`, `endorsed`, `owner_words` or `owner_words_from`. It changes nothing by itself (no marker, old definition). Then run `tacit rulings audit --dry-run`, review it, and run it for real; every client switches at its next sync.

**Import.** A memory its system files as the owner's (a Claude `feedback` memory, a Codex user preference or profile) is kind user only when one of its quoted phrases is a statement of theirs that proves the rule (the same checks, the memory's session first); otherwise observed. Without their words readable, nothing is imported.

## Statements

Something the owner said once, where it is not sure to be a standing rule (a choice about a name, a plan or a design for the matter at hand, a remark that something is so, an instruction that may hold only for now), is a statement: their words verbatim, the day, the session and one line of context saying what was being discussed. It is strong but soft evidence: never a rule and never a `RULE` line, and an agent never changes it; Opus weighs it and must say why when it goes against it. It replaces the observed fact with their words that an uncertain one-off used to be.

**Capture.** The dreamer marks such words kind `statement` with `quote`, `context` and `relevance` (below; dreamer prompt v8, and v9 with the held list); the note's body ends `Quoted from the session: "..." Said once; context: ...`. The split's entry of kind `statement` carries `owner_quote` and `context`; code keeps it when the words are in the note and are a statement of theirs in their own turns (as for a ruling, the note's session first), and writes the fact: type `statement`, `source.kind: observed`, `owner_words` and `owner_words_from` with a words ledger line, `created` the day they said it, the description the context, and the body

    You said once (2026-10-21): "<their words>"
    Context: <what was being discussed>
    Gloss (the curator's reading, not your words): <the model's reading>

In a store of format 1 the words stay on an observed fact as before. With the local layer statements are written in the overlay whatever the store's format and never leave the machine.

**The day they said it.** A statement's day (its body's first line and its `created`) is the day of the owner's turn that holds the words, never the day a step read the session or wrote the fact: in a rebuild those are the run's days, weeks after the words. Code reads the turn's time from its source (`ownerwords.Corpus.SaidAt`: a Claude Code, Codex or pi line's `timestamp`, a prompt history's, a Hermes row's), in the session the words line names, the turn whose hash it recorded first, else the earliest turn of that session that holds them as a statement of theirs; only when that session holds none (its transcript is gone, or the words are in a resumed or forked copy) is it the earliest such turn anywhere. The day is this machine's (local time). It is recorded with the words line as `said` (`ledger.Quote.Said`; the line's `at` is when the line was written): the split's statements and one-offs, the reviewer's trims (the day of the message they typed), `tacit rulings one-offs`, a decision the statements step makes (its newest statement's day), and the audit's quote and words lines. With no turn time (a digest, a note they wrote in the app) the day is the note's, as before; a day after the write is no day they said it and is not taken. A statement already written with another day is corrected, idempotently: the statements step corrects one whose day disagrees with its words line's `said` (the ledger only, no transcript); `tacit rulings one-offs` also looks up the turn for a words line that records no `said`, appends the line again with it (the ledger keeps the last line of a key), and corrects the statement (its `--dry-run` reports them: `redated`, `redated_ledger_lines`, `redates`). A correction changes only the day on the first line and `created` (`fact.RedateStatement`; the words, the context, the gloss and a check's flag lines stay, `updated` is set) and logs a `redated` line in `review/statements.jsonl` saying from what day to what, and why. The step reads a statement with its corrected day, so which statement is the earlier one, and which changes which, follows the days they said them.

**The step.** `tacit statements [--model M] [--dry-run] [--max-runtime D]`, also a step of the full curate after the batches and before the assessment: the curator's model reads each new statement once, in batches of 8, with the earlier statements and decisions code found that share two content words or a folder name with it (at most 6): whether it is a choice or a standing instruction, which earlier items make the same point or the same point changed, and the dry claims its words make (canonical, exists, absent, renamed, path, version). It reads the same way, once, every live ruling whose words name a repository with a naming question (another name of a checkout, or a checkout known by other names). A refused answer goes back once. No batch starts when less than 10 minutes are left before the run's deadline (`--max-runtime`, default 1 hour, alone; the curate run's budget inside it): what was judged is written, and the statements not read wait for the next run (`left for the next run`). Code checks the claims and decides, by these rules alone (`statement.Plan`):

- The same point said again in a separate session: a choice becomes a decision; a standing instruction becomes a preference, and the third session a rule (the one-off ladder).
- Said once, and a check holds for its claims and none fails: a decision.
- A check that fails flags it: a line `> check disagrees <day>: <the check>` is appended to its body (nothing above it changes), delivery says "(a check disagrees, maybe misread)", and `review/<date>-statements.md` gets an optional `check?` item (`outcome=misread`): nothing waits on the owner's answer. The same check output flags a statement once. A flagged statement is not left for the owner: the step reads it again with the disagreeing check shown (the reading may have misread the words), the run after the flag and then weekly while a check still disagrees with its reading's claims; a new reading whose claims a check confirms promotes it as above.
- A newer statement that changes an earlier statement's point supersedes it. A decision or rule changes only by a newer confirmed one (the changed point promoted, which replaces it) or by a check; a statement that differs from one that stands is an optional item (`outcome=differs`). A statement that makes a decision's or ruling's point again stands for it (superseded into it).

A decision or rule code makes is kind user with the newest statement's words as `owner_quote` and its ledger line (a preference keeps them as `owner_words`), its body `You decided (<day>): "<words>"`, the context, and how it was made (`said in 2 separate sessions`, or `a check agrees: <the check>`); the statements it rests on get `superseded_by`. Every judgement, promotion, supersession and flag is a line of `review/statements.jsonl` (the overlay's with the local layer).

**Relevance.** The owner, 2026-10-25: "not every sentence of me is statement. if it has some relevancy, great, if not, drop it". Wherever their words would become a statement or a ruling (the dreamer's capture, the split, the reviewer's trim to their statement, `tacit rulings one-offs`), the deciding model also judges whether the remark would matter to future work, `relevance`: `keep` with `instruction`, `decision`, `preference`, `fact` (about a project, a machine or the world) or `correction`, or drop with `acknowledgement` ("ok", "go", "check", "yes do it"), `question` (a passing one), `frustration`, `steering` (one-time task steering: "run it again", "now push") or `other`, and a reason (`client/internal/relevance`). Code keeps a remark only with a keep category and a reason; a keep without them is refused (not kept), and code still checks the words are the owner's. A dropped remark is not curated: the dreamer writes no note of it (the run's `owner_remarks_dropped`), the split files no fact of the entry (the report's `owner_remarks_dropped`, its note marked done and kept in the inbox), the reviewer makes no statement of it (the claims resting on it are removed, basis `dropped`; with nothing else kept the note stays uncertain, the judgement on its line), and `tacit rulings one-offs` retires the ruling (a `dropped` line in `review/statements.jsonl`: its words, the category, the reason). The rulings pass of the split is told which entries were dropped, so it does not recover them.

**One-offs.** The owner, 2026-10-25: "not everything I say needs to become a rule". A ruling resting on words they said in one session is their statement, scoped to its moment. Code counts the sessions (`ownerwords.Corpus.SaidIn`): those whose turns hold the quote as a statement of theirs (exact, or a typo of theirs the quote corrected; not a question, not negated), a prompt history line with no session not counted, nor a turn word for word the same as one counted already (a resumed, forked or imported copy). In the split, a ruling `ApplyEvidence` kept whose words code finds in fewer than two sessions becomes their statement (`curate.OneOff`: type `statement`, their words, the entry's context, the model's text as the gloss; the report's `one_offs`); one they wrote in the app stays theirs. On a store curated before this, `tacit rulings one-offs [--dry-run] [--json F]` runs the relevance gate on each such live ruling (Opus, batches of 20, `--batch`, `--jobs`; the prompt shows their words, the whole turn code finds them in, the rule an agent made of them, its scope and day) and writes each kept one as their statement (`<name>-said-once`, the ruling's description as the context, its text as the gloss) that the ruling points to (`superseded_by`, never deleted), and retires each dropped one, in one curator commit; the model is asked before the write takes the store, and a judgement the model did not give, or one code refused, leaves the ruling for the next run. `--verdicts F` takes an earlier report's judgements of the same rulings on the same words (a dry run's, so the write pays nothing again); `--found F --dry-run` takes the sessions and turns from an earlier report instead of this machine's transcripts (to judge on another machine); `--no-gate --dry-run` finds only. It leaves a ruling said in two sessions or more, one they wrote in the app or endorsed, and one the statements step promoted. Only the ladder above makes a decision, a preference or a rule of a statement again.

**Folder records.** A statement that names a folder or its alias is evidence in the assessment (`owner's statement, said once (...)`). A decision code made of statements, or a ruling the step read, whose canonical claim names a folder is the owner's decision on its name (Planned renames); the words of a live ruling or decision that the ledger backs may be a decision's `owner_quote` without this machine's history.

## Derived facts

`tacit curate` runs a git pass after its inbox batches, and `tacit derive` runs it alone. No model is called. For each repo that has a live curated `projects/<repo>` scope (at least one non-inbox, non-superseded fact) and a checkout at `~/projects/<repo>` (its own `.git`, file or directory), the curator writes two facts under `derived/<repo>/`, as `curator`, with `source.kind: derived` and `derived_from: <12 characters of the commit it was read at>`:

- `<repo>-hot-spots` (type `hot_spot`): the 10 code files touched by the most commits in the last 400 code-touching, non-merge commits, each with its commit count, its last-touch date and up to 3 co-change partners (files in the same commit at least 3 times and in at least half of this file's commits). A file needs 3 commits to count. Commits that touch more than 30 code files are not counted. No fact is written when no file reaches 3 commits.
- `<repo>-module-map` (type `structure`): one line per directory with its file count, code file count, most common extensions, the number of window commits that touched code in it, and the date of its last change; plus the root files. The top-level directories are opened into subdirectories, code-rich ones first, until the map holds 30 lines. A directory is opened only if it is mostly code, most of that code is below it, and it has two or more subdirectories. No fact is written when the map has fewer than two lines.

Code is a fixed allowlist of extensions and build file names (`client/internal/derive/code.go`); data, logs, lockfiles, prose, vendored and generated paths are not counted. Blame age is not a fact of its own: line age in a young repo says little (memra is five weeks old, most repos here are under a year), and the actionable part, which module is dormant, is the last-change date on each module-map line.

Names are text chosen by whoever committed them, and a description is the line a hook prints into an agent's context. So a file or directory name is written into a fact only if it matches `[A-Za-z0-9._@+=,~-]` per component (components up to 100 characters, no spaces, quotes, colons, brackets or non-ASCII) and does not match the server's secret scan. Other names are left out and counted in the body ("N files ... are not shown"). README prose is not copied either.

Which commit. The branch the machine's config names for the repo, else the remote default branch of the checkout (`origin/HEAD`'s target, else `origin/main`, else `origin/master`), so that a feature branch that happens to be checked out never becomes a shared fact. With none of those (no remote, never fetched) the checkout's HEAD, and the body then says which branch ("no remote default branch found"). A branch name is written into a body only if it passes the same conservative character set and length bound as a path; otherwise the body says "branch name not shown", and an `origin/HEAD` pointing at such a name is not taken as the default. The body always names the ref, the commit and the commit's date ("read at commit b1bbd74f287f of 2026-10-05"), so a stale read shows.

The config is `~/.config/tacit/derive.yaml` (or `$TACIT_DERIVE_CONFIG`), written by `tacit derive --set-branch <repo>=<branch>` (empty branch removes the entry) and read by `tacit derive` and `tacit curate`:

```yaml
branches:
  sglang: dev
ordinary_names: [atlas, beacon]
```

`ordinary_names` lists repo names that are also plain words. gitev counts such a name as the repo a fact is about only when the fact's scope or `applies_to` names it, or its text mentions it three times or more (see Git evidence). A built-in set (`tools`, `tacit`, `docs`, `web`, `api`, `app`, `site`, `notes`) always applies; the list adds to it. `--set-branch` keeps it.

A configured branch is read at `origin/<branch>`, else at a local branch of that name, else the run falls back to the default and says the branch was not found. A file that does not parse (unknown key, a branch name that could be an option) stops the step. The case that made it: a fork whose `main` mirrors upstream and whose `dev` is the production tree (main plus the carried patches), so the useful facts are dev's. Set with `tacit derive --set-branch sglang=dev`.

Fresh reads. Before reading a repo, a real run of `tacit derive` or `tacit curate` (not `--dry-run`, not `--out`, not `curate --dry-run`, which use the network and move no ref) runs `git fetch --no-tags origin +refs/heads/<branch>:refs/remotes/origin/<branch>` in the checkout (`--no-fetch` skips it). It moves that one remote-tracking ref and nothing else: not the working tree, not a local branch, not HEAD, not FETCH_HEAD, no tags, no gc, no commit-graph. The timeout is 30 seconds: on the workstation at load 40 one branch with a few days of commits took 1.1 s (valkey-glide), 2.0 s (sglang dev), 2.6 s (memra) and 9.9 s (sglang main, the busiest), so 30 s is three times the worst and a dead link costs half a minute, not the three minutes a repo is otherwise allowed. A failed fetch leaves the ref as it was (git moves it only after the objects arrived), the read falls back to it, and the run report says "fetching origin/<branch> failed". After three failures in a row the other repos are not fetched (a dead network would cost every repo the timeout) and the run says so. A checkout without an `origin` is not fetched and not reported. Whether the fetch worked is not written into the fact, which is a function of the commit read; the commit date in the body is what shows a stale read.

The facts are a function of that commit: dates are the commit's, the host is the curator's, and nothing depends on the clock. The same commit gives the same bytes, a repo whose commit did not move is not recomputed or rewritten, and a moved commit rewrites both files. A derived name that a curated fact already uses, or that another repo's name slugs to, or a file already at the path that is not a generated fact, is skipped and reported on every run.

Who owns a repo's derived facts. The host that produced them (`source.host`). Another host does not rewrite or retire them unless run with `--take-over`, so a Mac with three checkouts cannot delete the workstation's 39 or flip the facts of a repo both have.

Retiring. When a repo loses its `projects/<repo>` scope or its checkout, the generated files under `derived/<repo>/` are removed (an exception to supersede, never delete, like a stale folder overview: Overviews), by the host that produced them. Nothing is retired when no checkout can be found at all (an unmounted projects directory), on a partial run (`--repo`), or when a `projects/` or `derived/` fact does not parse (the scope may only look gone); unparsable facts are reported.

Writing. The facts are computed in memory; nothing touches the clone until the store lock is held. "Unchanged" is decided against what the server has (`origin/main`), not the working tree. Under the lock the step syncs, removes the generated facts a killed run left under `derived/` (and restores generated ones it changed) and puts `MEMORY.md` back to what is committed; a file there that is not a generated fact, committed or not, is never touched; writes what still differs, regenerates `MEMORY.md`, lints, and pushes once with `CommitPushOnceLocked`; a push that lost a race starts the locked part over. On any failure (cancelled context, a push error that is not a refusal, a linter that cannot run) the clone is put back exactly and any local commit dropped. A lint finding on a file this run wrote drops that repo. When the server refuses the push, the repos its lines name (`tacit: derived/<repo>/<file> looks like it contains a secret`) are dropped and reported with those lines, and the rest go in one commit again; a refusal that names no repo halves the set and pushes the halves. One bad repo costs one extra push, not one per repo, so the store lock is not held for minutes.

Numbers (window, changeset limit, thresholds, caps) and the evidence for each are in `client/internal/derive/analyze.go` and `eval/VALUE.md`.

## Results from git

`tacit curate` runs a results pass after the derived-facts pass, and `tacit results` runs it alone. No model is called. Git is often more correct than what an agent saved for a measured number, and a newer commit often replaces an older result that a saved fact still quotes. The pass reads the results committed to the repos that have a live `projects/<repo>` scope and a checkout (the same repos, the same branch and the same refs as the derived facts; it fetches nothing, `tacit derive` does), turns them into `result` facts that carry the commit, and flags the saved facts that quote a value a newer commit replaced.

What is read. Files touched by at least two of the repo's newest 6000 non-merge commits, of three kinds, each read in its newest version first and only then through up to 40 older versions:

- **Row logs** (`.jsonl`, `.csv`, `.tsv`): columns are classified by what they are. A metric is a numeric column whose name says it is a measured quantity (tok/s, throughput, latency, ttft, p50 to p99, accept, accuracy, f1, score, speedup, cost and the like; a counter such as `accept_n` is not). The setup is the string, small-integer and boolean columns that repeat (`cell`, `profile`, `arm`, `concurrency`). A time column (`ts`, `date`) orders the rows and a code column (`git`, `commit`) says what was measured. A row that its own `window_clean`, `valid` or `ok` column marks false, or its `error` column marks true, is not a result. A row log needs the row's own timestamp: rows without one are samples (per-request timings) and make no series. Rows of one setup are one run only when they share a full timestamp (a date alone is not one) and the same code; those become one point, their median, and the fact says how many rows it is. A column that counts runs is read as a count, and a file of per-item rows (a list of items, cases or samples) never makes a median: rows that share a run's timestamp but differ in what they say besides their numbers make no series. Runs are ordered by their time, and runs with the same time (a bare date) stay in the order of the file. Rows that each have a time of their own are one quantity measured again even when a column (an id, a note) is unique to each row; a per-request log with such a column is therefore read as a series.
- **Boards** (`.json`): every numeric leaf whose key path says it is a measured quantity; array elements are named by their `id`, `name`, `model` or similar field, and an object whose entries are all objects (three or more) or all numbers (two or more) under names that are not metrics is a table keyed by its entries (`scenarios.<name>.stages_ms.<stage>`). Not read: names that say a setting rather than a measurement (`timeout`, `deadline`, `budget`, `interval`, `window`, `expected`, `threshold`, `limit`, `target`, `lease`, a count or an id); the statistics that describe a number's uncertainty (`ci*`, `lower`, `upper`, `*_lower`, `*_upper`, `one_sided_*`, `delta*`, `stderr`, `std`, `p_value`); anything under per-item or per-slice records (`items`, `cases`, `samples`, `slices`, `per_task*`, `per_item*`, `per_slice*`) and `stages_ms`, which hold one item's score or a CI gate and not the result of a run; files named `*baseline*` or `*parity*`; and `analytics/`, `telemetry/` and vendored directories.
- **Tables** (`.md`): every table whose numeric columns carry a unit or a metric name; a row is its first text column (a repeated label drops the rows it names), a column is its header. A cell that is a range, an arrow or prose is not a number, and a cell whose unit disagrees with its header's is skipped.

A series is one measured quantity for one setup in one file. A setup (or a log row) that the file's newest version no longer holds is dropped, so a renamed column never leaves its last value standing as current. Its points are the values it held, each with the commit that wrote it (for a log row, the commit that first held that line; for a board or a table, the commit that changed the cell), the row's own timestamp and code reference where it has them, and the source line. A number written with seven or more decimals is shown with four significant digits and the raw text in brackets. Names, labels and setup values come from the repo and end up in a file a hook may read, so each must be one line of at most 60 characters with none of the characters that make a link, a code span, a quote or markup; a row that fails is left out. Every string from the repo is passed through `digest.RedactAll` (one call per repo) before anything is built from it: the file name, `applies_to`, description and body are made from the redacted strings, and only then stripped and clipped, so a clip never cuts a secret in two and a secret shaped like `password: x` is masked before it becomes part of a name. If redaction fails there is no fact.

A git read that fails is never a reason to retire a fact. A history read that errors, times out, returns a blob that is not the one asked for, or is cut short by a size budget marks the repo. With an error or a timeout the repo is reported failed: nothing is written and nothing is removed for it. With a budget cut the facts that were read are written and none is removed. Only a complete read may remove a fact whose series left the history.

What becomes a fact. Series are grouped by file and metric (a log), table (a document) or schema path (a board), and a group becomes one fact `derived/<repo>/<repo>-results-<file>-<group>-<hash>.md` with `source.kind: derived`, `created` and `updated` the newest commit date among its rows, and `derived_from` the commit that wrote the newest row (not the repo HEAD, so a repo whose results did not change gets a byte-identical fact and no commit). Only rows that recur (the series held two different values) or that a curated fact quotes are shown, at most 20 per fact, and at most 24 facts per repo: the repo's derived scope also holds the hot-spot and module-map facts and the prompt hook ranks it for one line, so many result files must not bury them. The cut keeps the groups a saved fact quotes, then the ones with more rows, then the newest.

The type says whether a hook may print the fact. Type `result` is a row log, a table or board group that a curated fact quotes, or one that a saved fact was retired in favour of (its `superseded_by` points at the result fact: accepting a flag retires the saved fact, and the replacement must not leave the hook with it). Type `result_ref` is every other group: `tacit search` and the MCP tool find it, the prompt hook does not print it. The description is made only from the file name, the metric (a name of at most four parts, else the unit), a count, a date and, when the row's label is a cell id, one row and its number: `<repo> <file>: <metric> for N setups, newest <date>`, then `; <label> <value> <unit>`. The row is the fact's first row, which is a row a curated fact quotes if there is one and otherwise the one whose value changed most recently; it is not chosen for the prompt, the hook prints the stored line. A cell id is one to three tokens of up to three alphanumeric parts joined by `-`, `_` or `.` with an optional `key=` prefix, each token holding a `=`, a digit or a separator, at least one digit in all, optionally followed by ` / column` for a table row (`cell=26b-spec-d1736 profile=balanced`, `frtrim27-mixed / tok/s`). Any other label stays in the body. No free text of the repo reaches the line a hook prints beyond that, the file name and the metric.

A row line gives the setup, the value with its unit, the basis, the commit that wrote it, the date, the code it measured (a log), the source line (`file:line`, or the JSON path), what it replaced and, for a log, the span of its last three values. Line numbers are those of the file at the commit the body names ("as the file stands at commit X", the newest commit that touched the file). The commit on a row is the one that first held that value, and the file may have been numbered differently then. The basis is what the file says: `median of N rows of one run (one timestamp, one code)`; `single run (the file says so)` only where the file has a run count of one; `N runs, how they are summarised is not stated`; otherwise `run count not stated` (a lone log row is `run count not stated (one row)`). A newer commit rewrites the same fact (the name depends on file and group only), so the store ends with the newer result and the store's own history keeps the older. A fact whose series left the repo's history is removed like a derived fact, unless a saved fact points at it with `superseded_by` or `conflicts_with`.

Which saved facts are flagged. A curated, non-superseded, non-derived fact (inbox notes are not delivered and are not checked) of a type that makes claims (a `history`, `past_mistake` or `code_change` fact records what happened and is never flagged) quotes a row when a number it states equals a value the row held, at the precision the fact wrote it, with at least three significant digits (a number of one or two digits is in every note); the unit written after the number is the row's unit; and the words that tell the row from the other rows of its group (its setup tokens) are in the fact: 60 percent of them, two at least (a row told from the others by one word is not matched); a ratio or score with no unit needs all of them. A whole number's trailing zeros do not count as digits (200, 480 and 1,000 are round figures), and a whole number cannot stand for a value that has decimals unless it has four digits. A number that sits in a bound is not a claim about what was measured: "must stay above 138.5 tok/s", "target 200", "a 1000 ms p95 bar", "at least 40" are skipped. All the numbers a fact states for a row are weighed together: if any of them is the current value ("went from 138.5 to 161.3", "161.3 now, was 138.5") the row is named by it and the fact is kept as it is. If it quotes only a value that was replaced, the fact is flagged when the difference to the current value is more than 1 percent and, for a log, outside the noise band of the new state (the replacing point and everything after it). Noise needs a sample to be called noise: under three points there is none, so 5 percent stands in for it (perf-ci's GPU cells move 2 to 5 percent between runs of the same code); with three or four points the band is the larger of 2 percent and half the observed range; from five points, the larger of 2 percent and three times the median absolute deviation. A flag also needs that the fact was not written before that value was recorded (a week of slack), and that the sentence around the number carries no date on or before the day it was replaced, since a fact that dates its number is a record and not a claim about now. A curator fact's dates are the day it was filed, not the day it was true, so a flag never says that a fact was wrong when saved.

A flag is a line in a review file the step owns whole, one per repo: `review/<date>-results-<repo>.md`, rewritten with the lines it already holds plus the new ones. `- result-superseded? [[<result fact>]] may replace [[<saved fact>]] - quotes ...`, with the quoted value, the commit that recorded it, the commit that replaced it and the value now. The file goes in the repo's own write, so a repo that failed or was cut gets no flag, and a repo the server refuses or the linter drops loses its review lines with it. The review page reads a line as a pair, A the saved fact and B the result fact, kind `result-superseded`, and the verifier is told to check that A names the same setup and quantity as B's row. B is generated and the next run rewrites it, so the page offers only the marks that leave B alone (retire A in favour of B, or keep both) and never one that patches B. A pair already in any review file is not raised again, whatever was answered. The step never retires a fact. A saved fact that is an owner ruling (`source.kind: user` or type `user_standard`) is put to the owner as `- RULING CHANGE? new [[<result fact>]] may supersede owner ruling [[<ruling>]]` and nothing else: the committer of a results file is usually an agent, so a commit is evidence of what was recorded, never a ruling.

Cost. A repo's read is cached by the commit it was read at, under `~/.cache/tacit/results` (or `$XDG_CACHE_HOME`), so a repo whose HEAD has not moved costs a cache read and one redaction call. Measured 2026-10-10 on the workstation at a load of 60 to 100, `nice -n 19`: every checked-out repo 34 s cold and 11 s warm, with identical output; one repo 2.4 to 2.8 s warm, against 34.5 s for `tacit derive --dry-run --out` over all repos.

Delivery is the derived facts' (see Delivery): the prompt hook's second query over `derived/<repo>`, at most one line, marked `(computed from git)`, only for type `result`, never SessionStart; `tacit search` and the MCP tool find both types. The host that produced a repo's result facts is the only one that rewrites or removes them (`--take-over` overrides). The write path is `tacit derive`'s: computed in memory, then under the store lock after a sync, written, linted, pushed once, with a refusal dropping only the repo it names.
## Staleness check

`tacit curate` runs it last, after the derived-facts step and the run's state, also when no inbox note is pending, and `tacit stale` runs it alone (`--dry-run` reads and prints, syncs and writes nothing). No model is called, and it never changes a fact: it writes findings. A fact git has overtaken is a question for the verifier or the owner, not a decision.

**Candidates.** Every curated fact that is not superseded, not retired, not under `derived/`, and has no unanswered stale finding. They are taken least recently checked first: each machine keeps a cursor in `~/.local/state/tacit/stale.json` (fact name, time of its last finished check), and a run reads git for at most `--budget` (45 minutes in `curate`); the facts it did not reach come first the next time. A fact whose read did not finish (a command timed out, a file list or a search was cut, the branch could not be read) flags nothing and is not marked checked; it is retried the next day (20 hours), then every 2nd, 4th and 7th day, so one that never finishes costs a seventh of a run, not all of it. `tacit stale --fact NAME` ignores the wait.

**Date.** A fact is current as of its effective date (`gitev.Builder.Effective`, the timeline's own dating): the date its text says it is from, else its source note's date, else `created`; moved forward by an `updated` day that differs from `created`, and by the day of its last store commit when the file was committed more than once. A curator fact filed in October from a note written in May is current as of May: the filing was a rewrite, not a check against git. Commits count from the end of that day; after a "still true" mark, from the instant of the mark.

**Rule.** gitev reads the fact's subject (see Git evidence) in the repos it names, each at the branch `derive` reads it at (`~/.config/tacit/derive.yaml`, else the remote default branch; HEAD only for a repo with no remote), not at whatever the checkout has out; the remote-tracking refs are the ones the derived-facts step has just fetched, and `tacit stale` by hand does not fetch. Of the fact's identifiers only specific ones are searched: a flag, or a name with an underscore, hyphen, scope, dot or digit in it, or capitals inside it (`gitev.Specific`); a plain word such as `suspended` never is. A fact is flagged when, at or after its date, something it names was deleted:

- a path it names is held by no repo read and a commit touched it (deleted or renamed): the newest commit that touched the path is read directly, so the others around it cannot hide it, or
- a commit removed or rewrote a line holding an identifier it names (a line the same commit adds back unchanged elsewhere only moved) and no repo read holds that identifier at HEAD any more (a rename leaves the old name nowhere). Only names that are gone are searched for in history, so the commit that removed one is among the few that touch it.

"After its date" is the committer date, the date git's `--since` filters on and the day a commit reached the repo (a rebased or cherry-picked commit written earlier counts from when it landed).

Not flagged: a commit that only touches a file the fact names, one that only adds lines holding an identifier, a rewritten line whose identifier still stands at HEAD (a reworded doc, a refactor, a changed value), and any term found in 26 or more files at HEAD (gitev drops it). So a hot file does not flag its facts and a deleted name does. The first design flagged every changed line holding a name; hand-checked it was almost never a stale fact, while deletions were (numbers in eval/VALUE.md), so a changed line that leaves its name standing is not a trigger.

A read that failed, ran out of time or was cut (a file list, a search, or the diff of a commit that removed a name: it is read with `-G` so only the files that hold a gone name are in it, and one past 600 KB is incomplete) flags nothing, whatever else it found: a file list that failed says nothing about a path (it is neither present nor absent, as for an identifier whose search failed), and a cut search can miss the commit that did it. The fact is skipped as incomplete.

**Once per commit set.** The finding's key is its newest triggering commit. The same commit never makes a second finding. A fact with a finding nobody has answered (no mark, or an unanswered question) is not flagged again, however many commits follow: the page and the verifier read git fresh. An answered finding no longer holds the fact back: a "still true" mark moves the fact's date to the mark, and a deletion after it, of a name or a file, is a new event that flags again; an agent's `fix` that waits for the owner does not hold the check back either, and the new finding carries the old fix.

**Cap.** A run writes at most 60 findings (`--max`, the verifier's default batch per run), strongest first: most deleting commits, then newest, then name. The rest are found again next run and the report says how many were held.

**Finding.** A line in `review/<date>.md` with a few indented lines for a person; the first line is what the page and the verifier read back:

```
- stale? [[name]] (scope) @abc1234 n=3 since=2026-10-01
  commits count from 2026-10-01 (text); 3 deleted something the fact names
  2026-10-09 abc1234 memra: engine: rename FOO to BAR - FOO (gone at HEAD)
```

`@sha` is the newest triggering commit, `n` how many commits deleted something the fact names, `since` the day commits started to count. The newest finding of a fact is its finding; older ones are history. Its id is a hash of the kind, the fact and the sha.

**Marks.** In `review/decisions.jsonl` like every other finding: `current` (still true), `retire` (outdated per git: the fact gets `retired: <date>` and `updated`; reopen restores both exactly), `fix` (an agent: true, but a detail changed, and what), `ask` (an agent's question for the owner), `reopen`. A `fix` names the corrected detail and the detail it replaces (`was`, as the fact writes it); when the live fact, not a ruling, holds `was` word for word, the mark writes it as an in-place note (`> superseded <day>: <was> -> <fix>`, `updated` the day) in the same commit and the finding is applied. Otherwise a `fix` is closed when the fact file is committed after the verdict (the owner or the curator applied it), or when the owner marks the finding; applied, it dates the fact. A rotation commit (`curator: rotation: `) whose change to a fact's file is its `last_checked` stamp alone does not date the fact (`gitev`'s effective date skips it, checked on the change, as a link repair is): a stamp says the fact was looked at, not that it is new. A finding whose fact is already retired or replaced takes no mark and does not need the owner. An agent may make only `current`, `retire`, `fix` and `ask`, and none on a finding the owner marked or reopened or on a fact the owner kept in a pair. The page shows a stale finding as one galley with the two owner marks, why git flagged it, and the same "What git says" timeline the pairs have, read for one fact (`gitev.Builder.BuildOne`).

**Rulings.** A ruling (`fact.IsRuling`, see Rulings) can be stale too. It is flagged like any fact, `tacit verify` never sends it to a model, and whatever an agent marks on it (`retire`, `fix` or `current`) is turned into a question for the owner and nothing is written into the file. Only the owner retires a ruling.

**Verifier source directories.** The store is required. `TACIT_VERIFY_ROOTS` adds read-only source directories, separated like `PATH`; each must exist or the verifier fails before calling a model. Claude auto-memory for `$TACIT_PROJECTS` (default `~/projects`) is included when present; its absence does not block a fresh install.

**Verifier.** `tacit verify` takes stale findings after the pair findings, in batches of their own, with the fact, the commits that triggered it and the one-fact timeline as input. Its marks are `keep` (still true, recorded as `current`), `retire`, `fix` (needs the corrected detail) and `owner` (a question). Evidence is required for all but `owner`, as for pairs, and free text is redacted before it is stored.

**Attempts.** `tacit verify` sends a finding, pair or stale, at most 3 times without a verdict landing (`attempts.json` in the verifier's state directory, `~/.local/state/tacit/verify/`); then it is no longer sent. A call the model never ran (no cost and no timeout) and a batch whose answer could not be redacted count no attempt. Each counted failure records why (`failures.json`, mode 0600, the last one per finding, kept while the finding has a count; a reason goes through the redactor before it is kept, and one it cannot redact is not kept, and no reason, and no line a run prints (`--dry-run` prints the marks it would make, evidence and all), repeats a verdict's free text): the call's error, `no verdict came back for it`, a verdict this finding cannot take (a keep that names neither fact, an owner mark without a question, a fix without the fix, a mark of the other kind of finding such as `retire` on a pair), the mark the review page refused with its reason (`keep b: that mark is not possible for this finding now`), or the marks that were not written. Every run that ends with findings at the limit names each one with what it is about and its last failure: `verify: stranded <id>, <kind> <a> / <b>: <why> (<day>)`. `tacit verify --requeue all` (or `--requeue <id>,<id>`) clears the count and the failure of the findings at the limit (or of the ones named), so the next run sends them again; it calls no model and changes nothing else, `--dry-run` only prints what it would clear, an id with no count is an error (exit 1) and an empty value a usage error (exit 2). A finding settled since (a mark, a question, the owner's touch on it or, for a stale finding, on its fact) or gone from the review files loses its count at the next run's start, also when that run sends nothing. A stale finding whose fact the owner kept or marked in a pair is not sent: the page refuses an agent's mark on it. One run at a time writes the counters: a run holds `verifier.lock` in the state directory (`~/.local/state/tacit/`), a second run prints `verify: busy` and exits 0 having done nothing, and a requeue while a run holds the lock is refused (exit 1), since the run would write its counters back over it; a dry-run requeue needs no lock.

**Replaced facts.** A pair whose fact was superseded by a third fact (not the pair's other fact) since it was raised cannot take "keep the other": the page refuses to retire a fact that already has a successor, by design. Before v0.9.16 such a finding failed three times and stranded. Before it sends anything, `tacit verify` follows each side of every open pair finding (no mark, no question, no note or anything else the owner did on it or its facts, both facts in the store) whose fact a third fact replaced along its `superseded_by` chain to its end, and closes the finding with a `moot` record by the curator in `review/decisions.jsonl`, its reason in `evidence`. When both ends are live facts and differ, the finding moves there: the pair of live facts is raised as a new finding in `review/<date>-repointed.md` (the step's own file; the curator appends to `review/<date>.md` without the store lock), of the same kind (a supersede the curator applied as a proposal, a duplicate as a contradiction, a ruling change while its side is a ruling), with a line saying where it came from, unless a finding on those two facts already exists; the record names it (`repointed`), and the verifier takes it in the same run with the usual attempts. When a side has no live end (its chain ends in a retired fact or a fact not in the store, or loops) or both ends are one fact, the finding is closed as moot with that reason and nothing replaces it. The record changes no fact, so it carries no `before`; the page shows it as closed by the curator with the reason, and the owner may reopen it, which puts nothing back and makes the finding theirs. A binary older than v0.9.16 shows the record as an answer and sends neither finding. A finding with a fact missing from the store, or one the owner left a note on, is not moved: the first takes "both" as before, and on the second a verdict becomes a question for the owner. A moot closure of the curator's that the store no longer agrees with is reopened by the curator (`reopen`, by curator, which is not the owner's touch), and the same run moves it again or sends it: both its facts are in the store and neither is retired, and either neither fact is replaced by a third fact any more (a supersede it rested on was undone, for example by the answer to another finding) or the move it made is not the one it would make now (the chain it followed changed). A closure on a retired or missing fact stands. So does one whose moved-to finding was answered while both chains still run through that finding's facts: the answer settled the question there and may itself have extended the chain (keeping b on c / b makes a -> c -> b). The curator's reopen is checked again under the store lock, so an answer that landed since stays; a finding the owner touched, or whose facts they kept in a pair, is never reopened by it. A replay (`--ids`) that moves a finding verifies, in its place, the finding on the live facts. Commits of at most 20 findings (`review: ...`, by curator); a dry run prints what it would close and writes nothing; a replay (`--ids`) moves and reopens only the findings it names; `--max 0` moves and sends nothing more; the verifier never sends a finding this would close, also when the write failed.

**Dry run and rollout.** `tacit curate --dry-run` does not run the scan (it can take most of an hour); `tacit stale --dry-run` does and prints what it would flag. The scan runs last in `curate`, after the run's state is saved, with every git command under `nice -n 19` and, where `ionice` exists, the idle I/O class (`gitev.Git.Low`: the children are wrapped, because a priority set on the calling process would reach one thread of it only), and the unit sets `Nice=19` and `IOSchedulingClass=idle` for the whole service. A binary from before `retired` rejects a fact that has it (the frontmatter decoder is strict): such a machine skips that fact, prints "did not parse" and fails `tacit lint` until it is upgraded, so install this binary on every machine before the first verdict retires a fact.

Numbers (what day one flags, how many of those are really stale, cost per fact) are in `eval/VALUE.md`.

## Rotation

The rotation (`tacit rotation [--max N] [--age DAYS] [--fact A,B] [--dry-run]`, and a step of `tacit maintain` after curate and before verify; with the local layer, a step of the layer's full curate) sends the live curated facts nobody has checked for the longest back to the curator's model with proof, and stamps them. Nothing runs before the store format marker.

**Pick.** The folders left for review whose weekly retry is due (or that were never asked with extra evidence) are in the rotation's due set too: after the facts, the rotation puts them to the assessment, which gathers their extra evidence (Folder records, Assessment) and asks them whatever their fingerprint. The live curated facts that are due: those of this machine (its `machines/<host>` scope, or `applies_to.hosts` naming it, either in any case) whose description names a path under the home directory that is not there first, until they are checked after their last change (`goneProbe`, no model: a stat, once per path and run; not a path the clause around it says is gone, moved or an example, not one a command writes or a run makes on use, not a template, a glob or a cut one, a quoted path counted whole (a code span that is a command line counts by its first word), not another machine's: one of the store's `machines/<host>` folders, a box, server or remote, `ssh`, `host:path`; on the author's machine 524 of 9,416 live facts of this machine, and 27 of a fresh sample of 30 were stale, eval/VALUE.md, "Machine facts whose paths are gone"), then those that claim the owner's authority without their words (they fail the attribution check, Metadata checks; no hook delivers them, Provenance), then those made from an agent's note the reviewer could not confirm (`uncertain`, `nosource`: the silent notes no question is asked about, Questions), then never checked (`last_checked` missing), then the oldest check, then the oldest `created`, then by name. A checked fact rests 30 days (`--age`, `TACIT_ROTATION_AGE_DAYS`). Generated facts, facts in a folder suppressed into another (the migration moves them) and facts with an open finding (the verifier's and the owner's) are left out; with the local layer only this machine's own curated facts. The owner set no limit on the rotation's size (phase 2, answer 8): every fact that is due is checked unless `--max` (`TACIT_ROTATION_MAX`) says otherwise, and the cost of every batch is logged per fact in `rotation.jsonl` in the state directory.

**Proof.** Code gathers for each fact what it can find reliably, redacted (fail closed): what each repository's default branch holds of the paths and names the fact cites, and the commits that last touched or rewrote what is gone (the staleness check's light read, from the fact's effective date); whether the paths it names on this machine exist, when the fact is this machine's (`stat`: first every path the pick found gone, then up to 6 more it names under `~` or a system root, as Ancestors reads them, so a route outside those roots never reads as a missing path); newer live facts of its folder and of its repositories' folders, and older ones of its own folder, by a search with its description and distinctive names; facts anywhere that use its distinctive names (`gitev.Specific`); its folder's record when it is not active or is suppressed; an earlier staleness finding's answer. Each item has an id.

**Judge.** The model judges a batch of 12 against that proof alone, with no tools: `still`; `stale` (retired); `superseded` (by a newer live fact of the proof: `superseded_by`); `fix` (true, one detail changed: the old detail copied from the body, the new one, written as an in-place note, Supersede, never delete); `compress` (it and live facts of its own folder in the proof say one thing: one new fact that cites them all, which they point at); `reword` (only a fact marked `claims_owner`, which carries an `attribution` proof item: one new fact in the same folder, of its type and `applies_to`, says the same as an agent's observation and supersedes it); `unknown`. Every outcome but still and unknown cites proof items and says why. Code checks each verdict (`rotation.Check`): the cited items exist; a successor is a live fact of the proof, marked newer and written after it; a fix's old detail is in the body word for word and the note is well formed; a compress joins live facts of the folder that are not the owner's, under an unused name and a type a curated fact of that scope may have, and its body cites every fact it replaces; a reword is of a fact marked `claims_owner`, under an unused name, passes the attribution check, quotes no phrase (`ownerwords.Quotes`) the fact does not already quote (an agent never puts words in the owner's mouth), and cites the fact it replaces. A refused verdict goes back once with the problems. The other way out of a claim is code's: the rulings audit takes such a fact as a candidate, and a quoted phrase of it found in the owner's turns makes it their ruling (or their words, when short) with the ledger entry (Rulings); a reworded or promoted note is a new note to the assessment, which asks the folders it names again once (Owner words beat dates). The owner's facts (a ruling, or a fact holding words of theirs) are never changed: a verdict against one (a `fix` of a fact with their words excepted) is a question in `review/<date>-rotation.md`, `- check? [[name]] (scope) outcome=<o> on=<day>` with the curator's reading and the cited proof indented under it, which the page lists in Needs you and only the owner answers.

**Stamp.** One commit per batch, `curator: rotation: n checked (s still, t stale, u superseded, f fixed, c compressed, r reworded, k unknown, q asked)` with a line per change: the changes, `review/decisions.jsonl` lines `by: curator` for every change and question, and `last_checked: <day>` on every fact the model answered, whatever the answer (a verdict refused twice counts: the fact was looked at; a fact the answer left out is not stamped and stays due). Only the rotation writes `last_checked` (`fact.PatchRelations`); the tree's dates and the staleness check's effective date ignore it.

Measured with real Opus on a copy of a 16,600-fact store: one batch of 12, $0.116, $0.0097 a fact, about two minutes (10 still, 1 compressed, 1 unknown); the copy's repositories are rebuilt `.git` folders with no objects, so its git proof was empty or incomplete and the measured cost is for proof from search and records (eval/VALUE.md, "Rotation").

## Link repair

`tacit curate` runs it after the derived-facts and results steps (once, also when no inbox note is pending; `curate --dry-run` runs its dry run), and `tacit links` runs it alone (`--dry-run` reads the clone as it is, prints each repair it would make, syncs and writes nothing). No model is called. A link that names no fact (lint L6) is a link nobody can follow; the curator settles each one by rule, and a fact it cannot settle by rule is the owner's.

**Dead link.** Only a link counts: a `[[name]]` in a fenced code block (``` or ~~~), an indented code block (four spaces or a tab after a blank line, outside a list) or an inline code span (a TOML `[[table]]` header, an example) is code, for lint L6 and for this step alike, and is never read or touched. A `[[target]]` in the rest of the body of a curated fact is dead when its target names no fact in the store (inbox notes count as facts, as in L6), or names only curated facts that something replaced (`superseded_by` set) and a live successor is clear. A link to a fact this one replaced, directly or through another fact (the target's `superseded_by` chain reaches this fact: the statements a rebuilt ruling was made of, the note a decision replaced), is where the fact came from, not a dead link: it is left as it is, in a ruling and in any other fact, and is never put to the owner. A link to a live fact, to a retired fact with no successor, to a fact whose chain loops or dead-ends, or to a name only an inbox note holds, resolves for lint and is left as it is. Inbox notes are never edited, and a generated `derived/` fact with a dead link is reported on stderr and left to its generator, which rewrites it.

**Clear match.** A dead link is rewritten to a fact name only when exactly one live curated fact answers to it, by one of these, in this order:

1. The target is the name of one superseded curated fact: follow `superseded_by` (at most 16 hops) to the live fact at the end of the chain.
2. The target spelled as a fact name is a fact this one replaced (as above): the link is spelled right, a link to where the fact came from. Else it is exactly one live curated fact. Spelled as a fact name: lower case, a trailing `.md` dropped, every run of `_`, `.`, `-` or spaces one hyphen (`[[Gpu_Notes]]` and `[[gpu-notes.md]]` are `gpu-notes`). If that name is held by a superseded fact, rule 1 follows from there.

Not a match, by decision: a repo name. `[[codex-desktop-linux]]` names a checkout, and the facts about it (its module map, its hot spots, the project facts) answer different questions; pointing the sentence at one of them changes what it refers to, and "reads naturally" is not something a rule can test. A repo name is plain text like any other name nobody answers to. Also not a match: a fact merely similar in name or description, a name that two live facts answer to (ambiguous), and a rewrite that would make a fact link to itself.

**What gets written.** A rewritten link becomes `[[<fact>]]` and keeps its label, the text after the first `|` (`[[a|label]]`, `[[a#section|label]]`); a `#section` is dropped (the section belonged to the old fact). Every other dead link is unwrapped to plain text, its label if it has one, else its target: `[[keys]]` becomes `keys`, `[[a|the label]]` and `[[a#section|the label]]` become `the label`, `[[a#section]]` becomes `a`. Nothing else in the file changes: the frontmatter and every byte of the body outside the links stay as they were (the file is edited in place, not re-encoded, and replaced by a rename so a killed run leaves it whole), `updated` is not touched, and `MEMORY.md` is regenerated from the tree as the commit will hold it (a fact the clone does not track, or has only staged, is not in it). A repaired fact is not "edited" for the staleness check: the commit subject starts with `curator: links:`, and `gitev` leaves such a commit out of a fact's store history only when the commit's change to that file is a repair (`links.IsRepair`: the same file with links replaced by a link to another target with the old label and no section, or by the plain text this step writes, and nothing else) or that repair the other way round (a link put back, below), so a sentence under that subject still counts as an edit. Without the skip, a fact repaired today would hide every deletion between its own date and today from the check.

**Rulings.** A ruling (`fact.IsRuling`, see Rulings) is not edited. For each ruling and each dead target the curator appends one line to `review/<date>.md` under a `## link check` heading:

```
- LINK? [[<ruling>]] (<scope>) links to [[<target>]], and <why>; this is an owner ruling, so the curator left it; it would write <plain text | [[fact]]>
```

Once per fact and target: a target already named by a `LINK?` line for that fact in any review file is not raised again, whatever the owner did about it, and a second occurrence of the target in the same fact does not make a second line. The line stays until the owner edits the ruling; lint L6 stays red for that fact meanwhile, by design. The review page does not list `LINK?` lines (they are not pairs); `tacit app` lists them in Needs you (see App).

**Write path.** The same as the other steps: under the store lock the step syncs, plans on the fresh clone (a repair is a function of the files, so a lost race recomputes instead of replaying), writes, regenerates `MEMORY.md`, lints, and pushes once as `curator`, committing only the files it names (`CommitPushNamedOnceLocked`: a change someone staged in the clone does not ride along); a push that lost a race starts the locked part over (up to three more times). The lint gate looks at findings that are new after the write: one the store already had (a fact with its own L7 that also holds a dead link) does not stop the repair; a new finding on a file the step wrote drops that file for this run and says so; a new finding anywhere else, a linter that cannot run, a refused push, a cancelled context or any other failure stops the run. On a stop every file the run touched goes back to the bytes it had when the run began (not to HEAD), and the local commit is dropped. What is left alone and reported as not done: a tracked fact file with changes in the clone that are not exactly what this step would write from its committed version, and a fact file the clone does not track (a curate batch killed before its push, a fact written by hand): never planned, written, committed or removed, and a link to such a fact is left as it is. What a killed run leaves is committed by the next one only when it is provably the step's own: a fact file whose bytes equal what the step writes now from the committed version of that file (never a ruling or a `derived/` fact), and a review file whose only uncommitted lines are this step's `LINK?` blocks. A hand edit to a link is not that, even when it touches only the link. Another writer's uncommitted lines in today's review file are never committed with ours; the owner lines wait for a later run. The report counts and names in the past tense only what reached the server; what was skipped, dropped or lost to a failure is "not done".

**Idempotent.** A second run finds no dead link in a curated fact that is not a ruling and every ruling line already raised, so it writes and pushes nothing. One exception by construction: a link nested in a link (`[[[[x]]]]`) leaves a new link when the inner one is unwrapped, and the next run settles that.

**Putting back what older runs unwrapped.** Runs before v0.9.17 unwrapped a link to what the fact replaced as dead. `tacit links --restore [--dry-run]` reads the step's own commits (their subject starts `curator: links:`), newest first, so a line two runs repaired comes back whole. In each tracked curated fact they changed (not a ruling, not a generated fact), it puts back each link the run unwrapped whose target the fact replaced, judged on the store as it is now (`links.Planner.Replaced`): the line the run wrote is rebuilt with those links as they were written, and it replaces that line when the run's text and the fact each hold it once, word for word (`links.Restore`). Each line comes back only while the file stays the fact with links put back and nothing else (`links.IsRepair` the other way round): a line that moved into code gets no link, and the lines beside it still get theirs. Only a link whose target the fact replaced comes back; any other link the run unwrapped or rewrote stays as the run left it, and so does a line edited since. The restore is planned on HEAD: a fact the clone changed is left (not done) unless its bytes are the plan's, what a killed restore leaves; a killed daily run's review lines are not its. It writes through the step's locked write in one commit, `curator: links: N link(s) to what the fact replaced put back in M fact(s), unwrapped by older runs`, which gitev reads as a repair. On the author's store on 2026-10-30 its dry run finds the 20 links in 5 facts that `eval/curate/link_history.py` lists. A second run puts back none, and the step leaves them, since a link to what the fact replaced is not dead.

## App

`tacit app` is the owner's own window onto the store: what waits on them, every fact, and their edits. Code: `client/cmd/tacit/owner.go` (the operations), `app.go` (the methods the page calls), `app_desktop.go` (the window), `reviewui/app.html`, `desk.js`, `desk.css` (the page; design in `reviewui/DESIGN.md`, "The app").

**Three ways in, one code path.** The desktop window (Wails v2, the system webview) binds the exported methods of `App`; the page calls them through the webview bridge, so no port is open and no token exists. `tacit review` serves the same page in the browser from every build, on 127.0.0.1:7448, and is the owner's channel where the desktop build is not installed (release builds carry no window): Needs you, every fact with edit, retire, restore and undo, new rules, and the Folders page (create a folder, its status with a reason, an alias, a fold into another folder, an area's tools and commands). `tacit app --browser` serves it on 127.0.0.1:7450. Both answer `POST /api/call/<Method>` with the run's token in `X-Tacit-Token`, and serve the page itself only to the URL that carries the token (`/?t=<token>`); a request without it gets a short refusal, never the page, so a client that can reach the port but was not handed the URL (an agent) cannot read the token. The token (16 random bytes, compared in constant time) is new each run, goes to the browser the command opens, and is printed only when the command's output is a terminal: an agent's shell reads a pipe and sees the address without the token, and `--no-open` without a terminal refuses to start. Loopback addresses only, and only a loopback `Host` (no DNS rebinding); no MCP tool or other command hands out the token. The limit: any process of the owner's user can run the command under a pseudo-terminal, or read a browser's history or another process's arguments, as it can read the curator key; the owner commits are the channel `fact.OwnerWrote` trusts, not proof against such a process. `tacit review --label` serves the review page alone, whose marks go to the label file, with no owner write reachable. Both run the review page's own code (`reviewServer`): its items, marks, timeline and write path. The window is in a separate build (`-tags desktop,production,webkit2_41` on Linux, `-tags desktop,production` on macOS); the default `tacit` the hooks run stays pure Go, since the window's GTK and WebKit libraries cost every process start about 30 ms.

**Plain words.** The page speaks the owner's words, not the store's: fact, note (inbox), your rule (a ruling), retire, who it reaches (the scope, said as "in memra", "on workstation"), what agents read (the description), Details (name, file, frontmatter). Five places: Needs you, Your rules, What agents believe you prefer, All facts, Inbox (keys 1 to 5). Design: `reviewui/DESIGN.md`.

**Find any fact.** A search box at the top of every place (`/` focuses it) asks `Browse` for every curated fact, the owner's rules among them, live only unless "Retired and replaced too" is ticked, and shows the first 12. A result opens in All facts, which then holds the same search, with the fact's own actions. `tacit review --fact <name>` and `tacit app --browser --fact <name>` put `#fact=<name>` after the token on the URL they open and print (the fragment stays in the browser); the page opens on that fact the same way, or, when the store has no fact of that name, says so in the page and lists what the search finds for it, and the command says so on stderr. `--fact` needs the owner's page: label mode and the desktop window refuse it.

**Needs you** shows everything waiting on the owner one finding at a time, with "N left" as its only count: the review findings (pairs, `result-superseded?`, `RULING CHANGE?`, `stale?`, and the agents' questions on them, with the review page's marks), the rotation's questions about their own facts (`check?`, one fact each, "Checked by the curator", answered Still true or Outdated by the owner only), and one item per `LINK?` line. Each kind is asked as a fixed plain question with choices named by what they keep (Keep the newer, Keep the older, Both are true, Mark as conflicting; Use the number from git; Keep your rule; Still true, Outdated, retire it), each a mark the review page already had, and Skip for now, which saves nothing. Every pair also takes Neither is true (`wrong`): through the owner's write path (lock, sync, lint gate, one named `owner: neither is true: retire <a> and <b>` commit) both facts get `retired: <day>`, and one decision records both as they were (`before`), so reopen puts both back byte for byte. The owner may answer it on their own rulings; an agent never sends it, nor a note. Any finding takes a note in their words: sent with an answer it is the decision's `comment`; alone it is a `note` record that leaves the finding open, is shown on it, and is not a mark (the verifier still takes the finding). Either way the note is redacted with `digest.RedactAll` (fail closed: no redaction, nothing saved) and also written in the same commit as their inbox note (`inbox/human@<host>/owner-note-...md`, `source.kind: user`, quoting them with the day and linking the finding's facts by name), so the curator reads it like any remark of theirs. An open finding's notes reach the verifier as `OwnerNote`, which outranks every source: a verdict that would retire a fact of such a finding becomes a question for them. The two facts are named older and newer by the day each speaks for (the newest date in its text not after the day it was written, else that day); the older card is drawn left and the arrow keys follow the screen. An agent's question shows as its suggestion and reason, with its A and B named as the facts, never as a headline. What git shows leads with `Timeline.Summary` (Git evidence) and folds the dated events; a stale check also says what its finding line records as deleted, where and when. Kind, scope, find and past answers sit behind one Filter control. A `LINK?` line an older curator raised for a link to what the ruling replaced is no item (the ruling still holds the link, which is where it came from). A `LINK?` item is open while the link planner still finds that dead target in that ruling (the line itself stays in the review file); it offers Apply the fix, which writes into the ruling exactly what the curator would have written for that one link and nothing else, and Edit the rule. A ruling that was retired or replaced closes its items.

**Your rules, What agents believe you prefer, All facts and Inbox** list every fact of the clone at its HEAD: Your rules is All facts with rulings only (`fact.IsRuling`), each with their words under it ("In your words: ..." for a quote; "You said this is yours" for an endorsement; "You wrote this"); What agents believe you prefer is the curated `user_standard` facts that are not rulings and every fact that holds words of theirs (Their words, shown as "Your words in it: ..."), less those the owner said are not theirs, said as what agents wrote down, not their words, each with This is mine (key m), Not mine (key x) and Retire; it is a place to browse, and nothing in it waits for them or reaches Needs you. Inbox holds the inbox notes. "Your rule" appears on a card, a tag, a hint or a question only for a ruling. Each opens on its search field; the filters (scope, repo (the project or derived scope, or `applies_to.repos`), type, source kind, status (live, retired, replaced, any), curated or with inbox notes) fold behind one Filter control. Free text uses the full-text index of the clone at its HEAD (`search.Index.Rank`: every scope, every term as a prefix; the view's filters are applied before the fallback, so all terms are required only while a fact the view shows has them all, and otherwise any one is enough; the query pages past its first page until it has as many rows the view keeps as it asked for, so a filter that drops most of the top hits never leaves the list short), after the facts whose name holds the query as typed. A fact opens with its description and body (with its `[[links]]`: live, retired, replaced, inbox note, or no such fact), one sentence of where it applies and its dates, and its actions; Details folds every frontmatter field, the curated facts that link to it, the store's git history of its file (author, time, subject; a commit whose subject starts `owner: ` or an owner's review mark reads "you") and What git shows (`gitev.Builder.BuildOne`, cached like a finding's timeline, read when Details opens).

**Owner writes.** Edit (description, body, scope, type, `applies_to`), Retire, Restore, Undo last edit, New ruling, Replace with a new rule, This is mine, Not mine, Apply a link fix. Each runs `ownerWrite`: under the store lock, sync, plan on the fresh clone, lint, write the files, regenerate `MEMORY.md`, lint again, and push once as `curator` with `CommitPushNamedOnceLocked`, which commits only the files the write names (the fact, the old path of a move, `MEMORY.md`, `.gitattributes`), so anything else staged in the clone (a killed run, a hand `git add`) never rides along under the owner's name; a push that lost a race syncs and plans again (up to four times). A lint finding the store did not have before (keyed by rule, file name and message, so a fact's own old finding, such as a ruling's dead link, does not block it and a move does not make it new) refuses the write: the files go back to HEAD, the index cached for that HEAD is dropped, and the findings return to the form, which keeps the draft. A refusal by the server or a failed commit also keeps the draft. A fact file with uncommitted changes in the clone is not written; other files' uncommitted changes stay out of the commit (above).

**Stale forms.** A draft is kept by the fact's name (so a scope move made elsewhere does not lose it) and carries the hash of the file it was started on (`rev`) and that version's text, for as long as it lives, also across a refusal, a switch to another fact and a sync; the page never gives it the rev of a newer version by itself. An edit whose rev is not the file's (or has none) saves nothing and returns `changed`; the page then shows the version in the store now beside the draft (the lines the draft lacks marked, and the last change's author, time and subject) and offers two choices, focused on the first, and nothing is saved until the owner makes one (Esc returns to the choice and keeps the draft): Keep my draft (the draft takes the new rev and Save comes back; the store's version stays beside the form, folded on request, until the draft is saved; saving replaces it, and it stays in history) or Take the new version (the draft is dropped). What is marked in the store's version is what changed there since the draft was started, so the owner's own edits are not marked. A draft over a fact that changed while it was set aside opens the same way. Inbox notes are read-only and generated `derived/` facts are not edited or retired (their generator rewrites them).

- Edit re-encodes the frontmatter (`fact.Encode`), sets `updated` to the day, and keeps every other field. A scope change moves the file to the new scope's directory in the same commit and names the old path in the commit body (`Tacit-Moved-From: <path>`); this is a rename, not a delete, and the history follows it.
- Retire sets `retired: <day>` and `updated`, through `PatchRelations`, so only those lines change; the fact stays in the store and leaves the index, the hooks and search at once, like a staleness retirement. Restore clears `retired`. The owner may retire their own rulings; agents still may not (their guards are unchanged).
- Undo last edit is allowed when the newest commit on the fact's file (following a move) is one of the owner's `owner: ` commits and was not the one that created it; it writes the file as it stood before that commit (at its old path for a move) as a new commit, `owner: undo ...`, so history keeps both, and a second undo redoes. A ruling written in the app is retired, not undone.
- This is mine appends their decision `{"id": <mineID(name)>, "action": "mine", "a": <name>}` to `review/decisions.jsonl`, sets `source.kind: user` and `source.endorsed` to its id (`PatchSource`), in one commit `owner: this is mine: <name>`. Not mine appends `{"action": "not-mine"}` (`owner: not mine: <name>`): the fact leaves What agents believe you prefer and words of theirs it holds no longer guard it; the file is unchanged. While their Not mine stands, the fact's page says so, still shows their recorded words, and offers Undo Not mine (key x), which reopens the decision. An edit of theirs that takes the `owner_words` phrase out of the text drops `owner_words`. An edit of a ruling that rests on a quote and takes the quoted phrase out of the text records the same decision and rests the ruling on it: the words are their edit now. Undo of either appends a `reopen` of that decision (and undoing the undo records it again), so the audit agrees with the file.
- New ruling writes `<scope>/<name>.md` with `type: user_standard`, `source.kind: user`, `source.harness: human`, the machine's host, `created` the day, `applies_to.repos` the repo of a `projects/<repo>` scope, and the owner's text as the body, verbatim. The description is their first sentence unless the owner writes one; the name is a slug of it unless the owner edits it. A name any fact or inbox note holds is refused, except the inbox note the ruling is promoted from, whose name the ruling records as `origin`. The form asks which repo the rule is about first and lists scopes narrowest first (the repo, the machine, user, system), and says that agents tend to widen the owner's remarks when user or system is chosen. Promoting an inbox note opens this form filled from the note and changes nothing in the inbox; the curator may still read that note later, and a duplicate it makes is put to the owner as a pair.
- Replace with a new rule is New ruling with `replaces: <name>`: the form starts from the live fact's body and scope, and the one commit (`owner: new ruling <name> (<scope>), replacing <old>`) writes the rule and sets the old fact's `superseded_by` to it and `updated` (`PatchRelations`). A retired, already replaced, generated or inbox fact is not replaced. Undo on the replaced fact puts it back.

Every commit subject starts `owner: ` (`owner: edit <name> (<fields>)`, `owner: retire <name>`, `owner: restore <name>`, `owner: undo ...`, `owner: new ruling <name> (<scope>)` (with `, replacing <old>` for a replace), `owner: link in <ruling>: ...`, `owner: folder <action> <folder>`) and its body says the owner made it in tacit app (or tacit review, the same page); the commit author is `curator`, the writer the server lets touch curated facts. These commits count as edits for the staleness check (they date the fact). The owner's text is not redacted: it is theirs, and the server's secret scan still refuses a push that holds one.

**Controls.** Every button draws one icon from one inline SVG family (20 px grid, one stroke weight, round joins) before its label and its key. No native popup opens in the window: each filter and the edit form's Type keep a hidden `<select>` as their model and are drawn as a button and a list the page renders (arrow keys, Home, End, Page keys, type-ahead, Enter or Space to choose, Esc to close). Free-text fields carry no `<datalist>`, and the two search fields are plain text fields (no toolkit clear button; Esc clears and leaves one). **Undo from a slip** is bound to the fact the slip was shown for, and asks the store whether undo is possible for it before it runs. **Concurrency:** the queue reads the review items under the server's mutex, since the window runs each call on its own goroutine.

`tacit install app` (from the desktop build) writes `~/.local/share/applications/tacit.desktop`, running `<that binary> app` (with `TACIT_STORE` when it is set), and the icon `~/.local/share/icons/hicolor/scalable/apps/tacit.svg`. It runs nothing. On macOS it writes `~/Applications/tacit.app` instead (see Install).

## Models

The client calls models through the configured runner: Claude, Codex, Hermes, Grok, pi, Muse or agy. `runner` selects the default CLI and `runners` overrides each role. Generic defaults use the Claude alias `opus` for every deciding call: dreaming, curation, judging and verification (the owner, 2026-10-24: "but we said opus"; the measurements behind the dreamer and curator choice are in eval/VALUE.md). The verifier alone falls back to `sonnet` when Opus has no capacity for a batch. Operator-specific model versions, effort, profiles and cross-runner fallbacks are loaded from private configuration. Explicit runner selections can use the CLI model default. See [runner configuration and boundaries](docs/portable.md#model-runners). Each step has an environment override, which a job takes from its env file (`EnvironmentFile`, `--env-file`):

## Install

`tacit install <target>` writes files and prints the commands that load them; it never starts a job. Every target is idempotent (a rerun replaces tacit's own entries and nothing else). `claude` changes `~/.claude.json` only when its server entry differs. It keeps every other member and server as written, copies the old file to `~/.claude.json.tacit-backup` first, and refuses a server named `tacit` that does not run `tacit mcp`. With the server it writes the SessionStart hook as `tacit hook session-start --mcp`.

| Target | Linux | macOS |
|---|---|---|
| `claude`, `codex` | SessionStart (matcher `startup`), UserPromptSubmit, PreToolUse (matcher `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|apply_patch\|mcp__.*`; an entry an earlier release wrote under the narrower matcher is widened in place when it is tacit's alone) and PreCompact hooks (a reinstall replaces tacit's entries where they are and removes a tacit entry under any other matcher) in `~/.claude/settings.json`, `~/.codex/hooks.json`; for `claude` also the `tacit` MCP server (`tacit mcp --harness claude`) in `mcpServers` of `~/.claude.json`, unless `--no-mcp` (which removes it) | same |
| `follow` | `~/.config/systemd/user/tacit-follow.service` | `~/Library/LaunchAgents/ai.tacit.follow.plist` |
| `dream [--env-file F]` | `tacit-dream.service` (`EnvironmentFile=F`, default `~/.config/tacit/env`, `TimeoutStartSec=2h30min`: Run limits) and `tacit-dream.timer`; the idle job `tacit-dream-idle.service` (oneshot, the same `EnvironmentFile`, `TimeoutStartSec=2h30min`, `Nice=19`, `IOSchedulingClass=idle`, `ExecStart=-tacit dream --idle 20m` then `ExecStart=tacit curate --quick --min-interval 30m`, the second whatever the first's exit code: the `-` prefix, as in the curator's unit) and `tacit-dream-idle.timer` (`OnUnitActiveSec=10min`) | `~/Library/LaunchAgents/ai.tacit.dream.plist` running `tacit dream --env-file F` (default `~/.config/tacit/env`), and `ai.tacit.dream-idle.plist` running `/bin/sh -c 'tacit dream --idle 20m --env-file F; tacit curate --quick --min-interval 30m --env-file F'` every 600 s |
| `app` (desktop build) | `tacit.desktop` and the SVG icon | `~/Applications/tacit.app` |

**launchd.** launchd has no `EnvironmentFile` and no `RestartPreventExitStatus`, so the two differences are carried by the binary, not the job file. The follower's agent runs `tacit follow --launchd`, `RunAtLoad`, `KeepAlive {SuccessfulExit: false, Crashed: true}` (restart after any failing exit or crash, as `Restart=always`), `ThrottleInterval` 5 (`RestartSec=5`); under `--launchd` the config exit 78 becomes exit 0, which KeepAlive does not restart, after the reason is logged. The follower writes its own log (`--log ~/Library/Logs/tacit/follow.log`): each line stamped with the local time, and a line that would take the file past 1 MiB first moves it to `follow.log.1` (replacing the older one), so the log never holds more than about 2 MiB; launchd's own `StandardErrorPath` is `follow.err.log`, which gets only start-up errors and panics. The dreamer's agent runs `tacit dream --env-file F` every 14400 s (`StartInterval`, not at load), and the idle agent its two steps through `/bin/sh` every 600 s (launchd runs one program), and `--env-file` loads the file's `KEY=VALUE` lines (optional `export`, `#` comments, one pair of quotes removed) into the process before any model job; a missing file or a malformed line fails the run (exit 2) and no value is ever printed. Both agents: `ProcessType Background`, `LowPriorityIO`, `Nice` 10 (follower) or 19 (dreamer), stdout and stderr to `~/Library/Logs/tacit/` (the directory is created by install, since launchd does not), and `EnvironmentVariables` with `TACIT_STORE` when set at install time and a `PATH` of the binary's directory, `~/.local/bin`, the directories where `git`, `scrump` and the configured runners were found at install time, `~/.cargo/bin`, `/opt/homebrew/bin`, `/usr/local/bin` and the system directories (launchd's own PATH lacks all of the first). Load with `launchctl bootout gui/$(id -u)/<label>; launchctl bootstrap gui/$(id -u) <plist>`. The curator and the verifier have no macOS target: they run on the curator's machine.

**Run limits.** Every scheduled job's unit but `tacit maintain`'s stops a run that outlives the run's own limits: systemd's `TimeoutStartSec=` (a oneshot's is infinite unless set) and the Windows task's `ExecutionTimeLimit`; launchd has no such key, so a Mac relies on the run's own deadlines. Each git call of a run has a deadline of its own and git's low-speed limit (Sync), so a dead or stalled server fails the run in minutes; the unit's bound is for a run that hangs outside all of them, which would otherwise hold its job for good. Each bound is above the sum of the run's own limits at their defaults, so a unit never stops a run the binary allows: `tacit dream` 2h30min (a 45-minute wait for an idle dream, 20 minutes to push what an earlier run left, 45 minutes of batches), the idle job 2h30min (20 and 45 minutes for the idle dream, the quick curate's 20-minute budget and 10-minute tail), the local layer's `tacit curate` 5h (an hour's wait, the 150-minute budget, the 30-minute tail of its last batch). `tacit maintain` has none: verify has no overall budget, and a batch also splits at its payload limit, so 60 findings can take 60 calls of up to 20 minutes and a fallback call 20 more, more than any bound under the daily timer. The follower is a daemon (`Restart=always`) and has none. A run limit raised by configuration (`TACIT_DREAM_TIMEOUT`, `dream_max_runtime`, `--budget`) needs the unit's bound raised with it. The deploy copy of the curator's unit (`deploy/systemd/tacit-curate.service`, `curate` then `verify`) keeps the 5h it had, which is under its worst case for the same reason as `maintain`: a verify still going at 5h is stopped, and the findings of the batch it was in count an attempt. Whether Windows stops `tacit.exe` with the PowerShell that started it is not verified. The optional store mirror (`deploy/systemd/tacit-store-fetch.service`) runs plain git, so its `ExecStart` passes the client's low-speed limit and the unit stops a run after 10 minutes, under its 15-minute timer.

**The app bundle.** `tacit.app/Contents/` holds `Info.plist` (`CFBundleIdentifier ai.tacit.app`, `CFBundleExecutable tacit-app`, `CFBundleIconFile tacit`, `LSEnvironment` with the same `PATH` and `TACIT_STORE`, since Finder starts apps with launchd's PATH), `MacOS/tacit-app` (a copy of the running binary: macOS reads a bundle's Info.plist and icon only for an executable inside it; skipped when install runs from that copy), and `Resources/tacit.icns` (embedded in the desktop build from `client/cmd/tacit/macos/tacit.icns`, made by `scripts/make-icns.sh` from `reviewui/icon.svg`). The bundle is signed ad hoc with `codesign --force --sign -` when codesign exists. Finder starts the executable with no arguments (or `-psn_...`): run from inside a `.app` bundle, `tacit` then opens the window instead of printing usage.

**Read-only clone.** `tacit clone --read-only [--as <harness>] <url>` clones with `--config credential.helper=` (so no inherited helper answers, also during the clone itself), sets `tacit.readonly=true` and points `remote.origin.pushurl` at `read-only://this-clone-never-pushes`, a URL git has no transport for, so even a hand-typed `git push` in the clone fails locally and sends nothing. `Store.ReadOnly` reads `tacit.readonly`. With `--as` (normally `reader`, see Public path) the clone also gets `credential.<server>.helper` = `tacit credential <harness>` and `tacit.as=<harness>`: every fetch signs with that key, the follower signs the feed with it (`Store.ReadAs`), and `tacit authcheck` uses the clone's origin; the key must exist here before the clone starts (exit 2 otherwise). What it blocks, each before any work (no sync, model call, cursor move, file write or commit): the page writes (`applyOps` and `ownerWrite`: every mark, note, edit, retire, restore, undo, new rule, This is mine, Not mine, link fix); `tacit dream` (with the local layer off); `tacit import`; and the curator's commands `curate` (with the local layer off), `verify`, `stale`, `links`, `derive`, `results`, `dedupe`, `resolve`, `rulings audit` and `review apply` (`refuseWriter`, exit 2). Their `--dry-run` and `--out` modes write nothing to the store and still run. `commitPush` also returns `ErrReadOnly` before it stages anything, and a review mark that meets it puts back every file it wrote, as a second line of defence. `tacit install dream` refuses a read-only clone unless its local layer is on (Local layer). `addFact` (`tacit add`, the MCP tool) does not refuse: it writes to this machine's local overlay instead (Local overlay). Sync, the follower, hooks, search and the pages' views work as on any clone.

**Writer keys and view only.** The same up-front check (`writerCheck`) also asks, for a clone of the server (an `http` or `https` origin; a path remote needs no key), that this machine holds the key of the writer the command pushes as: `dreamer@<host>` for `tacit dream`, `curator@<host>` for the curator's commands. A machine without the curator key (a Mac set up by `scripts/mac-setup.sh`, by decision: it is never a curator) starts `tacit app` and `tacit review` view only: `Meta`, `Queue` and `/api/items` carry `view_only` ("View only on this machine. Edit from the curator's machine."), no finding offers a mark (`allowed` is empty), a fact offers no edit, retire, restore, undo, This is mine or Not mine, the page hides New rule, Make it my rule and the note box and shows that one line, and `writeRefusal` refuses every page write before it writes (label mode, which writes only its own label file outside the store, is unaffected). A read-only clone is turned into a writer clone by removing it and cloning with a key (`scripts/mac-setup.sh` does this when nothing in it is uncommitted).

**Mac setup.** `scripts/mac-setup.sh` is the whole first run on a Mac and every rerun (README "Mac"). It takes the server as a parameter (`--server` or `$TACIT_SERVER`, required: there is no built-in address; with `--read-only` it is the public path, such as `https://tacit.example.ts.net`) and, optionally, the ssh target the printed enroll line runs on (`--enroll-ssh` or `$TACIT_ENROLL_SSH`; without it the script prints the bare `tacit_server rpc` line to run on the server); it checks the server with `/healthz` (200 on the tailnet; 401, a key asked, is the public path's answer, accepted only with `--read-only`); it waits for enrollment with `tacit authcheck <harness> --url <server>`, which asks for receive-pack's refs with the writer's token (what `git push` asks first; for `reader`, upload-pack's refs, what `git fetch` asks first) and sends nothing, and clones after the keys are taken. `--read-only` creates only `reader@<host>`, clones with `tacit clone --read-only --as reader`, installs the hooks (claude, codex when `~/.codex` exists), the follower and the app (view only), builds scrump like writer mode (the agents' notes are redacted into the overlay), never installs the dreamer, and replaces an older read-only clone (another origin, or no `tacit.as`) when it holds no changes. Exit 0: the server takes the writer. Exit 1: wait (401 `unknown_key`, not enrolled yet; the server unreachable; 5xx). Exit 1 also for 429 (the public path holding off an address after failed requests) and for the public path's one 401 body. Exit 3: waiting cannot help (401 `host_mismatch`, `bad_signature`, `expired`, `unknown_harness`; 403; no key here). The script prints the answer on every try and stops at once on exit 3. scrump is built with `cargo install --rev` pinned to scrump's `v0.2.0` tag, when the scrump on PATH fails the text profile's canary or records mode (#84's repro as two records); so a rerun upgrades a Mac that has an older one. `--dry-run` executes only checks and prints each change; `client/cmd/tacit/macsetup_test.go` runs it on Linux against stubs of the macOS tools and asserts that HOME stays empty and launchctl, go builds and cargo never run.

## Public path

The server binds the tailnet address (`TACIT_PORT`, 7447) and, when `TACIT_PUBLIC_PORT` is set (7448 in the unit), a second listener on 127.0.0.1 only. Tailscale Funnel on the server host proxies public port 443 to that listener (`server/deploy/funnel.sh <host> on|off|status`); nothing else off the host can reach it. It exists for a machine that cannot join the tailnet (decision 2026-10-11: read only, the harnesses there share notes locally, no dreamer). Funnel is allowed per host:port, not per mount, so `funnel.sh on` reads the node's `tailscale serve status --json` and refuses unless 443 serves nothing yet or exactly `/` -> `http://127.0.0.1:7448` (`server/deploy/funnel_guard.py`: no other Web handler on `<host>:443`, no `TCPForward` or `TerminateTLS` on 443, no foreground serve session there).

**Telling Funnel requests apart.** By the listener: a request on the public listener is public (`TacitServer.PublicRouter` marks it), and Funnel only proxies to a local address, which is that listener. tailscaled deletes `Tailscale-Funnel-Request` and the `Tailscale-User-*` identity headers from what the client sent, sets `Tailscale-Funnel-Request: ?1` on every request that came in through Funnel (`addTailscaleIdentityHeaders` in tailscale's `ipn/ipnlocal/serve.go`), and overwrites `X-Forwarded-For` with the Funnel client's address (`addProxyForwardedHeaders`). So a request with `Tailscale-Funnel-Request` on the tailnet listener is a Funnel pointed at the wrong port or a spoof, and gets 403 at once: it is never taken for the node itself (whose own tailnet address is a WhoIs hit) and never reaches the public path's counters with a caller-chosen `X-Forwarded-For`.

**Rules on the public path.** Every route needs a `reader@<host>` key token (`Authorization: Basic <keyid>:<token>`): `/healthz`, `/journal`, `/events`, info/refs, upload-pack, receive-pack and unknown routes alike answer 401 before the route runs and before any body is read, and the connection is closed. Any other key (a writer's, the dreamer's, the curator's) is refused there: a private key copied off a harness machine must not become an internet-wide read credential. There is no tailnet node, so the key's host is not compared with one; the signature names the key. Every failure (no token, malformed, unknown key id, not a reader, expired, bad signature, replay) has the same body, `unauthorized: the public path needs a reader key token`, so an unauthenticated caller learns nothing about which key ids exist; the reason goes to the server log only. Unknown key ids cost no git: `Keys.public_key` first looks in the cached set of ids under `keys/` on main (one `git ls-tree` per 30 s, the positive key cache's TTL, dropped by every enrollment and every push that moves a ref). Nonces are claimed under one constant peer for the whole public path, so git's reuse of one token across a command survives a client whose address changes mid-command; a token first used on the tailnet listener is a replay here. A request whose token verifies is always served. A source (`X-Forwarded-For`) that has failed 60 times this minute gets 429 instead of 401 (a legitimate client fails once per git command, since git asks without credentials first); the counters live in their own table of at most 4096 sources, and a new failing source past that is answered 429. Every push is refused (403, "the public path is read-only"), on the advertisement and on the pack, before git runs; enabling pushes there would be a later decision of the owner. A feed stream on the public path ends after 300 s (the follower's own verification interval) with one `event: reconnect` frame; the follower reconnects at once with a fresh token and `Last-Event-ID` (a stream asked to end sooner than one reconnect delay is backed off like a failure), so a revoked reader key stops receiving journal rows within that time. The tailnet listener is otherwise unchanged: reads need a tailnet peer and no key, pushes a writer key.

**Reader keys.** `reader@<host>` is a key that only reads: enrolled like any key (`TacitServer.Auth.Keys.enroll`), it fetches and follows the feed on either path, and every push it makes is refused (403, "reader keys cannot push") on every path. It is the only key the public path takes. No fact is written as `reader` (`agentHarness` excludes it). `tacit authcheck reader` asks upload-pack's refs with the token; the public path's one 401 body means "not taken yet" there (exit 1, wait), since it cannot say whether the key is not enrolled yet or the clock is off.

## Local overlay

On a read-only clone, `addFact` (`tacit add`, the MCP `tacit_add`, the Hermes provider) writes to this machine's overlay, `$TACIT_LOCAL` or `~/.local/share/tacit/local/<harness>@<host>/<name>.md` (`client/internal/overlay`), in the store's fact format: the same redaction with scrump (fail closed: no scrump, nothing written anywhere), the same normalization, harness and host in `source`. A fact whose description and body any overlay file already holds is not written again, whichever harness wrote it; a name taken by another fact gets a short suffix. The overlay is a plain directory outside the clone and never a git repository; an overlay directory inside the clone, also through a symlink and before it exists (the nearest existing ancestor is resolved), is refused (`ErrInside`) and never indexed, so no commit or push can carry it.

Search reads it with the store: the index is keyed by the store's HEAD and a stamp of the overlay's files (`index-v<schema>-<sha>-l<stamp>.db`, a copy of the store-only `index-v<schema>-<sha>.db` with the notes added, so a change of the overlay never builds the store again), so `tacit search`, `tacit_search` and the curator find a new note at once. The hooks never wait for a build: while the file for the current overlay or HEAD is missing they read the closest older one and start the build in the background, so a new note reaches them a prompt or two later. An agent's overlay note carries the path `local/<harness>@<host>/<name>.md`, is never an inbox fact, never a ruling and never their words whatever kind its writer gave it (no overlay file is ever owner-written), and is marked `(this machine)` in hook blocks and `tacit_search`. The local layer adds two directories to the overlay, with their own rules (Local layer): `local/inbox/` (dreamer notes, inbox facts) and `local/curated/` (the local curator's facts, where a quote the local ledger backs makes a ruling, `overlay.IsRuling`). With the layer off the overlay is read without those two directories. `tacit fact` and `tacit_fact` fall back to the overlay. They reach only the harnesses on this machine; they are not reviewed and never reach the store.

## Local layer

A machine whose clone is read-only can dream and curate its own sessions into its overlay, which never leaves the machine. The owner's rule is that a read-only machine's information stays there: the store (served from the server) never receives anything from it. The setting is `local_layer: on` in the settings file, or `TACIT_LOCAL_LAYER` (`on`, `true`, `yes`, `1`; anything else is off). It is off by default, and off a read-only clone behaves as it did before: the full dream and curate refuse (exit 2), the idle dream, the session dream and the quick curate do nothing quietly, no hook starts a dream, and `tacit install dream` refuses. The layer applies only to a read-only clone: on a writer clone the dreamer and the curator write the store as before.

**Layout.** The layer's files sit in the overlay next to the agents' notes (`<harness>@<host>/`), under names no harness directory can have:

```
local/inbox/dreamer@<host>/<name>.md   the local dreamer's notes: unreviewed, inbox facts
local/inbox/dreamer@<host>/_repos.json this machine's repository catalog (Scopes), read by its checks only
local/curated/<scope>/<name>.md        the local curator's facts
local/curated/review/owner-quotes.jsonl the local quote ledger
local/curated/review/<date>.md         the local curator's review lines
local/curated/review/agent-reviews.jsonl the local reviewer's ledger (The reviewer)
```

The overlay is never a git repository, so there is no history; every write is atomic (a temporary file in the same directory, synced, renamed), files are mode 0600, and an overlay inside the clone is refused before any work (`ErrInside`), as for an agent's note. Every write resolves its final path, every symlink on the way included, and is refused when that path is inside the clone or outside the overlay. Nothing of the layer writes the clone: no file, no commit, no sync, no push. With the layer off, `inbox/` and `curated/` are not read at all: not indexed, delivered, searched or found by `tacit fact`, so nothing the layer wrote outlives the setting. Its runs read the clone as the follower keeps it (its facts, its HEAD for the index) and do not sync it.

**Dreaming.** `tacit dream`, `--idle`, `--session` and the hooks that start them (the prompt hook's full window, PreCompact) work as on a writer clone (Dreamer sources): the same prompt, `dreamer.json` cursors, `dreamer.lock`, the failure backoff and `dreamer.log`, all in this machine's state directory, with `local: true` in the meter line. A window's notes go to `local/inbox/dreamer@<host>/`, each redacted with scrump before it is written (fail closed: no scrump, no note and the cursor stays), a note already there is not written again, and there is no recovery step, since nothing waits for a push. `--dry-run` writes nothing, as before.

**Curation.** `tacit curate` and `curate --quick` curate the layer's dreamer notes into `local/curated/<scope>/`. Only notes under `local/inbox/dreamer@<this host>/` of harness `dreamer` and this host are taken; any other file there is never curated. They go through the store curator's steps (The curator, Near-duplicates, Contradictions): the same batches, split prompt, rulings pass, invalid-answer splits and strikes, `curator.lock`, the quick run's 24 hours (read from the note file's time, as there are no commits), two batches and `--min-interval`, with the run's state in `curator-local.json` and its report line in `curator.log` with `local: true`. What differs:

- *Rulings.* The evidence check is the store's (`curate.ApplyEvidence`), against the owner's turns on this machine only: its transcripts, prompt histories, pi and Hermes sessions. The store's notes are not read. A local entry stays `kind: user` only when its quote is in the note it came from, proves the rule and is a statement of theirs here; its ledger line goes to the local ledger. Anything else is filed as observed. A redaction that changes a ruling's quote files it as observed too.
- *Near-duplicates.* A note is set aside before the split, and an entry absorbed after it, when it restates a curated fact of the store, a fact of the local curator or an agent's note on this machine (`curate.Restated`, `curate.Absorber`, with all three).
- *Conflicts.* Each new fact is paired with its closest fact in the index, which holds the store's facts and the overlay's (Index), and with the batch's own facts. A `contradicts` is a line in the local review file. A `supersedes` retires a fact of the local curator by the store curator's rule (same origin or most terms shared, never a ruling or a fact with their words), by setting `superseded_by` in the overlay. A `supersedes` against a store fact or an agent's note on this machine is only a line (`- supersedes? [[new]] (this machine) may replace the store's [[old]]; owner decides`): the store changes only on the curator's machine, and an agent's note is never edited, as a store inbox note is not.
- *The store curator.* On a writer clone the store curator's conflict check never pairs a new fact with an overlay fact, so no local fact reaches its judge, a store review file or a push.
- *No whole-store step.* No derive, results, disowned, links or staleness step runs, full or quick, and no verifier; `--recheck-conflicts` is refused. There is no `MEMORY.md` and no lint of the overlay.
- *Writes.* Each fact is redacted with scrump (fail closed: the batch is not written and its notes stay pending) and written atomically. The ledger and review files are rewritten whole and renamed, never left half-appended.

**Delivery.** The index loads the overlay with the store (Local overlay) and reads the layer by its paths: a note under `local/inbox/` is an inbox fact (not delivered by hooks; `tacit search --inbox` and the MCP tool find it, marked `(unreviewed) (this machine)`); a fact under `local/curated/` is ranked with the store's curated facts (by BM25 and the prompt gates; the weighted relationship evidence leaves the overlay out, as before) and marked `(this machine)`, and SessionStart's cap on this machine's notes does not apply to it. A local fact is a ruling (`overlay.IsRuling`) only when it is under `local/curated/`, its harness is `curator`, it is `kind: user` with `owner_quote` and `owner_quote_from`, and the local ledger records that quote for it: then it is a `RULE` line on this machine (a ruling in its task is a plain line, as for the store's). An agent's note, a dreamer note, and a local fact that only carries the fields are never rulings and never their words. The local ledger is part of the overlay's stamp, so a new ruling rebuilds the index.

The limit of the design: the overlay is a directory of the user's, and whoever can write it (any agent with shell access on the machine) can write a curated file and its ledger line and so forge a local ruling. The local curator never makes one without the evidence check, and a forged one stays on that machine; the store's rulings rest on the server, which a local file cannot reach. `tacit_search` marks a local dreamer note `[unreviewed] (this machine)`. The app (`tacit app`, `tacit review`) does not show local facts: it lists the clone's.

Why local rulings are rulings: the check that makes them is the store curator's, run on the same kind of evidence (their own turns, found by code, no model), and the owner on this machine is the owner. Delivering them as observations would teach agents on this machine that the owner's own words here weigh no more than an agent's guess. They stay this machine's: they reach no other machine, no one reviews them, and the store's rulings are unchanged. The agents' notes stay unreviewed observations, as before.

**Install.** `tacit install dream` on a read-only clone with the layer on writes the dream job and the idle job (as on a writer clone) and a daily local curate job: `ai.tacit.curate-local.plist` (`tacit curate --env-file F` every 86400 s) on macOS, `tacit-curate-local.service` and `.timer` (05:30 daily) on Linux, the `curate-local` task on Windows. Each job, and every job written while the layer is on, carries `TACIT_LOCAL_LAYER` and `TACIT_LOCAL` from install time, so it runs in the layer whatever the settings file says later.

**Turning it off.** Remove `local_layer: on` from the settings file (or set `off`) and unset `TACIT_LOCAL_LAYER`, then remove the jobs:

```
# macOS
for l in ai.tacit.dream ai.tacit.dream-idle ai.tacit.curate-local; do launchctl bootout gui/$(id -u)/$l; rm -f ~/Library/LaunchAgents/$l.plist; done
# Linux
systemctl --user disable --now tacit-dream.timer tacit-dream-idle.timer tacit-curate-local.timer
rm -f ~/.config/systemd/user/tacit-{dream,dream-idle,curate-local}.{service,timer}; systemctl --user daemon-reload
# Windows (PowerShell)
Unregister-ScheduledTask -TaskName 'Tacit dream','Tacit dream-idle','Tacit curate-local' -Confirm:$false
Remove-Item "$HOME\.config\tacit\tasks\tacit-dream.xml","$HOME\.config\tacit\tasks\tacit-dream-idle.xml","$HOME\.config\tacit\tasks\tacit-curate-local.xml"
```

The overlay's `inbox/` and `curated/` stay on disk, unused; delete them to remove what the layer wrote. The curate job runs `curate`, not `maintain`: the verifier is the store's. The layer's full curate runs the overview step for this machine's own folders and the rotation of its own facts (Rotation) itself, into the overlay. The hooks (`tacit install claude`, `codex`) are the same; they read the setting from the settings file, so set `local_layer` there.


## Delivery

A statement is printed in their words: `- <name>: you said once (<day>): "<their words>"; context: <context>`, with `(a check disagrees, maybe misread)` when a check flagged it; it ranks with decisions and past mistakes, never as a rule.

**Provenance.** Every delivered line says whose it is, from code-checked fields only (`search.Hit.Provenance`, the index's `ruling`, `intask`, `words` and `claim` columns): an owner rule (a ruling not in its task) is a `RULE` line; another ruling of theirs (a quote in its task, a decision code made of their statements, a rule they wrote in the app) is `- <name>: you said (<day>): <description>`; a statement `you said once`; a fact computed from git keeps `(computed from git)`; every other line is an agent's: `- <name>: agent note (<day>): <description>`, or `agent note holding your words (<day>)` for one with words of theirs the ledger backs. A fact that fails the attribution check (Metadata checks: it says the owner ruled, said, decided or wants something and is not their verified words; the index's `claim` column, schema 14) is pushed by no hook (SessionStart, the prompt, a tool call, an area or org push: `withoutClaims`, and the hooks' queries leave it out before their limits) until it is fixed; `tacit_search` still finds it, as `agent note (<day>; claims owner authority without evidence)`, `tacit_fact` opens with `# whose: <name> is <label>` for each fact it shows, and the tree's fact lines add `agent note`, `agent note holding your words` or `agent note, claims owner authority without evidence` (the folder index files are not changed; they mark rulings already). The store is not changed by any of this; the rotation (reword) and the rulings audit (their quote found) fix such facts. An org's facts reach its members' sessions (Orgs), and a repository whose forge name differs is named `<intended> (GitHub: <current>)` (Planned renames).

The hooks read the local index of the local clone and fail open. An owner rule here is a ruling (Rulings) that is not in its task: it is a `RULE` line, it comes first among the owner's rules and standards, and it is the one the prompt hook's rule slot adds. A ruling in its task is a `you said (<day>)` line, not a rule: at the prompt it is ranked like any other fact; at SessionStart it ranks with the standards.

Each repo-first part below has its own setting, on by default, in the config file's `delivery` section or as `TACIT_DELIVERY_<NAME>` (`on`/`off`): `repo_start`, `repo_aliases`, `prompt_metadata`, `prompt_action`, `instruction`, `tool_push`, `tree_pointer`, and `TACIT_DELIVERY_AREA_PUSH`, `TACIT_DELIVERY_TOPICS` (areas and topics, below), `TACIT_DELIVERY_WORKSPACE` and `TACIT_DELIVERY_PROMPT_REPO_RANK` (workspaces and the prompt's ranking, below); and the bounds `start_ceiling` (6), `prompt_ceiling` (5), `prompt_relative` (0.7), `meta_ceiling` (1) and `TACIT_DELIVERY_AREA_CEILING` (3). With every switch off and `prompt_ceiling: 3`, `prompt_relative: 0` the hooks deliver what release 0.7.1 did. Measurements behind each default: eval/VALUE.md, "Repo-first delivery".

A fact is **tied to a repo** by its metadata: its `applies_to.repos` names the repo or an alias of it, or its scope is `projects/<repo>` and its `applies_to.repos` is empty. The **tiers**: rules and standards (rulings and `user_standard`) are tier 0, `design_decision` and `past_mistake` tier 1, every other type (history, reference, structure, machine facts, host notes) tier 2. The repo-first lines take tiers 0 and 1 only.

**Repo aliases** (`repo_aliases`). The session's repo and its names are repoid's (Scopes): the main checkout's directory name, the lexical name of a symlinked checkout the session ran through, origin's repository name; all read from files, no git process. With the setting on it also answers to the repository name of every remote in the repository's config, and the package name its checkout's root manifest declares (`package.json` `name` without an npm scope, `Cargo.toml` `[package]`, `pyproject.toml` `[project]`, the last element of `go.mod`'s module path) when that name shares a word of three letters or more with one of the others. A renamed or republished repo keeps the facts filed under its other names, with no list of renames to keep. Off: repoid's names only. A linked worktree's directory name is no alias: the worktree is its main repository.

**Workspaces** (`TACIT_DELIVERY_WORKSPACE`). A folder that is in no repository but holds several is a workspace: a Brazil workspace (its packages under `src/`), a folder of checkouts. When the cwd is one, and no folder record names the place (`rootFolder`), the session's repositories are all of the workspace's: the git roots repoid finds at most two levels below the cwd (a real `.git` directory or gitfile whose checkout is that folder; a linked worktree is its main repository, so a repository's worktrees count once), not inside dot folders or `node_modules`, a symlinked folder looked at but never walked into, under every name delivery knows each by (Repo aliases, and the names the records join them with). The home directory, the file system root and every folder above home are never scanned. A folder with more than 8 distinct repositories, or more than 2,000 entries on the way, is a general folder of projects, not one piece of work, and gets none (measured on the author's Mac: Brazil workspaces and worktree folders hold 1 to 6, the folders above them 10, 16 and 84; eval/VALUE.md, "Workspaces and the session's repositories first"). The SessionStart repo block, its tree line (`# the workspace's <n> facts by folder: ` and the tree call for each folder that holds them; `tacit_search`'s last line the same), the prompt hook's scopes, the PreToolUse push and `tacit_tree`/`tacit_search` then read every one of them, as the one repository of a session in a repo; the title names `the workspace <folder>: <repo>, <repo>`. A file a tool call writes narrows the call to the workspace repository it is in (its path facts, relative to that checkout; a `tacit_search` path filter the same); a shell command run from the workspace root is matched against all of them. At the prompt, paths of one workspace repository in the prompt and the transcript (the activity rule below) narrow the session to that repository; activity pointing outside the workspace changes nothing. Off: a folder in no repository is in none, as before.

- SessionStart: after a bounded sync (skipped while a healthy follower has just confirmed the clone current, see Change feed). In a repo (`repo_start`): the facts tied to the repo of tiers 0 and 1, rules and standards first, each tier ordered by the BM25 score of the repo's names against the fact's name and description, at most `start_ceiling`; this machine's agents' notes count at most 3. Facts that only mention the repo in their words, and host and machine notes, are not in it. Outside a repo, or with the setting off: at most 10 facts for the session's repo and host (query: the repo and host names), owner rules first, then rulings in their task. Derived facts are never in this block. Its first line says where the detail is: `tacit fact <name>`, or with `--mcp` (the session has tacit's MCP server) `mcp__tacit__tacit_fact <name>`. With `instruction` on, its second line is the instruction line: `tacit holds this owner's rules, decisions and past mistakes. Before an action that changes something, run one <search> for it.`, where `<search>` is `` `mcp__tacit__tacit_search` `` or `` `tacit search <what you will do>` ``; the MCP server's `instructions`, which a harness shows while the tools are deferred, are the same sentence with the bare tool name and one clause more: `tacit holds this owner's rules, decisions and past mistakes. Before an action that changes something, run one tacit_search for it; tacit_tree shows what it holds.` (the server's only instructions; none with the setting off). With the setting off the title names `mcp__tacit__tacit_fact` for detail and `mcp__tacit__tacit_search` for more, as before. With `tree_pointer` on and the repo block showing fewer of the repo's facts than are tied to it (all types; the ceiling and the tier filter cut the rest), the block's last line is `# this repo's <n> facts by folder: <tree> projects/<repo>`, where `<tree>` is `` `mcp__tacit__tacit_tree `` or `` `tacit tree `` and `<repo>` the first of the repo's names that is a project scope of those facts: what the store holds beyond the block, and the one call that lists it. The hook answers source `startup` (or none) only; resume, clear and compact re-fire it with the facts already in the transcript.
- PreCompact (`tacit hook pre-compact`: Claude Code's and Codex's PreCompact, and the Hermes provider's `on_pre_compress` with `hermes_session_id`) starts the session dream (below) for the session about to compact and returns: the harness waits for the hook before it compacts, and a dream takes minutes. The session's facts reach the store for other and later sessions; nothing is re-injected into the same session, since the compaction's summary carries its content (the SessionStart that follows a compaction prints nothing). It prints nothing and fails open; with no transcript and no session it starts nothing.
- The session dream, started by PreCompact and by the prompt hook's window trigger: `tacit dream --session <transcript_path or Hermes id>` (with `--env-file` the dream job's env file when it exists), detached (its own session, setsid; on Windows no console, its own process group and out of the harness's job object, `CREATE_BREAKAWAY_FROM_JOB`, started again without that flag when the job forbids breakaway), with no stdin and its output appended to `dream-session.log` in the state directory (moved to `.1` past 1 MiB). On a read-only clone or a machine without the dreamer's key no hook starts one, unless the clone's local layer is on (Local layer). A dream already running makes it exit `busy`; a transcript that failed within 4 hours it passes over (Dreamer).
- The window trigger (UserPromptSubmit, every prompt, before the prompt's facts): when the transcript's undreamed part, its size less its cursor in `dreamer.json` (no cursor: the whole file), reaches about one dream window, the hook starts the session dream and goes on. Bytes stand in for the digest, which the hook does not build: 4 MiB for a Claude Code transcript and 1 MiB for a Codex one (the dreamer's own source globs say which; a transcript none of them holds starts nothing). A transcript holds far more bytes than its digest (tool output, metadata, images), and how many depends on the harness: on the author's Mac a 4 MiB Claude Code delta digests to a median of 0.71 windows of 60,000 characters and a 1 MiB Codex delta to 1.5 (eval/VALUE.md, "Dreaming at a full window"); 4 MiB is also what one dream reads of a transcript per run, so a larger Claude Code threshold would only read part of it. A Hermes session (the provider's `prefetch` passes `hermes_session_id`) is measured in message content bytes after its cursor, one query of its store, with a threshold of 120,000 bytes (content is close to the digest's characters; not measured). The check is a stat and a read of `dreamer.json`, no digest, no git and no model (about 3 ms with 5,000 cursors, in the test); the writer check runs only once the threshold is met. It starts nothing while `dreamer.lock` is held, for a transcript that failed within 4 hours, on a machine with no cursors yet, or for a cursor it already started a dream at (`dream-trigger.json` in the state directory, the cursor per transcript; an entry whose cursor has moved is dropped).
- UserPromptSubmit: at most `prompt_ceiling` (5) curated facts above a score floor (15 in a known repository, 20 without one) that also score at least `prompt_relative` (0.7) of the best candidate's score, each once per session (with `prompt_relative: 0` the ceiling alone bounds the block, as the cap of 3 did). When none of them is an owner rule (and the request is not a short one, below), the best rule among the candidates that passed the gates below (the prompt query returns twice the ceiling), at a score of 10 or more, is one more line; a ruling the session already saw counts as present, and the slot is not refilled with the next one. The slot is part of the local selection; with a utility provider (below) the scores decide. When the cwd is in no repository, the hook takes the repository the session works in from paths, with the dreamer's rules (Scopes): those in the prompt (counted twice, so one typed path alone does not decide, but one the owner says to work in, `cd` or `git -C` with it, does) and those in the last 512 KiB of the transcript (`transcript_path`, read only when it is a regular file under the home directory once symlinks are resolved, and opened without blocking). It runs only for a prompt the hook would answer, stats at most 2,000 paths and stops after 300 ms (then no repository). That repository is then the session's, as if the cwd were in it (in a workspace, only one of its repositories: it narrows the workspace to it). The index stems words (FTS5 `porter unicode61 remove_diacritics 2`, since index schema 7) and a query term counts once per stem, so "amended" and "amend" are one match. Before ranking limits, require at least two distinct name/description query matches and coherence: the least-frequent known summary term or any known term in at most 50 indexed names and descriptions and at most 2% of the indexed facts, two name matches, or an adjacent query-term phrase. A syntactic identifier (underscored or mixed letters/digits) present in at most five indexed documents can qualify alone. Bodies do not satisfy coverage. Harness-injected turns are skipped, and so is a pure text operation on a literal the prompt supplies (the word `literal` plus an operation: upper/lowercase form, reverse, spell, length, count characters/letters/words); either alone does not skip. A second query can add at most one derived fact from the current repo, above floor 12. Derived facts never displace curated facts. Last, a line that says back what the request says (a scheduled job's own instructions, filed as a fact from an earlier run of it) is left out, whatever chose it (a ranked line, the rule slot, the derived fact, a metadata or action line), and nothing takes its place: its name and description have 5 distinct words or more (compared by stem), the prompt holds at least 7 in 10 of them, and it says no (`no`, `not`, `never`, `don't`, `avoid`, `without`, ...) only where the prompt does too (eval/DELIVERY.md, "Echoes of the request"). See eval/DELIVERY.md for the measured precision/recall tradeoff.

  With session repositories (a repo, or a workspace) and `TACIT_DELIVERY_PROMPT_REPO_RANK` on, the candidates are ranked over a pool of 50 (`TACIT_DELIVERY_PROMPT_RANK_POOL`) before the floor, the relative threshold and the rule slot: a fact of tiers 0 and 1 tied to the session's repositories weighs 1.5 times its score (`TACIT_DELIVERY_PROMPT_REPO_BOOST`), so it comes before another scope's fact with a similar match; a fact filed under another project and not tied to them weighs 1/1.5 of its score (`TACIT_DELIVERY_PROMPT_OTHER_PENALTY`), so it needs a stronger match to clear the floor; with `TACIT_DELIVERY_PROMPT_PENALIZE_MACHINES` on (off by default) so does a machine's fact not tied to them. The user's, the system's, an org's, a topic's facts and the repositories' own others keep their score; the block then sees the best twice-the-ceiling of them, as before. Measured on the crdm-bench cells and the 276-case replay (eval/VALUE.md, "Workspaces and the session's repositories first"): the held-out facts reached stay level up to a boost of 1.5 and fall above it, and the penalty on machine facts loses held-out facts the task needed.

  Two repo-first lines follow, in a known repo, each not backfilled (when its best candidate is one the session has, or one already in the block, nothing is added). The metadata line (`prompt_metadata`): at most `meta_ceiling` (1) facts tied to the repo, of tiers 0 and 1, whose `applies_to.paths` cover a path the prompt names (a token with a slash, or a file name with an extension), or whose `applies_to.commands` the prompt names: the whole command as words, or its last word when that has four letters or more and is no flag ("commit" for `git commit`, `tsup` for `tsup`), compared by stem. Path matches rank first (a deeper glob first), then command matches; then rules and standards, then newer. A glob matches by `filepath.Match`, as a directory prefix (`src/**` or `src` covers `src/a/b.ts`), `**/` on the base name, or a bare file name anywhere in the repo. The action line (`prompt_action`): when the block has no fact of tiers 0 and 1 tied to the repo, the best one for the prompt by BM25 without the coherence gate, at score 10 or more (the rule slot's floor), from the store or the local curator (Local layer), never an unreviewed local note. No list of actions or words: the facts' own words and metadata decide. A request of fewer than 3 distinct words of 3 letters or more (the search's own stop words aside, a path's parts counted as words, compared by stem) gets neither the action line nor the rule slot, in a repository or not: it names too little to pick a rule or an action for (eval/DELIVERY.md, "Short requests"). Its ranked, metadata and derived lines stay.
- PreToolUse (`tacit hook pre-tool`, `tool_push`): before an edit (Claude Code's Edit, Write, MultiEdit, NotebookEdit: `file_path` or `notebook_path`; Codex's `apply_patch`: its `*** Add|Update|Delete File:` lines) or a shell command (`Bash`, `tool_input.command`), at most `meta_ceiling` (1) facts tied to the repo, of tiers 0 and 1, whose `applies_to.paths` cover a file the call writes (relative to the checkout's root; files outside it are not matched) or whose `applies_to.commands` are how one part of the command line starts (split at `;`, `&&`, `||`, `|`, `&`, parentheses and command substitution; environment assignments skipped; the program compared by base name), or how it goes on after the part's first word when the second is no flag: a program that runs the next one (`npx vitest`, `sudo make lint`, a loop's `do make lint`) runs that command, with no list of such programs. A command of one word (a bare program: `ssh`, `python3`) matches only with a second tie: a word of the fact's name or description, other than the command's own, is in the command line too, not counting the words of the session's repository names, its folder and the home directory, which every fact of the repository shares (measured on the author's graded pushes, eval/DELIVERY.md, "Pushes keyed on a bare program"). Ranked as the metadata line, and not backfilled: each fact once per session, in the session's delivered set the other hooks share, so a fact SessionStart or the prompt printed is not printed again. It answers as JSON, `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": "<block>"}}` (plain stdout of a PreToolUse hook does not reach either harness's model), never denies, asks or changes the call, and prints nothing when nothing matches, on any error, or after 400 ms; outside a repo and a workspace only the area push below runs.

Before an MCP call whose tool name an area's `tools` globs match (MCP tools only: a pattern that matches a harness's own tool, `Bash` or `Edit`, matches no call; it pushed the area at each session's first shell command), or a shell command one of its `commands` starts (the command matching above; an area's command needs no second word), in a repository or not, it prints, the first time the session uses that area, at most `area_ceiling` (3) of the area's own facts of tiers 0 and 1 (a fact whose own `applies_to.commands` the call runs first, then rulings, standards, decisions and past mistakes, newest first) and one line `# more on <area>: \`tacit_tree areas/<area>\` (<n> facts)`. The records are in the search index, so the hook reads no file beyond it; an MCP tool's input is never read as a path or a command, and an edit outside a repository opens nothing. Measured on a copy of a 16,600-fact store, 300 process starts each on a loaded workstation (eval/VALUE.md, "Area push"): an MCP call no area matches p50 49 ms, p95 65 ms; one that pushes p50 62 ms, p95 76 ms; the bare process 26 to 33 ms p50. The prompt hook searches a live topic's folder too when the prompt names the topic or one of its aliases as a run of words, compared by stem; its facts still pass the prompt's gates. Code matches names; no model.

### Search and the tree

What an agent asks for itself, through the MCP server (`tacit_tree`, `tacit_search`, `tacit_fact`, `tacit_add`) or the CLI (`tacit tree`, `tacit search`, `tacit fact`, `tacit add`). Search results are one line per fact (`- name: <whose>: description`, rules as `RULE`, whose each other line is as in Delivery's Provenance, inbox notes `(unreviewed)`, this machine's notes `(this machine)`), with a first line `# <from>-<to> of <total> fact(s)` and `more: offset <n>` when there is a next page; a body is `tacit_fact`'s; the folders are `tacit_tree`'s (Tree index).

**The MCP server across upgrades.** `tacit mcp` reads its stdio itself (newline-delimited JSON-RPC, nothing read ahead it cannot hand over). At each call the client sends (not `initialize`) it stats the executable it was started from (the path it was invoked by; file identity, size and modification time): when that changed, is at least two seconds old and answers `version`, the server holds the call until every earlier call is answered (or cancelled; at most 30 s, else it serves the call and tries at the next), then re-executes itself in place, same pid, stdin and stdout. The new process reads the handoff from `TACIT_MCP_HANDOFF` (base64 JSON; over 64 KiB, a private file in the state directory named by `TACIT_MCP_HANDOFF_FILE`, deleted once read), clears it, and resumes the session from it with no new initialize: the `initialize` parameters, the negotiated protocol version, the `initialized` notification and the log level, then every byte the old process read and did not handle, the held call first. On Windows, which has no exec in place, and after a failed exec, the server serves on and appends to every tool result that it runs the binary it started with and how to reconnect. `tacit doctor` lists the running tacit processes on an outdated binary (Linux: `/proc/<pid>/exe` ending in ` (deleted)` or naming a file that is no longer the running inode; macOS: `ps`'s executable and start time against the file's modification time; not checked on Windows).

- **What a session reads** (`tree.Session`, one rule for the tree and the search). By default: `system`, `user`, the session's `projects/<repo>` and `derived/<repo>` under every name delivery knows its repository by (repoid's, with the repo aliases of Delivery; in a workspace, every one of its repositories, Delivery's Workspaces), this machine's `machines/<host>`, and this machine's local layer when it is on. Another project's or machine's scope only when the caller names it (a search's `scope`, a tree's `path`), and that scope alone: naming another project was already possible with `repo`, and another machine's facts are about that machine. A project's scope also holds the facts filed elsewhere that are tied to it (`applies_to.repos`). Inbox notes only with `inbox`; superseded and retired facts never.
- **`tacit_search`**: `query` (BM25, as before, with two-letter words kept as terms: an agent's query words are picked to find something, `pi` or `pr`, unlike a prompt's prose, and BM25 weighs the grammar ones to nearly nothing) and the filters `scope`, `type`, `rulings_only`, `path` (facts whose `applies_to.paths` cover the file, with the metadata line's matching; an absolute path is taken relative to the checkout repoid finds, symlinks resolved) and `command` (facts whose `applies_to.commands` start the command, or that the command starts: `git commit` finds the facts on `git commit -s`); `limit` (8, at most 50) and `offset`. With a query and no `scope`, `path` or `command` filter, every candidate (up to 500) is ranked with the facts tied to the session's repository (Delivery) weighing 1.5 times their BM25 score, and the page ends with `# this repo's <n> facts by folder: `tacit_tree projects/<repo>`` when the repository has facts (as in the SessionStart block). The query is optional when a filter is given; then the answer is every fact the filters keep, rules, rulings in their task, standards, decisions and past mistakes, the rest, newest first, 20 a page: `scope` alone lists a scope's facts. With neither it answers an error. `tacit search` with a filter gives the same answer, with these page sizes unless `--limit` is given.
- **`tacit_tree`**: the session's scopes under the asked folder, each with how many live curated facts of each type it holds (a project's with the facts tied to it from elsewhere; from the search index, left out when the index cannot be read), then the folder indexes (Tree index).

### Weighted relationship evidence

The curated prompt query also admits directly supported relationships, before
candidate limits. Index schema 6 records active curated summary terms and
ordered adjacent pairs, excluding inbox, local overlays, retired/superseded
facts, derived scopes and result references. Term weight is
`log((N+1)/(df+1))`; unknown terms have zero weight. A qualifying fact covers a
strict majority of known-query weight, shares a summary pair with
`(pair_df-1)*N/(df(a)*df(b)) > 1`, and binds at least one supported pair term
to its fact ID or stored path, command or symbol. Such a fact may clear prompt
selection without clearing its ordinary BM25 floor; BM25 still orders results.

Only when cwd, the prompt and the session's paths all lack a repository can this evidence route
into a curated project scope or bypass capture-repo applicability. Known or
explicitly named repos and machine scope restrictions remain enforced.
SessionStart, derived isolation, explicit search and no-backfill behavior are
unchanged. `tacit search --prompt --json` exposes the hook selection without
session-state writes, with word/relationship evidence and stored location
pointers. Unique active curated `[[links]]` add one-hop pointers, not recursive
retrieval. Evidence and location metadata never grant action permissions.
See eval/RELATIONSHIPS.md for measurements and known limits.

## Change feed

`GET /events` streams the journal as server-sent events. Over the tailnet reading needs no key; over the public path it needs a key token (Public path). The stream is "notify, don't carry": an event says the head moved; the content is fetched with git.

```
: connected head=<seq>                  first line of every stream: where the journal ends
id: <seq>
event: head_moved
data: {"seq":<seq>,"ref":...,"old":...,"new":...,"writer":...,"ts":...}

: keepalive                             every 20 s
```

The server replays every journal row with `seq` above the client's `Last-Event-ID` header (or `?since=`), then streams live rows. A client that was away loses nothing.

`tacit follow` is the client side. It holds the stream and, for each burst of `head_moved` events (1 s of quiet, at most 5 s), does what `tacit sync` does: fetch, fast-forward, reindex. The fetch runs without the store lock and lands in a private ref (`refs/tacit/follow/main`, fetched with `--refmap=` so git does not also touch `origin/main`); the lock is held only to point `origin/main` at it and merge. Hooks and writers never wait behind the network, and two overlapping fetches of `origin/main` (one of which fails with "incorrect old value provided") cannot happen. Needs git 2.29 or newer (`--no-write-fetch-head`, so the fetch does not rewrite the `FETCH_HEAD` that a concurrent `git pull --rebase` reads). Rules:

- **Resume.** The last synced `seq` is saved in `~/.local/state/tacit/follow.json` after each sync (the `seq` read before the fetch started, so a push that landed mid-fetch is synced again, never skipped). A restart sends it as `Last-Event-ID`. A reconnect in the same run sends the newest `seq` seen. If `: connected head=N` is below the saved seq, the server rebuilt its journal: take N and resync. If N is above it, a sync to N is owed even if no event arrives.
- **Reconnect.** Exponential backoff with equal jitter, 1 s doubling to 60 s (a server restart takes about 5 s; an outage costs one request a minute; the jitter spreads the machines that lose the feed together). The backoff resets after a stream stays up 30 s. A stream silent for 60 s (three keepalives) is dropped.
- **Fallback.** While the stream is down, sync every 60 s, so a broken feed leaves the clone at most a minute behind.
- **Verification.** The stream carries only journal rows, and a ref can move without one (the server dies between receive-pack and the journal append, or the journal is restored). While connected, every 5 minutes (288 small requests a day) the follower runs `git ls-remote origin main` and checks the answer is in the clone's HEAD. If the server is ahead it marks the clone behind and syncs. `verified_at` records the start of the last successful sync or check.
- **One follower per store.** An flock on `<state>.lock` refuses a second follower (exit 75) so two processes never overwrite one heartbeat. The state file is `follow.json` for the default clone and `follow-<hash of the path>.json` for any other store (`TACIT_STORE`).
- **Start-up.** A missing clone, an unreadable origin or a state directory that cannot be opened yet (a home not mounted at login) is waited out with the same 2 s to 60 s backoff, not an exit. Exit 78 (EX_CONFIG) means a bad invocation (unknown flag, bad `--as`, no key); the service unit does not restart on 78 and restarts on everything else, a Go panic (exit 2) included. Under launchd (`--launchd`) the 78 becomes exit 0, which KeepAlive does not restart (Install).
- **Auth.** None by default. A read-only clone made with `--as` signs each connection with that key (`tacit.as`, read at every connection, so a clone made after the follower started is picked up). `--as <harness>` signs explicitly.

`follow.json` is also the heartbeat. It holds `pid`, `store`, `seq`, `head`, `synced_at`, `verified_at`, `alive_at`, `connected` and `behind`. `alive_at` is stamped on connect, on every keepalive and after every sync, only while the stream is up and no announced push is unmerged (`behind` is false). `behind` is set the moment an event arrives and cleared by the sync that covers it.

### The local leg of a sync

A sync's network steps (fetch, `ls-remote`, push) run under the caller's deadline (60 s when the caller set none) and git's low-speed limit: a transfer under 1 KB/s for 5 s stops, also when the server took the connection and sends nothing. Git has no connect timeout; a connect to a dead host ends with the kernel's SYN retries (134 s measured on Linux) or the deadline. Its local steps (status, the fast-forward's checkout, a reset) do not. They run on their own deadline of 10 minutes, so a checkout is never cut off half way: a checkout killed at its deadline leaves HEAD at the old commit, the files half way to the new one and a stale `.git/index.lock`, and every later sync then refuses the clone as dirty. A caller whose time left is too short for the update (300 changed files a second plus 2 s; 12,890 files took 3.5 s on a Mac) gets a deferred update and an untouched clone, and the next sync with more time does it.

While git writes the working tree for a sync, its pid and start time are in `.git/tacit-checkout`. A git lock (`index.lock`, `HEAD.lock`, the branch's ref lock) is stale when that marker's git is gone, or, with no marker, when the lock is older than 15 minutes; a stale lock is removed, a live one leaves the clone alone.

A clone left dirty by an interrupted update is finished by code when it proves, path by path, that the dirt is only toward the remote: HEAD is an ancestor of `origin/main`; nothing is ignored; every changed or new file holds the content of `origin/main`'s file at that path, or of a version a commit between HEAD and `origin/main` wrote there, or a start of such content (git writes a file in place, so the files it was writing when killed are cut, at most 16); every missing file is gone at `origin/main` or was deleted by such a commit. A path no such commit names is outside the store's layout and fails the proof. The repair resets the clone to `origin/main` and removes the files of commits in between that `origin/main` no longer has, and logs what it did on stderr and in `.git/tacit-sync.log`. Any other dirt is refused as before, with the first path that fails the proof. A writer clone is repaired only on the same proof, so a local commit (HEAD not an ancestor) is never reset.

### Skipping the SessionStart sync

The SessionStart hook skips its own network sync when `follow.json` says a healthy follower covers this clone: `store` equals the clone, the `pid` is alive, `connected`, not `behind`, `alive_at` at most 45 s old and `verified_at` at most 10 min old. 45 s is two keepalive intervals (40 s) plus 5 s for a loaded machine to write, and below the follower's 60 s silence timeout, so a half-open connection cannot look fresh for longer than it takes the follower to notice. 10 min is two verification intervals: if the follower cannot reach the server to check, hooks sync for themselves again after that. Any other state, or no file, and the hook syncs as before.

What the skip costs: a push from another machine can be invisible to this clone, and the hook will not sync, for up to 45 s after the follower's last keepalive (if the connection died silently) and in the normal case for the second or two between the push and the follower's merge. A push the journal never announced is invisible for up to 5 minutes (the next verification) and then synced. Before the follower, every SessionStart fetched, so it saw a push the moment it landed. Measured 2026-10-10 on the workstation at load 47, three separate runs each: `tacit hook session-start` took 381 ms (363 to 391) with the network sync and 31 ms (16 to 31) with a fresh follower; with a push waiting the synced path took 1346 ms (1299 to 1907), because the hook then also merges and builds the index.

## Git evidence

`client/internal/gitev` reads git as evidence about facts, without a model. From facts it takes the repos they are about (`projects/<repo>` scope, `applies_to.repos`, or a repo named in the text; each must be a git checkout under `$TACIT_PROJECTS`, default `~/projects`, worktree copies `wt-*` excluded; for a name in `ordinary_names`, see Derived facts), at most three, and the subject terms: what the writer put in `applies_to` first (symbols, paths, command paths and flags), then backticked paths, flags, snake_case and environment names from the text, then bare ones. Generic words are never terms, and a term found in 26 or more files at HEAD is dropped as not distinctive.

For each repo it reads, with a timeout per command and read-only (no locks, no writes, and a partial clone's missing files are not fetched: `GIT_NO_LAZY_FETCH`, which needs git 2.44, so with an older git a partial clone is skipped with a note), the commits on the subject (`git log` by path, `-G` by identifier, `--grep` by message) from 14 days before the older fact to HEAD, and what HEAD holds (a named path or identifier present or gone). It keeps at most two commits of context before the older fact and the first and last few after it, and counts the rest. Each commit carries author, committer and `Co-Authored-By` identities. The facts' own dates join the same timeline: the newest date in a fact's text (when it says it is from), its source note's date, its `created` (for a curator fact, the day it was filed, not the day it was true) and its first and last commit in the store.

Git is strong evidence for what happened and what the numbers were; newer commits often supersede an old result. It is never a replacement for an owner ruling: the committer is usually the main agent or a subagent. Every text it reads from git or takes from the facts is redacted with `digest.RedactAll` in one call before any of it is clipped or laid out, and the structured `Evidence` is redacted the same way; if redaction fails there is nothing to return. A read that fails or runs out of time is marked incomplete, shown with a note, and never cached or remembered; a term whose search failed is neither present nor absent. Per-repo results are cached by the commit they were read at and the subject searched, in `~/.cache/tacit/timeline` (at most 4000 files, the oldest removed first). `--as-of` replays: repos are read at the last first-parent commit before that time, and fact dates and the store history are cut at it. A timeline also carries `summary`, a few plain sentences built from the structured evidence after redaction (what the facts name that no repo holds now; per repo how many commits since the older fact touched the subject and the latest one's date and subject, or that nothing did; the repos that could not be read; a partial read says so), which the owner's pages show above the folded events. The review page shows the timeline under each finding (`GET /api/timeline`, same token as a mark; a server-side timeout answers 504 with a message, and the page treats any body without events as an error); `tacit timeline` prints it. As verifier input it did not beat the baseline, so `tacit verify` does not send it for pairs (eval/VALUE.md); a stale finding carries it, since the commits are the finding (see Staleness check). The package also reads one fact alone: `Effective` (its date), `ReadSince` (the light read: only specific identifiers; the paths and identifiers HEAD no longer holds; for each gone path its newest commit, for the gone identifiers the commits since a date that removed or rewrote a line holding one, at the repo's default branch, by committer date; its texts are raw, and the caller redacts what it keeps with `RedactAll` before clipping it) and `BuildOne` (its timeline).

## Index

The search index (`client/internal/search`, `index-v<schema>-<sha>[-l<stamp>].db`) is schema 10: a `records` table holds the folder records this machine reads (the store's, the local layer's own folders, the layer's status over a store folder's) with kind, status, suppression, aliases, an area's tools and commands and a topic's repos, so a hook needs no file beyond the index, and a `quiet` column marks the facts of a dead or shipped folder (and a topic of such an area), which no hook delivers. A layered file (the store-only file copied, the notes added) takes the store's records from the store-only file, writes the table again with the local layer's among them and marks the store's facts quiet again from the merged records, so a folder only this machine has a record for quiets the store's facts in it as a build from nothing does. Schema 14 adds the `claim` column: a fact that fails the attribution check (Metadata checks) while it is not the owner's verified words (no ruling, no backed words, no statement, not generated from git), which no hook delivers (Delivery, Provenance).

`MEMORY.md` is generated by `tacit index`: one line per non-superseded, non-retired curated fact, grouped by scope, `- [name](path) - description`, sorted by scope then name. Inbox facts are not indexed. The curator regenerates it on every run, so no two writers ever edit the same file.

`MEMORY.md` is kept for compatibility (lint L10, older clients); nothing reads it for delivery and nothing sends it to an agent. At 3 to 7 MB on a store of 17,000 to 28,000 facts it is not something to put in a model's context: the tree index is what an agent reads.

### Tree index

The store is a tree of folders: the root, the scope roots (`system/`, `user/`, `projects/`, `machines/`, `derived/`) and the scope folders under them. Every one holds a generated `_index.md` (`client/internal/tree`); `inbox/`, `review/` and `keys/` hold none (the inbox is the writers', the other two hold no facts). The name starts with an underscore, which no fact name (a slug) can, so it never collides with a fact: `fact.Walk`, the search index, lint's fact rules, `tacit fact` and delivery pass it over.

A folder's index is built by code from what is below it, no model:

- a title and one summary line: the facts below it, the owner's rulings among them, the most common types, the latest change, and the description words most of its facts share;
- `## Folders (n)`: one line per subfolder, `- [name/](name/_index.md) <summary>`, the largest first (the root lists the scope roots in the order above), at most 60, the rest counted;
- `## Facts (n)`: one line per live fact directly in it, `` - `name` (type): description `` (`type, owner ruling` for a ruling; the description cut at 140 characters), rulings first and then the most recently changed, at most 30, the rest counted with a pointer to search; superseded and retired facts are counted, not listed.

Every writer of curated facts (the curator's batches, the conflict recheck, dedupe, disowned, links, derive and results, the rulings audit, `tacit resolve`, the owner's app and review marks) regenerates `MEMORY.md` and every folder index in the same locked write and the same commit as its facts (`regenIndexes`), from the facts that commit holds; a folder index whose folder holds no facts any more is removed in that commit. Lint L16 checks they match, so they never drift. `tacit index` rebuilds both in the clone (`--check` reports the stale ones); the next curated write commits them. The local layer's curator writes the same indexes for its curated facts under the overlay's `curated/` (never in the clone).

`tacit tree [--depth N] [--repo R] [--host H] [path]` and the MCP tool `tacit_tree(path, depth)` return the index files of a folder (default: the root) and of the folders below it down `depth` levels (when not given: 2 for the store root, whose third level would list every fact of every scope the session reads, and 3 for any other folder; a given depth always wins; at most 8; 0 is the folder alone), concatenated, each under a `=== <folder>: <path> ===` line. They read index files only: the folders they descend into are the ones an index lists, plus the session's own folders (which a long folder list may have cut). Only the session's scopes are listed (Search and the tree, "What a session reads"): another repository's or machine's folder line is left out of its parent's listing with a count, and that folder is read only when asked for by path. The answer opens with the scopes' facts by type (`# facts by scope and type ...`, one `- <scope> (<total>): <type> <n>, ...` line per scope). With the local layer on, each folder's local index follows the store's, marked `(this machine's local layer)`. A path is store-relative, each part a slug: an absolute path, `..`, a dot directory, `inbox`, `review` or `keys` is refused, and an index file that resolves outside the store (a symlink) is not read. An answer is cut at 64 KB with a note. The MCP server's one instructions string names the tool (Delivery).

## Import

`--host` must be a slug; import refuses anything that would resolve outside `inbox/import@<host>/`. Symlinked source files are skipped. Loading walks skip symlinks, dot directories and `keys/`.

`tacit import claude <memory-dir>...` reads Claude Code auto-memory files (frontmatter `name`, `description`, `metadata.type`, `metadata.originSessionId`, `metadata.modified`) and writes each to `inbox/import@<host>/<origin>/<slug>.md`, where `<slug>` is the source file stem slugged (links between memories point at stems, so the stem is the identity; the source's own `name` field is not used) and a second stem that slugs to the same name gets a short hash suffix, with `type: unclassified`, the original type kept as `source.original_type`, scope guessed from the origin directory (`-home-alice-projects-myrepo` becomes `projects/myrepo`, `-home-alice` becomes `user`), `source.kind: observed` (`user` only when the original type is `feedback` and a quoted phrase of it is their words, with the evidence; see Rulings), `source.imported_from` set, `created` from `metadata.modified` or the file mtime. `MEMORY.md` indexes are skipped. A source file without frontmatter is imported with `name` from the file stem and `description` from its first non-empty line.

`tacit import codex <memories-dir>` splits `memory_summary.md` into one fact per bullet (sections `User preferences`, `General Tips`; the `User Profile` paragraph becomes one `user`-scoped fact `codex-user-profile`), `name` as a slug of the first words plus a short hash so re-imports are stable, `source.original_type` the section name slugged, `source.kind: user` for preferences and the profile only with a quoted phrase of their words (see Rulings), else observed. `rollout_summaries/` and `raw_memories.md` are session material, not facts, and are skipped.

Import is idempotent: the destination path is a function of the source, and an unchanged source rewrites an identical file.

Import never writes outside `inbox/`.

## Situation match (push mode)

Current session and prompt hooks enforce nonempty `applies_to.repos` as a restriction, not an OR trigger with host. The current verified repository, its aliases (Delivery, "Repo aliases"), or a complete repository name explicitly mentioned in a prompt must match. A host match alone cannot admit a different project. Empty repo lists remain eligible for lexical matching; empty `applies_to` does not mean pull-only. Path and command lists trigger the prompt hook's metadata line and the PreToolUse hook, for facts tied to the repo (Delivery); symbol lists are stored metadata only. Explicit search does not apply the hook repo restriction. The per-prompt relevance and score gates described above still apply even when a repository matches.

Role options: `efforts`, `profiles`, `timeouts` and `fallbacks` extend client configuration. [config/example.yaml](config/example.yaml) is a generic template; `config/local.yaml` is ignored. Cross-runner fallback is attempted once, without chaining. It is attempted for provider capacity, temporary service failures, expired authentication, a missing runner, an attempt deadline, and a model's safety refusal (Claude: "safeguards flagged this session", with no HTTP status): that prompt fails on that model every time, so a fallback on another provider is the one that can answer it. [The README](README.md#configuration) documents every option.
