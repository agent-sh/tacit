# Does delivering facts have value? (2026-10-08)

Every measurement in this file ran on one owner's private store, transcripts and repositories. The numbers stay with the owner: the truth set, the A/B tasks and their raw results, the labelled pairs and the store are the owner's own sessions and rulings, and so are the counts, scores, costs and times measured on them. This file keeps what carries over to another store: the question each measurement asked and why, its method and the decision rule set before it ran, the direction of each result, and the decision and parameters it led to. Numbers that are tacit's own (thresholds, caps, floors, timeouts, weights, prompt versions) and numbers measured on public data are stated as they are. The scripts are in this directory, `eval/README.md` says how to run each one on your own store, and `eval/examples/` has a synthetic sample that runs end to end.

The question before more infrastructure: when a fact from the store reaches the agent at session start, does the session go better? Three measurements, all with Opus 5.5 as the working model.

## 1. Offline delivery (`eval/delivery/delivery.py`)

For each truth situation whose fact exists in the imported store, build the 40-line SessionStart block for the situation's repo and host and check whether the needed fact is in it. Three selections, scored by hit rate and split into pull and push situations: every fact eligible by scope (uncapped), the top 40 by idf term overlap, and the top 40 with the pull query added.

Scope eligibility almost always holds the fact. The cap of 40 is where it is lost, and the pull query wins a little of that back. Over all the detours of the truth set, the facts nobody ever wrote down are the other half of the loss.

Finding: imported memory files bundle many facts behind one description line. For most of the A/B tasks the stored note holds the fact in its body, but its description does not state it, so a description-line block cannot carry it. One fact per entry is a precondition for delivery, not a style rule. The curator split (`eval/curate/split.py`) rewrites the inbox notes as one-fact entries; measured below.

## 2. Live A/B, read-mostly tasks (`eval/ab/run.py`, tasks T1-T13)

Tasks that reproduce truth-set situations whose facts are still true on the machine (several candidates were dropped because their fact had gone stale). Arms: `bare`, `block` (ranked 40-line block), `oracle` (block with the truth wording guaranteed inside). Measured per arm: tasks passed, tool calls, input tokens, cost and wall time. First one rep per cell, then three reps, summed over per-task medians.

No task failed and no known detour recurred in any arm: Opus 5.5 solves these read tasks by reading. The gain is efficiency, not correctness. The oracle cuts tool calls and wall time. The ranked block cuts fewer tool calls and costs more, because the block is paid on every turn. At one rep, per-task deltas are noise, except where the fact removed most of a task's work.

At three reps the oracle's tool-call saving repeats. The 10-line block from the raw store (`block10`) saves nothing, because it rarely contains the fact. The same block from the curated store (`block10c`) passes every task and lands between bare and oracle on tool calls. Per-cell cost is not a usable metric at this scale: identical token counts cost several times more or less depending on whether the large system prompt was a prompt-cache hit, and that swamps the block's own cost. Tokens and tool calls are the stable measures.

## 3. Live A/B, decision tasks (D1-D14)

One-answer tasks built from owner rulings in the truth set, each a decision where the ruling was the agent's only source: approvals, merge and release order, secret handling, measurement settings and the like. Graded by a regex on the ruling and by a Haiku 5.5 judge (`eval/ab/judge.py`, yes/partial/no on substance; score = yes + 0.5 partial). The first run was invalid: with no tools and one turn, the model's first move was a tool call and most answers were empty. The runs that count give read-only tools and six turns. Arms: `bare`, `block` (40 lines), `block10` (10 lines) and `oracle` (40 lines, fact guaranteed), three reps; a cell that timed out counts as a failure.

The 40-line block costs more and helps nothing. The 10-line block is the only arm better than bare on every axis: most regex passes, fewer tool calls, flat cost. On the judged score the oracle leads, and both ranked blocks sit at bare's level.

A 10-line block from the **curated** store (`block10c`, three reps) shows no compliance gain over bare. Inspection of the secret-in-a-transcript task's block: the curated store held facts about the transcript scrubber and its excluded paths, and even a note that contradicted the ruling, but the split had not produced the ruling itself. Two lessons: the curator can drop the owner's ruling while keeping its surroundings, and nothing yet detects a fact that contradicts another.

The oracle's gain sits where the bare agent had no source for the rule at all: the secret-in-a-transcript task went from failing in every rep to passing in every rep, and other tasks with no source for their rule moved from partial to yes. Where the rule already reaches the agent through a global rules file or the repo's auto-memory, every arm passes. The ranked blocks add nothing on compliance because the ranking rarely carried the needed fact (the same failure the offline check shows); the 10-line block still saves tool calls because it distracts less than the 40-line one.

Finding from the invalid run that stands on its own: on the task that asks the agent to print a new token's value, the bare arm refused on a rule from the global rules file; both fact arms offered to print it "if you confirm", because the delivered fact quoted a dated ruling next to the rule that the current request wins. A fact that restates a rule as a dated quote can weaken the rule. Failure mode for the hardening review.

## 4. Dreamer recall on the never-written facts (`eval/dream/dream_recall.py`)

For each gap (a fact the truth set needs and nobody wrote), give the model the digest window around the detour and ask for facts; a judge call checks whether the truth fact is among them (yes, partial, no). Compared: Haiku 5.5 with prompt v1 (generic "durable facts"); Haiku 5.5 with prompt v2 (every failed command and its fix is a fact) on the v1 misses; Opus 5.5 with prompt v2 on the same misses.

Haiku with v1 and then v2 states most of the gaps at least partially, at a small cost. Opus with v2 recovers only a few more full hits than Haiku with v2, at many times the cost, so Haiku 5.5 with prompt v2 is the dreamer. Machine facts were the weak class under v1, and they are what v2 recovered.

## 5. Dense retrieval (`eval/delivery/embed_rank.py`)

EmbeddingGemma 2 (text backbone, 256 d, task prefixes, GPU) against idf and against RRF fusion (k=60), on the same eligible sets, hit@40, on the raw and the curated store.

Dense is worse than lexical on both stores. Fusion helps on the raw store, where descriptions are weak and bodies carry the facts, and adds nothing on the curated store. With one-fact entries whose descriptions state the fact, a lexical ranker over descriptions is the right tool, and an embedding sidecar is not worth its cost. Negative result: the eval script stays as the record, and the client has no dense path.

Query form matters more than expected. For the A/B tasks whose fact survived the split, the task's actual prompt as the query (what a UserPromptSubmit hook has) beats the one-line intent (what SessionStart has) on curated hit@10 and hit@40.

## 6. Curator split (`eval/curate/split.py`)

Opus 5.5 rewrites each inbox note as one-fact entries; one note gives several facts. Offline delivery is compared with the raw store under the same ranker (idf over the situation's paths, command, repo and intent) at caps of 10, 20 and 40 lines, half-way through the store and over the full store.

Curated wins at every cap. But the eligible set grows several times over, and the lexical ranker is now the limit: scope weights, dropping the user scope and an applies_to boost change nothing (nearly every entry carries applies_to lists, too generic to discriminate), and ranking on descriptions only gives a small gain. Dense retrieval was the remaining ranker lever; measured in section 5 and rejected.

## Verdict (2026-10-08)

Decision rule set in advance: build only if (a) the oracle shows a repeatable gain on decision tasks and (b) curation plus ranking makes that gain reachable without an oracle.

(a) holds. With the right fact in the block, compliance on owner-ruling decisions rises (three reps, every cell judged), tool calls on read tasks drop at three reps, every task passes, and the gain sits exactly where the agent has no other source for the rule. A delivered fact is worth having.

(b) holds for the store, not yet for the ranker. The curator split lifts offline delivery at every block size, and the curated 10-line block already recovers part of the oracle's tool-call saving. But a 10-line block often misses the needed fact, lexical ranking has saturated, and when the block misses, its other lines cost more than they save (the raw 40-line block raised tool calls). The decision-task compliance of the curated block equals bare.

**Build, with the priorities the data sets:**

1. Precision over recall in what reaches the agent. SessionStart carries at most 10 facts; UserPromptSubmit retrieves with the real prompt as the query; nothing else is pushed. A fact that is not clearly relevant is a cost.
2. The store before the ranker. One fact per entry (the split), owner rulings kept verbatim as `kind: user` facts and never paraphrased away (the split lost a ruling while keeping its surroundings), and contradiction detection at curation time (the same store held a ruling next to a note that contradicted it).
3. The dreamer closes the gap of facts nobody wrote: Haiku 5.5 with the failed-command prompt recovers most of them at least partially, at a small cost per session window.
4. No embedding sidecar: dense retrieval measured below lexical on both stores (section 5). The ranker levers left are query form (the real prompt at UserPromptSubmit) and description quality from the curator. applies_to as emitted by the model is too generic to rank on and should be filled by the hook from what actually happened (paths touched, commands run), not guessed.
5. Measure in tokens and tool calls, never in per-cell dollars.

What these results do not show: value on long sessions (every task here was one prompt) and value for Codex, pi and Hermes (all runs were Claude Code with Opus 5.5).

## Review after the build (2026-10-08)

A clean-context reviewer found seven live defects (repo detection returned "projects" for every subdirectory and worktree; the 8 s sync budget did not bound git over HTTP; a refused push froze the clone; two hooks could corrupt one index build; the dreamer lost deltas past its call cap; the curator spent up to three model calls per fact and orphaned output on a deadline; model calls loaded CLAUDE.md and fired the hooks from inside the dreamer). All fixed with tests where the behaviour can be reproduced locally.

### Token efficiency

What reaches the model now:

| event | when | size | per session |
|---|---|---|---|
| SessionStart | startup only (not resume, clear, compact) | 10 lines, 1.8 KB, about 450 tokens | once |
| UserPromptSubmit | prompts with 2+ searchable terms, not harness-injected turns | 0 to 3 lines, 0 to 0.6 KB; 0 bytes for "hello there friend", "what is the weather" and any repeat | each fact at most once |

Before the review the prompt hook injected five lines on every turn, notifications included, and none of it measured as useful. The floor of 15 sits in a gap of the score distribution: junk prompts score below it and real requests above it. Bodies are never injected; `tacit fact <name>` or the MCP tool fetches them on demand.

### Failure modes and what catches them

- Store missing or network down: hooks print nothing and exit 0; sync is fetch plus ff-merge or rebase, bounded by process-group kill and http timeouts.
- Refused push (scope, secret, key): commit undone, files set aside as `.rejected`, clone keeps syncing. Still open: surfacing `.rejected` files to the owner.
- Stale or corrupt index: keyed by HEAD and schema version, rebuilt on first use, per-pid temp file, concurrent builders lose the race gracefully.
- Dreamer: cursor per transcript file advances only after its windows succeeded; 4 MB per file per run; shrunk files restart; unparsable model output yields no facts and the delta is retried next run; cost capped by `--max-calls`; secrets redacted by pattern before the digest leaves the machine (a secret the patterns miss would reach the model; the server's pre-receive scan is the second net before it reaches the store).
- Curator: per-batch commit and push, so a crash or deadline loses at most one batch; notes that produced nothing are remembered, not re-sent daily; the split can still drop a fact silently (it once dropped a ruling), which only a second pass over the same note would catch.
- Owner rulings: never retired on a judge's verdict; a supersede against `kind: user` is a review item.
- A fact that quotes a ruling beside "the current request wins" weakened the rule (the print-a-token task): rulings now render as `RULE name: <imperative>` with the dated preamble stripped. Whether that closes it is not yet re-measured.

### Contradictions

`conflicts_with` is frontmatter checked by lint (L13) and indexed; retrieval never delivers both sides of a known pair (the higher-ranked side stays and is marked "contradicted by X, unresolved"); the curator judges each new fact against its closest existing fact and against same-scope new facts of the same run in one batched call, writes pairs to `review/<date>.md`, and the owner resolves by superseding one side. Not covered: contradictions between two facts that were both in the store before the check existed (every curated entry already there), which needs one offline pass; and contradictions phrased in different vocabularies that bm25 does not pair.

### First live curator run (2026-10-08)

The first run curated one batch of pending inbox notes into one-fact entries, owner rulings among them, judged their conflict pairs in a few batched calls, and pushed the result with a `review/<date>.md` file. The contradictions it found are real and useful: an older note that recommended a research direction against a later ruling that rejected it; a capacity target against a measured fact that showed it does not fit. Some of its supersessions were wrong: a fact listing several repos was retired by narrower facts about one repo each. Fixed the same hour: automatic supersession now needs the same origin note or at least 0.6 term overlap; everything else is a review item for the owner. The wrongly retired fact was restored.

### Re-measure with the shipped hooks (2026-10-08)

Decision battery, three reps, judged, with a `live` arm: the installed hooks against the live store (curated split, RULE rendering, floor 15, top 3, once per session), beside `bare` (no facts) and `oracle` (fact guaranteed).

The shipped system recovers about half of the oracle's compliance gain, has the fewest violations of the three arms, and keeps all of the tool-call saving. One task moved from partial to yes under the RULE rendering, and the print-a-token task improved from all-partial. The secret-in-a-transcript task stays low because its ruling is still absent from the store (the split dropped it).

### Offline contradiction pass (2026-10-08)

Every same-family nearest-neighbour pair of curated facts with 3 or more shared terms went to a batched Haiku judge, at a small cost. A hand-read sample of its "contradicts" verdicts held only a few real ones (a rule against one git command next to a recipe that uses it; two different orders for one migration); the rest were refinements, exceptions or steps of one procedure. At that precision a verdict must not hide a fact at delivery. Changed the same hour: the curator writes contradictions to `review/` only, the judge definition excludes refinements and exceptions and answers "no" when unsure, the automatic `conflicts_with` from the first live run was removed from the store, and the candidates went to a recheck review file for the owner. `conflicts_with` stays as the mechanism, set on confirmation.

The second live run, with the ruling-recovery pass and the gated supersession, recovered rulings the split alone had folded away and raised a few items to review. The inbox was then fully curated, and the daily timer took over.

### What to iterate next, in order

1. `tacit resolve <a> <b>`: the owner confirms a review item and the curator sets `superseded_by` or `conflicts_with`; until then the review files are the queue.
2. Judge precision on contradictions: label the contradiction candidates once, measure the stricter prompt against them, and only then consider any automatic effect on delivery.
3. The dropped-ruling failure: a second curator pass that lists every owner sentence in a note and checks each has a `kind: user` entry.
4. A second machine (a laptop or a GPU box) to prove cross-machine delivery and the dreamer there.
5. Hook end-to-end test with a bare remote; `.rejected` surfacing to the owner.

## Verifier against the owner's labels (2026-10-09)

A sample of pairs the owner would know (their own rulings, repos and projects), picked from the store and labelled by them in `tacit review --label` (keep A, keep B, both stand; skip was offered). Labels live in `~/.local/state/tacit/labels/`, outside every root the verifier can read. The verifier (Sonnet 5.5, `--dry-run --ids`) answered the pairs still open in the replay store; pairs already settled there were skipped. Three runs per prompt, medians. Scored: agreement with the owner's mark, missed retirements, kept facts retired ("retired a kept fact" counts a wrong-side verdict too), and questions or queries.

Prompts compared:

- before: the prompt as it was;
- v1: "the store holds what is true now" (shipped);
- v2: v1 plus "a pause never retires a standing rule", "lessons do not age", "never retire a standard, ask";
- v3: v1 plus "a pause retires a plan, not a standing rule", "lessons do not age".

Before v1 the verifier read an outdated ruling or a paused plan as "a history note on a different subject" and kept both. v1 cuts the misses sharply. Its one new error is a single pair: it retired a standing owner standard because a later fact says the related work is dormant, in every run. v2 and v3, written to fix that in the prompt, gave back most of the gain and stay unshipped.

That error is closed in code instead. Many owner standards sit in the store as `type: user_standard` with `source.kind: observed`, because the curator read them in a transcript, and the ruling guard only looked at `kind: user`. The guard now covers `type: user_standard` too, so an agent's retirement of a standard becomes a question for the owner (test `TestAgentMayNotRetireAnObservedStandard`). Scored with the guard applied, v1 brings more of the owner's retirements to them as questions in their direction and misses fewer; v3 with the guard does worse than v1 with it.

Every both-stand pair stayed "both" in the median run of every prompt. The remaining wrong-side retirement (one project pair, every prompt, every run) is a state the owner knows and the sources contradict: the repo shows active commits after the stop. This is a development-set result, since the rules were written after reading the misses on these pairs. The next labelled sample is the held-out check, and it should include a standing rule against a later pause.

Label file format (`~/.local/state/tacit/labels/<sample>.jsonl`): one JSON record per mark, `{id, action, a, b, at, by: "owner-label"}`, where `action` is `left`, `right`, `both`, `query`, `skip` or `reopen` and the last record per `id` stands. From sample3 on, a record can carry `owner_only: true`: the owner says no source settles the pair and only the owner knows the answer. Scoring rule for those pairs: the verifier is right only when its verdict reaches the owner, "owner" (an ask) or "query" (a flagged conflict); a keep or both there counts as a guess, even when it matches. Other pairs score as above. Also from sample3 on, `action` can be `wrong`: neither fact is true. The verifier has no verdict for that today, so on such a pair it is right only when its verdict reaches the owner ("owner" or "query"); any keep or both counts as wrong.

## Hindsight's recall on the same delivery check (2026-10-09)

Part of deciding whether an existing open-source memory system should replace tacit. Hindsight 0.10.3 (vectorize-io, MIT) ran locally with its embedded Postgres, its default local embedder (BAAI/bge-small-en-v1.5) and reranker (ms-marco-MiniLM-L-6-v2), CPU only. The curated facts went in verbatim (`retain_extraction_mode: chunks`, no LLM), one document per fact, the fact's scope as its tag. Each situation was asked with the same text tacit's ranker gets, restricted by tag to the same eligible scopes (`any_strict`, every returned document checked against them), `budget: high` (`eval/delivery/hindsight_rank.py`, per-situation positions in `HS_OUT`). The comparison is tacit's idf ranker (`delivery.rank`, the prototype the shipped bm25 ranker replaced; section 6 has it a little below the shipped ranker), at hit@10 and hit@40.

Hindsight's recall (semantic + BM25 + rerank) ranks below tacit's idf at both depths. Two runs: the first with Hindsight's default BM25 cap (the 16 most selective query terms), the validation run with the cap off. Both gave identical results. In the top 10 most hits are shared, and idf has several times as many hits of its own as Hindsight. A recall at `budget: high` on a loaded CPU took tens of seconds; a lower budget or a GPU would be faster, and neither was measured.

What this does and does not show: on tacit's one-fact entries, a strong off-the-shelf hybrid retriever ranks below tacit's lexical ranker, the same direction as the EmbeddingGemma result in section 5. Every asymmetry runs against Hindsight: no LLM extraction (its default mode rewrites each fact and builds entity links at one model call per fact), a query form already tuned for idf on these same situations, and no tuning on the Hindsight side. So the gap is not a best-case Hindsight number, but nothing here argues for swapping tacit's retrieval for it.

## Derived facts: thresholds and delivery floor (2026-10-10)

`tacit derive` builds two facts per repo from plain git (SPEC.md "Derived facts"). Every number in `client/internal/derive/analyze.go` comes from `eval/derived/backtest.py`, run on the git history of four repos: three of the owner's and a large public upstream. The per-repo results stay with the owner; the rules they chose follow.

Window. Rank files by touch count over the K code-touching, non-merge commits before a split point; score = share of the top 10 touched again in the next 100 commits; 17 split points per repo; K of 50, 100, 200 and 400. The window barely matters. 400 has the best mean and the only full ten-file lists (a repo at K=50 can rank fewer than ten files). Counting commits instead of days keeps it a function of the commit: 400 code commits can be a week of a busy repo or the whole history of a small one. Shipped: 400.

Mass-edit limit. Code files per code-touching commit: the median is a couple of files, and the 99th percentile runs from a few dozen to several dozen across the four repos. The limit of 30 drops only a few percent of commits. At 60, the co-change rule fires several times as often and its measured precision jumps, because a handful of bulk commits dominate. Shipped: 30.

Co-change rule f -> g (learn on the window, test whether g is in f's commit over the next 150), changeset limit 30. Three rules: 3 changes and 0.3 of f's commits; 3 changes and 0.5 (shipped); 5 changes and 0.5. The stated "half of f's commits" roughly holds out of sample, and 5 changes would buy a few points of precision for far fewer rules.

Prompt floor. Derived facts are ranked alone in their own scope and added after the curated block, so their floor is separate. A set of prompts for two of the repos, scored with the derived fact's bm25 as the hook computes it, on the live store plus the derived facts of the checked-out repos, by kind:

- a prompt that names no file or module (work and junk prompts) scores far below the floor;
- a prompt about a module without naming a file ("deploy the X worker"), or about the layout without naming a directory ("which dir has the api router"), scores a little below it;
- a prompt that names one hot file by a short name or part of it lands anywhere in a wide band on both sides of the floor;
- a prompt that names two files or a full path, or asks for hot spots or the layout, scores above it.

There is no clean gap: the prompts that name one file by a short name spread across the band where the module and layout prompts sit. The floor is 12, which admits most of the one-file prompts, every stronger prompt and no prompt that names no file. It is a judgment inside that band, not a measured optimum, and it cannot be tuned without an outcome metric. Being wrong is cheap either way: a false positive is one line of about 60 tokens (name, "computed from git", description), a miss leaves the agent where it is today, and `tacit search` and the MCP tool find the facts by name. A floor of 9 would admit every one-file prompt and the module prompt, still not the layout question.

Not measured: whether the facts reduce tool calls or change any decision. The A/B harness (`eval/ab`) has no task that needs a layout or a hot file.

Size: a project scope with no checkout gets nothing; a checked-out repo gets a hot-spot fact and a module map (a few repos only one of them), each a few KB at most. The whole pass over every checkout takes under a minute on a loaded machine.

Fetch before the read (2026-10-10). One branch, `git fetch --no-tags origin +refs/heads/<b>:refs/remotes/origin/<b>`, timed in scratch clones that share objects with the checkouts, over ssh and https, on a loaded machine. Most of a small fetch is the handshake, which `git ls-remote` alone shows. The slowest was a busy upstream's main branch a few days behind. The timeout is 30 s, three times the worst measured fetch; after three failures in a row the rest of the run does not fetch. A real run against a fork with its `dev` branch configured left HEAD, local `dev` and the working tree as they were, and read `origin/dev`.

## Git timeline as verifier input (2026-10-10)

Labelling is too technical when it rests on memory: an owner often does not remember, and a decision has to be checked against repo history. So each finding gets a git timeline built without a model (`client/internal/gitev`, `tacit timeline`): the facts' own dates, the commits in the repos the facts are about that touched what they name (with author, committer and co-author), and what HEAD shows now. The review page shows it under each proof, in normal and label mode. The question here is whether the verifier is better when it receives the same timeline.

Same sample2 pairs, same replay store (the store at the commit that created the sample, so the same findings are open and the same ones already settled), same scoring as above (owner labels read from outside every verifier root, medians, "retired a kept fact" counts a wrong-side verdict too). Sonnet 5.5, `tacit verify --dry-run --ids`, each run inside `systemd-run --user --wait --pipe` with the model provider's environment file. Arm `main`: the shipped prompt and findings. Arm `timeline`: the same plus a `Timeline` field in each finding's JSON and one paragraph saying git is the primary truth for what happened and when, the state at HEAD wins, a fact older than a commit that changed its subject is suspect, fact dates are compared with commit dates, and rulings or preferences with no git trace stay "owner". Timelines were built as of the time the owner finished labelling (`--as-of`), so the repos are as the owner saw them; the verifier's own git probes see the repos today in both arms. Rounds were paired, one run of each arm side by side, so both saw the same machine load. Ten paired runs per arm.

The arms are level on every measure: agreement, missed retirements, kept facts retired, questions and both-stand pairs kept, in the median. With the ruling guard applied, the owner's retirements reach them the same way in both. A first batch of paired runs, with a timeline build that differed only in listing a path from one repo as "not present" in another, gave the same medians. In the ten-run batch an early look at half the runs had the timeline arm one pair ahead; the other half closed it, which is the reason for ten.

**Verdict: not shipped.** The medians of agreement are equal, so the arm is not better on the median, and `tacit verify` stays as it was. Why the change is so small:

- Several findings change mark between runs inside each arm, and about as many differ between arms. The arm difference is the size of the run-to-run noise.
- The model almost never uses it: very few evidence strings in the timeline arm name the timeline.
- Git has little to say about this sample. Fewer than half of the findings have a commit on what the facts name, and many name no repo at all (owner rules for agents, preferences). The verifier already had `git-log`, `git-show` and `git-blame` through the probe, so where a commit matters it was already looking.
- What git cannot show is the owner's intent, and the committer is usually an agent. The wrong-side retirements are the same in both arms; the project pair described above is the kind of case: the repo shows commits after a stop the owner knows about.

A timeline takes about a second to build, cold, on a loaded machine. The timeline stays on the review page, where the owner decides, and in `gitev`, which the curator can use for staleness checks and for git-sourced facts (bench results, where newer commits supersede an old number). The measured verifier wiring was kept on a tag in the development history and is not in this tree.

## Verifier against sample3 (2026-10-10)

The held-out check the 2026-10-09 section asked for. The shipped prompt (v1) and the ruling guard have not changed since that result, so no rule here was written after reading these misses.

Sample: 30 pairs drawn (15 contradictions, 15 supersede proposals) and labelled by the owner in label mode. The owner skipped the pairs they could not know without git and answered the rest: most retire one side, few both stand, and some say neither fact is true and are flagged owner-only. Only the answered pairs are scored; the verifier saw only those ids. Scoring follows the label rules above: on an owner-only or "neither true" pair the verifier is right only when its verdict reaches the owner ("owner" or "query"), and a retirement of a ruling becomes a question (`isRuling`: `source.kind: user` or `type: user_standard`).

Replay store: a clone of the live store, never the live one. No single store commit has every pair open, because the pairs were flagged over several days and agent verdicts on them landed in several review commits. The replay uses the parent of the last of those commits (the last curator run): every pair exists there and some are open. For the pairs that already carried an agent verdict, those agent records were removed from `review/decisions.jsonl` and the relations they changed were put back from each record's `before` snapshot (what reopen does), `MEMORY.md` was regenerated, and the git history was flattened to one commit so `git-log` cannot show the earlier verdicts. Nothing else changed. Every pair was then open. Labels and the pairs file stayed outside every root the verifier can read and were opened only by the scoring script. A check on the replay: its median mark equals the agent mark the sample file records for the pair (the live verifier's, or both stand where none was recorded) on most pairs.

Runs: Sonnet 5.5, `tacit verify --dry-run --ids` on the answered ids, three runs, each inside `systemd-run --user --wait --pipe` with the model provider's environment file and the replay store as `TACIT_STORE`. Medians.

## Merge and rescope verdicts (2026-10-10)

Two owner decisions after the prompt v2 result, written down before the runs.

A. Merge. In sample3 the owner retired a side in most pairs, and the verifier kept both in most of those, calling the facts "complementary". The owner retires the older side even when it still carries a detail. New verdict "merge": the verifier names the fact that stays (`keep`) and the still-true detail of the other (`fold`, exact short text); the other fact is retired as superseded by the kept one and the detail is appended to the kept fact as a marked paragraph (`Folded in from [[other]] (date): ...`, redacted, fail closed). The decision keeps both files' exact bytes, so reopen restores them. An owner ruling (`isRuling`) is never edited or retired by an agent: a merge touching one becomes a question that carries the proposed merge, and the review page offers it as a mark (key m).

B. Rescope. Most pairs only the owner can answer are an agent's rule that is wrong in scope: an agent read a remark the owner made about one repo as a rule for every repo. New verdict "rescope": the verifier names the fact, the narrower scope `projects/<repo>`, optionally a one-line description that names the repo, and what the pair is after (`both`, or `query`). The fact's file moves to the scope's directory, the pair is marked as the verdict says, lint stays clean, reopen moves it back. A ruling is never moved by an agent (it becomes a question with the proposed scope), and neither is a fact into a scope the store has no directory for yet. The prompt gets a paragraph telling the verifier to check scope first (the fact's `origin` inbox note, its source, the repo) when a rule seems to conflict with another repo's fact.

Scoring, fixed before the runs (the earlier sections' rules still apply):

- A merge that keeps side X counts as the owner's "keep X" retirement; a merge that keeps the other side is a wrong-side verdict.
- A rescope followed by both standing counts as the pair's "both": agreement only where the owner marked both stand, a missed retirement where the owner retired a side. A rescope followed by a query counts as a flagged conflict.
- On an owner-only pair or a pair where the owner marked neither fact true (the `wrong` pairs of sample3, all owner-only), the verifier is right only when its verdict reaches the owner: an ask ("owner"), a query, or a rescope that names a repo. A keep, a merge or a plain "both" there is a guess.
- The ruling guard is applied as before, to merges and rescopes too: a merge touching a ruling, a rescope of a ruling, and a rescope into a scope with no directory in the store are questions, not writes. They count as "asked", in the merge's direction.
- Ship rule: the new arm ships only if its median agreement is higher on both samples and it retires no more facts the owner kept (sample2's both-stand pairs). If only A or only B passes, it is tested alone and that one ships.
- Arms: baseline (main's prompt and code) against new (A and B), 3 paired runs per sample, Sonnet 5.5, `tacit verify --dry-run --ids` inside `systemd-run --user --wait --pipe` with the model provider's environment file, at most two at once, on the same replay stores as the v2 section (both clones, origin a local bare copy). Labels are read only by a scoring script outside every verifier root.
- Both samples were seen while this was designed: sample2 is the set v1 was written from and the sample3 misses are what merge answers. Neither is held out.

### Scope check without a model

On a read-only clone of the live store it finds candidates among the live facts filed under user or system, spread over many repos and concentrated in the two busiest; they are `user_standard` and `past_mistake` facts, no `design_decision`.

Hand check, by the agent and not by the owner: two samples of 15 candidates drawn with a fixed seed, each fact read against its origin note. "Over-wide" means the rule is only true or only meaningful in that repo and is filed as if it held everywhere.

Few candidates are over-wide; a few more are partly so (a general rule with a repo-only half, or repo vocabulary); most are general rules, correctly wide. Three cheap refinements did not separate the groups: the curator's own `applies_to.repos` naming the repo, the fact naming its repo in its text, and the fact's rare words appearing in no other repo's notes. ## Fewer pairs for the owner: two levers (2026-10-10)

The owner approved cutting how many pairs reach them, since the owner cannot answer most of them from memory. Two deterministic levers, no new model calls: (a) raise the judge's bar, (b) a git gate. This section holds the rules. They were written after the label counts, the text features and a partial git read (a first part of the labelled pairs) had been looked at, and before the other pairs' git columns existed; the results follow.

Ground truth: the owner's labels in label mode (`sample`, `sample2`, `sample3`; last record per id stands, a reopen clears it, the later record stands where one pair is in two samples), every pair still a finding in the live store. Three groups: real problems (`left`, `right`, `wrong` and `query`), false alarms (`both`) and skips (the owner could not tell; every skip is in sample3). The two older samples were hand-picked as "pairs the owner would know", so their false-alarm and real rates do not describe the live flow; sample3 is a draw across the findings of the time, half of each kind, settled by the verifier or not. No label, id or fact name appears in this file next to an outcome.

Ship rule, fixed before the final tables:

- Recall of real problems: lose at most one. A real problem that a gate holds back is a contradiction or a stale fact nobody looks at again; a false alarm costs the owner a few seconds. One pair is the finest step this sample resolves, so a stricter level is not measurable, and a looser one cannot be told from losing several.
- A lever is a rule with a stated reason. A threshold fitted to the labelled pairs is not a reason, so fitted splits are reported as ceilings (the most any single split could hold on this data) and are never shipped.
- Ship the lever or combination that holds back the most pairs while meeting the recall level; if none meets it, ship nothing.
- Held pairs are not deleted: they stay in the review files and would show under a filter on the page.

What each lever is:

- (a) The judge's bar. The judge answers one word per pair and the bm25 hit score that decides which pairs it sees is not logged, so no raw judge score exists. Recomputed on a read-only clone of the live store: the overlap of the two descriptions' search terms (the curator's own `overlap`), the overlap of description and body terms, the number of shared terms found in at most 3% of curated facts, and the bm25 score of the other fact when one fact's description is the query (current index, an approximation of the raise-time score). The one natural bar is 0.5 description overlap, which the curator already requires for pairs it forms between new facts; the rest are curves.
- (b) The git gate. A pair is raised when git shows that what one fact names changed after the other fact's date, or when the two facts name the same path or identifier and it is present at HEAD. "Changed after" is read per fact with the existing `gitev` subject (applies_to, backticked and bare paths and identifiers, the repos it names), a commit on a later day than the other fact's date (its newest text date, else its source note, else its filing day) that touches a named path, adds or removes a named identifier, or names it in the message. Variant b+ also raises every pair that holds an owner ruling (`source.kind: user` or `type: user_standard`), since the owner can answer those from memory and the trust rule sends ruling conflicts to them. Otherwise the pair is held. A git read that fails or runs out of time never holds a pair.
- (c) Owner-facing after the verifier: the findings the page lists under "Needs you" today (no mark, or an agent flag or question), counted on the clone.

What is counted: for each lever on the labelled pairs, pairs still raised, real problems kept, false alarms held and skips held; on all findings of the live clone, pairs still raised of the total and still open of the pairs open now.

### Where the queue stands today (lever c)

The live clone (read-only) holds findings from the offline contradiction pass, from the first labelling sample and from the daily curator runs. The verifier has settled nearly all of them (most as "both stand", the rest as retirements) and flagged one as a conflict. The few left under "Needs you" are questions the verifier left, that conflict, and one finding the verifier never reached. All of them are in the labelled set: real problems and skips, no false alarm. There is no stability threshold in the code: one verifier run's "both" closes a finding, so (c) is already in force.

The daily inflow is small: the judge raises a small share of the pairs it sees each day, and few of the daily findings are still open. Whatever a lever does to the queue is a fraction of a small daily inflow.

What the verifier did with the labelled pairs, which sets the comparison for any gate placed before it: it closed every false alarm as "both stand". Of the real problems it closed more than half as "both stand", applied a retirement on some and brought a few to the owner. The skips went all three ways.

### Results on the labelled pairs

Raised means the pair stays an owner-facing finding. Git columns were read at the time of this run, with a read that failed or ran out of time counted as "changed" (findings in the two largest repos, on a heavily loaded machine; counting those as "nothing changed" only lowers the git rows). One deterministic pass; no model is involved, so there is no run-to-run spread. A second pass read every repo as of the day after the review file that raised each pair (so no commit made after the pair existed is counted): b1 raised one more pair, a skip, with the same real problems kept, and every other row was identical.

Levers compared: none (today); a: description overlap >= 0.5; b1: what one fact names changed after the other's day; b2: both name the same path or identifier, present at HEAD; b: b1 or b2; b+: b, or an owner ruling is involved.

The ship rule needs every real problem but one kept. No lever comes near. (a) holds back almost every pair and keeps almost no real problem. b1, b2 and b keep a minority of the real problems. b+ keeps the most, about two thirds of them, and holds back almost no false alarm. Nothing passes.

Lever (a), the curves behind the one natural bar. A higher bar on any text overlap removes real problems about as fast as it removes false alarms and skips, because the three groups overlap on every measure: their median description overlaps are close together. Curves were run for description overlap from 0.10 to 0.30, for 3 and 5 shared terms found in at most 3% of facts, and for the bm25 score of the other fact (8, the bar on the existing-fact hit today, and 32). No point on any curve keeps all but one real problem. The bm25 rows are a recomputation on the current index (some pairs have no score because the other fact is no longer a top hit, for example after a retirement), not the score at raise time, which was never stored.

The ceiling. Fitting one split on one feature to all the labelled pairs (every overlap and score above, the facts' types, kinds, scopes, ages, lengths, the verifier's mark, the git signals), the most pairs any split could hold while losing one real problem is a small share, and the best of them is a set of fact types picked by looking at the labels. A lever with a reason holds fewer.

Why git cannot gate these pairs. Git can be asked about at least one fact for about half of the real problems, a third of the false alarms and most skips; the rest name no repo with a checkout, or a repo and nothing git can search for (an owner rule about how agents work, a machine fact, a plan). Where it can be asked, a later commit on a named subject exists for a minority. A third of the real problems have neither an owner ruling nor any git signal. On sample3, the draw across all findings, b keeps a third of the real problems and holds back most skips: the signal "no git evidence" is not far from independent of "the owner could not tell".

### Volume on the live clone

On all findings of the live clone, (a) leaves almost none raised, b1, b2 and b a minority, and b+ most of them. Among the findings open now, b+ holds back only skips, and b holds back real problems as well as skips. These cuts come with the recall losses above: only b+ keeps every real problem among the open findings, and it loses a third of the labelled real problems elsewhere.

Post hoc, not part of the rules above: the same levers applied only to the pairs that would still reach the owner after the verifier. That placement leaves the real problems the verifier already closed or retired untouched, so b+ keeps every real problem among the open findings and holds back only skips. A cut that small is no evidence of a signal: picking the same number of open findings at random lands on skips alone often enough. And it is a fraction of a small daily inflow. Not shipped, for the cost of a curator step, a git read per open pair and a new filter on the page against that.

### Verdict: not shipped

Neither lever meets the recall level, so nothing ships: the curator, the review page and the verifier are as on main, and there is no held-pairs filter to add because no pair is held. The mechanism of the failure is that real problems, false alarms and skips come out of the same judge and look alike on every deterministic measure the store has: a bar that holds most of the false alarms also holds most of the real problems, and git has nothing to ask about for nearly half of the real ones.

Observations on where the owner's time goes, not tested levers: the daily findings are the ones the owner cannot answer. In sample3 most pairs from the newest curator runs were skips, and fewer of those from the offline pass. The sample3 section records that the owner skipped those pairs because they could not know without git, and the timeline under each proof on the page already gives them the means to check. And the verifier, not an upstream gate, decides which real problems reach them: it closes more than half of the labelled real problems as "both stand" and retires others, the open verifier work of the sections above.

Limits. Most labelled pairs come from two hand-picked samples whose real and false-alarm rates do not describe the live flow; skips exist only in sample3. One id is in two samples (the later label stands). Both git signals depend on what `gitev` can extract from a fact's text, which is what the page's timeline uses too; a better extractor would raise b1 and b2, but a third of the real problems have nothing for git to find. The measured wiring (`gitev.MovedAfter` with tests, the harness that writes one record per finding, a pair scoring script) was kept on a tag in the development history and is not in this tree. Labels, ids and fact names are not in this file.

## Results from git (2026-10-10)

Step 4 of "Git as a source" (docs/PLAN.md): measured results committed to repos become facts that carry their commit, a newer result replaces the older, and a saved fact that quotes the older number is flagged. Built as `client/internal/results`, `tacit results`, and a pass in `tacit curate`; the contract is SPEC.md "Results from git". No model, no network. Round 2 (2026-10-10, after a clean-context review) changed what is read, what a hook may print and what is flagged; what follows describes the final build, and where round 1 differs it says so.

### Where results live (survey of every repo with a store scope and a checkout)

Read-only over the projects directory, the refs each checkout already had (the repo's remote default branch, or a configured branch such as a fork's `dev`). Counted per repo: curated facts, commits, files with a metric column, structured files touched twice, results-named docs, the files the step reads, series, recurring series, saved facts quoting a value, result facts, and commit messages with a number. The per-repo counts stay with the owner.

"Files with a metric column" is jsonl, csv, tsv and json files at the default branch whose first row or top level has a column named like a measured quantity. "Files read" is the files the step reads: touched by at least two of the newest 6000 commits, with a measured number in their newest version. Round 1 read more series and recurring rows; the ones round 2 dropped are mostly JSON statistics, per-item records and baseline or parity files (see "Fact quality"). A repo of JSON receipts is the largest source of series with no recurring row, and none of them becomes a fact. Pull request bodies (`gh`, merged) often carry a measured number with a unit; for squash-merged repos most of that text is also the commit message.

What the survey says about where results live:

- **Per-experiment receipts, written once.** Most files with a metric column sit in folders of one experiment's raw output committed in one commit: per-request timings, telemetry, run dumps. Only a small share of a repo's structured files are touched twice. A file written once has no older value; it is not read. Rows of one setup with no timestamp are samples of a run, not results measured again, and are dropped.
- **Row logs that append a row per run with its own timestamp**: a perf CI log with cells by profile, each row a single run with the code sha it measured, and the bench boards beside it. This is the one place a number is measured again and again.
- **Boards rewritten as results change**: a board of published numbers and a site data file; an upstream project's CI baselines (`perf_baselines/*.json`, no longer read); a private repo's plan files.
- **Tables in lane documents**: the `RESULTS.md` files of research lanes, performance and profile documents, a private repo's server docs. A table is edited while its lane runs, so a cell does change.
- **Free text**: commit messages and PR bodies. A small share of commits carry a measured number.

### Deterministic, and why no model

Row logs, boards and tables have a key (a setup, a metric, a unit) and are read with no model. Free text was measured, since the design brief allows a model there only if nothing deterministic covers it. Haiku 5.5 (the dreamer's `claude -p` path, no tools, one turn, 8 messages per call) read the commit messages of several repos that carry a measured number, cheaply. A deterministic check drops what the message does not contain (the quote must be in the message and the value in the quote); it dropped few. A hand-checked sample of the results with one number, a unit, a named metric and a setup was nearly all right on value, unit, metric and setup; the error took the low end of a range.

Extraction was not the problem, keying was. Grouping those results by repo, unit and setup words (Jaccard 0.7) leaves very few groups with two values from two commits, and those are sibling arms and before/after pairs from one lane written within hours, not a number that a later commit replaced. Commit messages record the arms of an experiment; the living number is in the file the lane edits. The stored facts that contain one of their values are coincidences of the number, or a lane's own inbox note quoting its own arms. So the model path is not in the step: it would buy nothing for "newer replaces older" and cost a call per new commit message.

### What was built

Details in SPEC.md. Per repo, the newest 6000 non-merge commits are listed once with their files; every row log, board or table touched at least twice is read in its newest version, kept if it holds a measured number, then read through up to 40 older versions. A series is one quantity for one setup in one file; each point carries the commit that wrote it. Log rows that share a full timestamp and a code sha are one run and become one point, their median, labelled with the row count; per-item rows never make a median; a table or board number is "run count not stated", and "single run" appears only where the file says it. A setup the newest version no longer holds (a renamed column) is dropped, so its last value is never shown as current. Groups become `derived/<repo>/<repo>-results-<file>-<group>-<hash>.md`, at most 20 rows a fact and 24 facts a repo, kept if a row recurs or a curated fact quotes it. A fact is rewritten by a newer commit and removed when its series leaves, unless a saved fact points at it. A git read that fails or is cut retires nothing (tested with a git wrapper that fails on demand). `derived_from` is the commit that wrote the newest row, and a repo's read is cached by its HEAD, so the daily run of an unchanged repo writes nothing.

A saved fact is flagged when it states a number with at least three significant digits that equals a value the row held at the precision it was written, with that row's unit after it, with the words that tell the row from its group's other rows (two at least), when the value was replaced by more than 1 percent (and outside the noise band for a log), the fact is not older than the value by more than a week, and the sentence carries no date on or before the replacement. Round 2 added: no flag when the fact also states the current value (in any word order, `->` included), a number inside a bound ("must stay above", "target", "floor", "budget", "at least") is not a claim, `history`, `past_mistake` and `code_change` facts are records and never flagged, and the noise band needs a sample: under three points 5 percent stands in (a GPU benchmark cell moves a few percent between runs of the same code), three or four points use half the observed range, five or more use three times the median absolute deviation. A flag is a line in `review/<date>-results-<repo>.md`, read by the review page as a `result-superseded` pair whose generated side is never patched; an owner ruling becomes a `RULING CHANGE?` line. Nothing is retired.

### Fact quality (round 2)

The review found that the facts were more precise than useful: most of the result facts and rows came from JSON, and a sample of them were confidence bounds, a per-item score or a CI gate. Three filters, in the order the review gave them:

1. **Not a result of a run**: JSON statistics (`ci*`, `lower`, `upper`, `one_sided_*`, `delta*`, `stderr`, `std`, `p_value`), anything under per-item or per-slice records and `stages_ms`, files named `*baseline*` or `*parity*`.
2. **Round**: a number with seven or more decimals shows four significant digits and keeps the raw text in brackets (`41.67% (raw 41.666666666666664)`).
3. **Gate what a hook may print**: a result fact is type `result` (printable) only for a row log, a group a curated fact quotes, or a group a saved fact was retired in favour of (accepting a flag retires the saved fact; the replacement stays printable); every other group is type `result_ref`, found by `tacit search` and the MCP tool and never printed by the hook. The description is `<repo> <file>: <metric> for N setups, newest <date>`, plus one row when its label is a cell id (a `key=value` pair, a slug with a digit, a table row `slug / column`; anything else stays in the body). The row is not matched to the prompt: it is the fact's first row, a row a curated fact quotes if there is one and otherwise the one that changed most recently, and the hook prints the stored line. So a prompt about one cell (`how fast is the small model on short prompts`) can print another cell's row. No other free text of the repo reaches a hook line.

Result: fewer facts and far fewer rows than round 1. JSON's share of the rows fell from about two thirds to about a third; JSON still holds most of the facts. The round-1 text understated the JSON share; it counted the sample, not the output.

### Precision of extraction

Rows drawn at random (fixed seed) from the result facts of the final run, each checked against git: every table and log row holds the value at the cited line at the commit the body names (the file's newest commit), every JSON row holds it in that blob, and the commit named as the writer holds it too. Row label and unit read right against the cited line on every sampled row. Every JSON row of the output was then followed by key path (array elements by their name field, table entries by their key) to the same value. An earlier draw of this check found a real bug: a table that renamed a column kept the old column's last value as current. A series the newest version no longer holds is now dropped, with a test.

The round-1 text said line numbers were "as the file is at that commit". They are the file's numbering at its newest commit (the body says which); the writing commit of a row may have numbered the line differently, and the extraction check reads the line at the newest commit.

### What the live store gives

Checked against every curated fact of the live store (and, in a separate pass, its inbox notes):

- **Named, not stale: a few curated facts quote result rows at their current value** (round 1 matched more). Examples: a latency fact quotes two numbers from a repo's docs, a hardware fact quotes a memory bandwidth, and a recipe fact quotes a throughput from a results document. The matches round 2 dropped, by hand: record types (a `code_change` and a `past_mistake`), stated bounds (a latency bar, a requirement), a JSON statistic (`delta_points`), a measurement misread as a bound (a "times off its floor" figure; the skip is on the safe side and costs a match, not a flag), and some not traced.
- **Flags: none.** No curated fact quotes a value that a later commit replaced. A loose search (any unit, two digits, no setup check) over curated and inbox facts finds many candidates, all coincidences of small numbers. A search of git history for any number a curated fact quotes being replaced in place (`git log -G`) finds no replacement. The store's facts are filed after a lane's last number and the lanes append, so the case the step is for (git is more correct, and newer commits replaced the old results) does not occur on this store today.
- **A near miss that the dated-record rule exists for.** One fact says a headline number "was published at" a value on a given day; the board that holds that headline moved it several times since. The fact dates its number, so it is a record that stays true, and two digits are below the rule. Not flagged.
- **Reproduction on real history** (one fact constructed, because none exists): a scratch store, a copy of the live one plus one fact that quotes an older value of one cell of a row log, saved after a later row replaced it. `tacit results --out` writes the review file, with a line of this shape:

  `- result-superseded? [[demo-api-results-bench-latency-3f9c2a]] may replace [[demo-api-checkout-p50]] - quotes 41.8 ms for cell=checkout profile=default, which git recorded in commit 5e1f0c2a9b7d on 2026-09-02, row time 2026-07-20T09:12:05Z, code 3c4d5e6 and replaced in commit 5e1f0c2a9b7d on 2026-09-02, row time 2026-08-14T10:30:44Z, code 7a8b9c0d; git now holds 37.2 ms in commit 5e1f0c2a9b7d on 2026-09-02, row time 2026-08-14T16:02:19Z, code 1e2f3a4b (run count not stated, one row). Source: bench/latency.jsonl.`

  (When one commit imports a whole log, as here, the rows' own times and code shas are what date the measurements.)

### Delivery, measured twice

The prompt hook's second query ranks `derived/<repo>` for one line. Two prompt sets, each run through `tacit hook prompt` with the cwd of the repo on a scratch copy of the live store (with no result facts, with round 1's, with the final build's), every line judged by hand against the prompt: helpful (the line is about what the prompt asks and carries or points at the number), weak (right topic, no number or a neighbouring row), wrong (a different quantity, setup or model than the prompt asks). Set A: the prompts of the derived-facts trial (two repos; most name no file, the rest a module, one file, or several files or the layout). Set B: the reviewer's prompts (perf-flavoured and plain, several repos).

On set A no result line helps: round 1 printed one weak line, the final build prints none, and the hot-spot and module-map lines are identical to the run with no result facts. On set B round 1 printed a result line for most prompts, some of them wrong; the final build prints fewer, none wrong and about half helpful. The helpful lines are the row logs and a board a saved fact quotes; the weak lines are table groups a saved fact quotes whose line gives the file, a unit and a count and not the number. The numbers the dropped lines carried are still found by `tacit search` and the MCP tool. With no wrong line, the hook line stays, restricted to type `result`. The floor stays 12: on set A no result fact reaches it on a prompt that asks for no number, and on set B helpful and weak lines overlap in score, so no floor separates them (the gating does the work). A result line never enters SessionStart (tested). Set B is the sample the reviewer drew; both sets are small and were used to design the gate, so a third set is the real test.

### Cost

Every checked-out repo, `nice -n 19`, on a loaded machine: a cold run costs about what `tacit derive --dry-run --out` over all repos costs, and a run with the per-repo cache about a third of that, with byte-identical output; one repo takes a few seconds with the cache, the largest included. The cache holds one entry per repo and HEAD. No network, no model. The store lock is held only for the write, as in `tacit derive`. Round 1 spawned the redactor once per fact; redaction is now one call per repo.

### Limits

- Recall is bounded by the structure the extractors see. A number in prose, or in a table whose rows have one distinguishing word, is not matched; free text is out for the reason above.
- Flag precision is measured on fixtures and by the current-value matches, not on real stale quotes, because the store holds none. The first live run is the test.
- A curator fact's date is its filing day, so a flag never says a fact was wrong when saved, only that a newer commit holds another number.
- The bound filter errs toward silence: a "times off its floor" figure is skipped as a bound.
- A log whose rows each have a time of their own is read as a series even if a column is unique to each row. A per-request log with a request id and a timestamp per row would make a series (an earlier guard dropped any setup whose rows mostly differ, and with it perf logs that carry a uuid or note column; it fired on nothing in the checked-out repos, which read identically with and without it). Items that share a run's timestamp still make no series.
- The hook trial is two small sets judged by one reader; the reviewer's prompts were also used to tune the gate.

## Staleness check (2026-10-10)

PLAN step 3. `tacit stale` (also the last step of `tacit curate`) flags curated facts that git has overtaken and sends them to the verifier or the owner with their timeline. No model, no write to a fact. This section is the rule it shipped with, the rule it replaced and why, and what it costs.

Setup. Two copies of the live store, taken a few hours apart, read against the real checkouts in the projects directory on a loaded machine, everything at nice 19, 4 to 6 facts at a time. Dry runs with `--max 0`; the live store, the live review pages and the server were not touched, and the copies and caches were deleted afterwards. The three-rule comparison and the hand check of the changed-line rule come from the first copy and the first version of the code; the shipped rule's day-one results come from the second copy and the final code (after the clean-context review: repos read at their default branch, committer dates, path presence across the repos a fact names, reads that did not finish flag nothing). Every hand label below is the agent's, not the owner's, and was written before the verifier's answers were read.

Funnel, whole store, final code: about a third of the curated facts name no repo with a checkout; about a quarter name one but nothing git can be asked about (no path, no specific identifier); the rest have a git trace, and the shipped rule flags very few of those. A fact whose read did not finish is incomplete and is retried later.

Three rules on the same facts:

- naive: any commit on a path, an identifier or a message the fact names, after its date (gitev's full read). It flags a large share of the facts with a git trace; not checked by hand.
- changed line: a commit after the fact's date removed or rewrote a line holding a specific identifier it names, or a named file is gone. It flags a few percent of them; by hand, a minority of its flags are stale and most are still true.
- deletion (shipped): a named file is gone from every repo read, or a named identifier was removed after the date and no repo read holds it any more; repos read at their default branch. It flags very few, and by hand most of those have something stale.

The hot-file case is the naive rule: a fact about a file that commits keep editing is flagged on its first commit and every later one. The unit tests `TestHotFileTouchedByUnrelatedCommitsIsNotFlagged` and `TestAChangedValueWithItsNameStandingIsNotFlagged` fail when a file touch or a rewritten line is allowed to trigger (checked by letting it, then reverting).

Why the changed-line rule went. Every one of its flags that came from a deleted file was stale, and none of its flags that came from a changed line was. The changed-line flags were facts flagged on flags that other tools share (`--workspace`, `--state`, `--filter`, `--locked`, found in another tool's docs), on a reworded or refactored line around a name HEAD still holds (a doc paragraph, a rules line, a table row), on a name removed from an old script or comment but still used elsewhere, on field names that another repo's docs share, and a lesson whose code was deleted and whose advice stands. The deletion rule keeps only what that split left: something the fact names was deleted. A changed value with its name standing is no longer flagged; there is no measurement of a value-aware rule, and step 4 reads committed results directly.

The day-one flags, by hand. About half are outdated and the fact should retire: plans whose scripts were deleted, facts about code that was removed, a plan item already done, notes on lines of a file that no longer exists, a lesson about a site that was folded into another, and facts about a scheduled job that was removed. Most of the rest are true in substance with a detail to fix: guidance files consolidated into one, a directory folded into another, a table naming a deleted entry. A few are still true: a fact that records the deletion itself, a GitHub behaviour lesson whose repo no longer names the token, and a CLI lesson whose setup text quoted a flag of a removed script. Owner rulings among them (`kind: user` or `user_standard`) go to the owner as questions and are never sent to a model (here: references to a moved file under a rule that stands, and a read-first instruction that names a deleted file). The sample is small and from one store, so this is a development-set result.

What the review changed in the count: the first version read each checkout's HEAD, and one checkout was behind `origin/main`, so a job removal (several flags, most of them stale) was invisible; reading the default branch found it. Judging a path as gone only if no repo the fact names holds it dropped one flag, a file that moved from one repo to another (it had been a stale detail).

After day one. The day-one flags come from a handful of commits spread over months, most of them from a few consolidation or retirement commits (a site folded into another, the guidance files consolidated, a recovery chain removed, a feature retired, a job removed) that flag a few facts each. So the steady state on this store is a few flags at a time, in bursts, far under the cap of 60 a run. A flag is written once per newest triggering commit, an unanswered finding is never flagged again, and a deletion after a "still true" mark is a new event (unit tests `TestSettledFindingsDoNotMuteALaterDeletion`, `TestStillTrueIsSpentUntilANewCommitLands`).

Cost. A cold pass over a whole real store is long, longer than the step's budget, and a warm repeat is far faster. A fact with a trace takes a handful of git commands; the time goes to `git grep` of each identifier at HEAD, which can take seconds each on a loaded machine. A command that times out leaves its fact incomplete: nothing is flagged or recorded as checked, and the fact is retried the next day, then every 2nd, 4th and 7th day. `curate` gives the step 45 minutes at nice 19 and idle I/O priority, runs it last (after its own state is saved), skips it in `--dry-run`, and keeps a per-machine cursor (`~/.local/state/tacit/stale.json`), so a run that runs out of time continues where it stopped.

Verifier on the first version's non-ruling flags (most of them still flagged by the final code). Sonnet 5.5 (`tacit verify --dry-run --ids`, replay copy, each run in `systemd-run --user --wait --pipe` with the model provider's environment file), three runs, medians. The stale prompt carries the fact, the commits and the one-fact timeline. Against the agent's hand labels (retire, fix, keep), the verifier matches nearly every flag exactly and makes every stale-against-true call right in the median run. It never retired a fact the labels kept. The one fact labelled retire that it did not retire is a plan item that is half done, which it marked fix in every run. One run kept a fact labelled fix (a historical record that cites a file that moved). Not re-run on the flags the review added.

Not measured. Recall: how many stale facts the rule misses (a value that changed under a surviving name, a plan overtaken without deleting anything). Anything on a second store. The owner's own labels. The step did not run in the live `curate` timer yet.

## Verifier model: Opus 5.5 against Sonnet 5.5 (2026-10-10)

The evaluation setup on 2026-10-10 used Opus 5.5 first, with Sonnet 5.5 after a capacity failure. Each verdict recorded the model that produced it. These are historical evaluation settings, rather than current runtime defaults. The runs below test whether a stronger model moves the ceiling the earlier sections hit (Sonnet misses most of sample3's retirements as "complementary").

How a capacity failure surfaces. `claude -p --output-format json` exits 1 and still prints its result object: `is_error: true`, the HTTP status in `api_error_status` and the provider's text in `result` (for example `API Error: Repeated 529 Overloaded errors`, or a cloud provider's `ThrottlingException`, `ServiceUnavailableException` or `ModelNotReadyException`). An unknown model id is a 400 (`The provided model identifier is invalid`, plus `[claude-code:unrecognized_model]` on stderr), checked live. The fallback takes 429, 503 and 529, and the overloaded, throttling, unavailable and high-load texts on a failure with no status or a 5xx status, read from `result` and stderr together (Claude Code's own "Repeated 529 Overloaded errors" can come with no status). A 403 or 404 (Opus access lost, the model not offered) is not capacity: it fails the run, non-zero, rather than running on Sonnet unseen. A 400, a budget stop, a schema failure, a plain 500 or a crash fails the batch as before and is not retried on Sonnet. Same-model retries for a hiccup before any work (30 s, then 60 s) come first; the fallback is for capacity that does not come back. The Opus call's cost counts toward the run even when it failed after some turns. `--model` names one model and turns the fallback off. The verdict's model goes into the decision record (`model` in `review/decisions.jsonl`), the dry-run output, and the run line (`by model: ...; N batch(es) fell back to ...`). The CLI's own `--fallback-model` is not used: it switches models inside one session, so one batch's verdicts could come from both and could not be attributed.

Tests (`client/cmd/tacit/verify_fallback_test.go`) put a fake `claude` on PATH that logs the model it was asked for and answers per model: Opus answering is one Opus call and every decision records Opus; Opus failing with 503 before any work, with 529 after some paid turns, or with "Repeated 529 Overloaded errors" in an error result with no status, ends in exactly one Sonnet call, every decision records Sonnet, the run counts one fallback and the failed Opus call's cost is kept; a 400 invalid model id, a 403 lost access or a budget stop fails the batch with no Sonnet call and no verdict, and verdicts that come back with an error are discarded; a stale finding falls back the same way and records its model; with a named model a 503 fails the batch with no Sonnet call; a table checks the classification.

### Runs

Same setup as the earlier verifier sections, rebuilt from scratch for this run: replay stores are clones of the live store (never the live one) with `origin` a local bare copy. sample2 pinned at the commit that created it, history after it removed; the same findings open and settled as before. sample3 rebuilt as before: the agent records on the sample removed (one of them an ask with no before snapshot), the relations they changed put back from their `before` snapshots as reopen does, `MEMORY.md` regenerated, history flattened to one commit; the answered ids sent. Labels were read only by the scoring script under `~/.cache`, outside every verifier root. One binary (this branch), `tacit verify --dry-run --ids ... --model M` with the model named, so no run fell back. Each run inside `systemd-run --user --wait --pipe` with the model provider's environment file, `Nice=19`, its own clone of the replay store. Three paired rounds per sample, Opus and Sonnet side by side, two at once. Scoring as before: on an owner-only or "neither true" pair only a verdict that reaches the owner ("owner" or "query") is right, and the ruling guard is applied to every verdict as `applyOps` would. "Retired a kept fact" counts a wrong-side verdict too.

Raw model marks, medians: on sample2 Opus agrees on slightly more pairs than Sonnet in the median run, keeps every both-stand pair in the median run and has fewer wrong-side verdicts; Sonnet's own runs spread wider than that gap. On sample3 both models agree on the same few pairs in the median and miss most of the retirements, and neither reaches the owner on an owner-only pair. One Sonnet run on sample2 returned one verdict fewer than the findings it was sent; the missing one counts as not agreeing. With the ruling guard applied, the owner's retirements reach them about the same way under both models; on sample2 Opus asks more in the owner's direction and never on the wrong side.

Cost and time: Opus costs several times as much per finding and takes several times as long.

### Per-pair flips

Counted without pair ids or fact names, as before. Majority outcome over the three runs of each model:

- sample2: a few pairs differ. Most go Opus's way: a miss Sonnet made became an agreement, and a pair where Sonnet asked or flagged became an agreement. One goes the other way in kind: a wrong-side retirement Sonnet made became a miss ("both") under Opus. The remaining wrong side is the project pair the earlier sections describe, wrong in every run of both models. Opus changes outcome between runs on fewer pairs than Sonnet.
- sample3: one pair differs: a retirement Sonnet applied in the owner's direction in every run is split under Opus (one agreement, one query that names no side, one wrong-side retirement that would be applied, since neither fact is a ruling). Other retirements that both models miss in their median were caught by Opus in single runs. Opus changes outcome between runs on a few pairs; Sonnet on none.
- Replay check on sample3: the majority mark equals the agent mark the sample file records on most pairs, for both models.

### What it says

Opus does not move the ceiling. On sample2, the set the prompt was written from, Opus agrees slightly more often than Sonnet in the median run, keeps every both-stand pair in the median run and has fewer wrong-side verdicts; Sonnet's own runs span more than that gap, so the gap is inside Sonnet's run-to-run range. On sample3, the held-out sample for model choice (no model was chosen on it before), both models agree on the same few pairs in the median and miss most of the retirements. Opus's evidence on those misses reads like Sonnet's: the facts "agree", there is "no conflict", B "is consistent with" A, or they are "scoped cases of one rule". Neither model reaches the owner on the "neither is true" pairs in any run. Opus is not worse at keeping facts the owner kept: it retires fewer of them on sample2, and its one wrong-side retirement on sample3 came in one run of three. It is less stable on sample3.

So the missed retirements are not a model-strength limit that Opus lifts; they follow from what the verifier is asked and shown (the earlier sections: the owner retires the older side of two complementary facts, and nothing in the sources tells the model which one the owner counts as current). The default is Opus, the owner's choice, at several times the cost per finding, which is small at a store's daily inflow of findings.

Limits. Three paired runs per model per sample and medians, no five-run rerun: the sample3 medians are equal and the sample2 gap is inside Sonnet's own range, so more runs would not turn either into a clear difference in the direction that matters (sample3). sample3 was seen during the failed prompt attempts but never for model choice. Machine load during the runs was low, and the two models ran side by side, so load affects both.

## Curator backlog and the lost conflict checks (2026-10-11)

### The index errors

A curator run logged `curate: index query: unable to open database file (14)` for every fact after its first batch, so it made conflict checks for the first batch only. The first batch queried before the follower restarted on a new build (index schema v3); the curator was the older build (schema v2). `search.Open` opened the database lazily: no file was opened until the first query, which came after the minutes-long split call. In that time the follower synced, built `index-v3-<head>.db` and pruned every other `index-*` file, the curator's included; the follower did the same after each of the curator's pushes. The follower's own `disk I/O error (5898)` later in the run is the reverse: the curator's prune deleted the journal of a build in progress. The same race exists within one build: any push (the dreamer's, a hook's) moves HEAD, and the next index build prunes the file a long-running holder has not opened yet. Not the cause: open files, paths under a worktree or scratch HOME (both processes used `~/.local/state/tacit/index`).

Fix: `search.Open` opens and reads the file before it returns and keeps one connection (an open file survives its unlink); a file gone between build and open, or one that fails to read, is built again. `prune` keeps newer schema versions and the files of a build whose process is alive. The curator opens the index after the split, opens it again once when a query fails, and otherwise writes nothing for the batch and stops non-zero. `tacit curate --recheck-conflicts --since D [--until D]` runs the check alone. A dry run of the recheck on a copy of the store, for the day of the lost checks, made a few batched Haiku calls and raised a few contradictions and supersedes, all review lines (some of them same-day siblings).

### What the backlog is

The dreamer wrote notes to `inbox/dreamer@<host>` faster than the curator took them at six batches a run, so the pending inbox grew every day. Dreamer notes are one fact each already, and the split keeps most of them, so promotion is about one fact per note. The run line's "N notes to M facts" is pending against made: the run read only part of the pending notes.

### Levers measured

Duplicates (no model, `curate.Restated`): a small share of the pending dreamer notes share 0.6 or more of their description terms with a live curated fact (fewer share 0.8 or more), and some with an earlier pending note. Most of the high-overlap pairs differ in a number, a path or a negation (a new port, "no longer needs"), which is an update the conflict check must see. With those guards, and scope, body and owner-words guards, very few notes go: every one read in a sample is a restatement. Duplication is not what fills the inbox.

Value (Sonnet 5.5 as labeler: durable for another agent's next task, or true only inside the task it came from): in samples of pending dreamer notes a sizable minority were task-only, and notes filed under a worker worktree's name were task-only about twice as often as the rest.

Dreamer prompt. v3 is v2 plus one rule: "Skip facts that hold only inside the task in progress: the status of one PR, review round, rebase or run; where one task's worktree, scratch files, contract, receipts or logs are; an instruction addressed to one task id, round or worktree." v4 adds "A failure and what fixed it, and a rule or preference of the owner, are never task-only, even when they came up inside one task." Each sample is 30 transcript windows (the middle full window of a session touched in the last 48 hours), both prompts on the same windows, Haiku 5.5, labels by Sonnet 5.5 on the mixed set. On four samples (two seeds, each drawn twice a few hours apart), v3 and v4 cut the task-only facts to a small fraction of v2's and write fewer facts in all, with about as many durable ones.

Recall on the truth gaps (section 4, run with `--bare`, Haiku extractor and judge, every gap, two runs per prompt): v3 lost, in both of its runs, gaps that v2 found in both: a fix and two owner rules that came up inside a task. v4 finds them again; one gap goes the other way for each of v2 and v4 in both runs, and the rest moves within a prompt's own run-to-run spread. v4 ships: fewer facts, far fewer task-only facts, about as many durable ones, and recall at v2's level. Labels are one model's reading, with a lenient rule (unsure is durable).

Repo of a session: the dreamer took the basename of the session's cwd, so many pending notes were filed under a worktree's name, the home directory's name or `projects/client` (tacit's subdirectory). `dream.RepoOfCwd` maps worktrees and subdirectories to their repo and the home directory to no repo.

Batch size: the split's cost is per note (input and output both grow with the notes) and its time is output-bound, so larger batches change neither; they only risk the output limit. Not changed.

### Budget

Intake falls after v4 and the restated drop. `--max-batches` goes from 6 to 16, with `--budget 2h30m` on the split phase and the unit's timeout at 5 h. With that the curator takes more notes a day than come in, the backlog clears in days, and the curator then keeps pace. Its daily cost rises, most while it clears the backlog.

Scored: yes, partial and no, the same for rulings alone, whether the truth target is in the context, prompt lines, and median context characters.

The index stems with Porter, and a query term counts once per stem, so "amend" and "amended" are one match for the two-match gate. Against main, the stemmed index gives more yes and fewer no, puts the truth target in more contexts (it enters more often than it leaves), and adds few prompt lines and characters. Where the truth fact entered or left the context, the verdict rose far more often than it fell; where it did not, rises and falls are close, which is the judge's noise. The relationship route matches words as written and gets every spelling. The hook's warm time per prompt went from 181 to 191 ms at the median.

Measured on the same ladder and not shipped:

- **A ruling line** when the three facts hold none (score 10 or more): no better. It adds a line on some prompts, mostly rulings on the task's subject, but few of them are the truth target.

## Idle dreaming (2026-10-20)

A fact a session found used to wait for the 4-hour dream and then for one of the two daily curator runs: up to about 16 hours before any prompt could see it. Close events do not help: Ctrl-C, a closed terminal and a crash fire nothing. So the idle job dreams what went quiet for 20 minutes or compacted, every 10 minutes, the PreCompact hook dreams a session before it compacts (so its facts reach the store; nothing is given back to the same session, since the compaction's summary carries its content), and a quick curate pushes the last day's notes at most every 30 minutes (SPEC.md "When a transcript is dreamed", "Curator runs"). Measured read-only on a real machine's transcripts and meter logs, with `eval/dream/idle_schedule.py --days 4` (and `--days 7`).

**What the dreamer costs now.** From the meter log of the 4-hour dream: every call carries a fixed prompt overhead (the prompt and the runner's own system prompt), which the cheapest call, with a window of almost nothing, bounds. The curator's split and judge calls carry one too.

**The replay.** Both schedules over the same transcripts (Hermes not replayed). An event is one transcript delta of more than 4,000 bytes taken by one run, about one model call; the replay of the 4-hour schedule matches the calls the log shows. With the idle job and PreCompact, events a day rise by about half, most of them the idle job's, and the byte-weighted median time from write to dream falls to about a third.

**The cost.** Both schedules read the same bytes, so the window content costs the same; the idle schedule adds calls, each with the fixed overhead, a modest share over the dreamer's cost. The quick curate runs at most 48 times a day. A run with fresh notes makes one split call, one rulings pass and at least one judge call, so it adds a few calls' overhead. Each note is still split once, so the per-note cost does not change, and the full runs find fewer notes pending. An idle dream that finds nothing costs no model call, no sync and no meter line. Retries are bounded: a transcript whose window failed is passed over by the idle job and the hooks for 4 hours (`failed_at` in `dreamer.json`), so a window the model cannot answer costs at most one call per 4 hours, as with the 4-hour dream alone, not one every 10 minutes (144 a day). Not measured: whether a dreamer that sees a session in smaller pieces writes more or fewer of the facts that matter (eval/dream/dream_recall.py would tell).

## Dreaming at a full window (2026-10-20)

The prompt hook starts a session's dream once its undreamed part reaches about one dream window (60,000 characters of digest), so dreaming does not depend on a compaction, a quiet spell or the 4-hour run (SPEC.md "Delivery", the window trigger). The hook builds no digest, so bytes stand in for it. Measured read-only over a machine's large Claude Code and Codex transcripts: each transcript cut into consecutive deltas of a fixed size (1, 2 and 4 MiB) at line ends, each delta digested as the dreamer does (before redaction, which keeps line lengths), and its characters counted against 60,000.

A Claude Code transcript holds many bytes of file per digest character (tool results, metadata and images are in the file, not the digest), so one window is more file than a dream reads per run. A dream reads at most 4 MiB of a file per run, so the threshold is 4 MiB, a little under one window at the median. Most Codex sessions hold far fewer bytes per character, and sessions of mostly tool output far more; its threshold is 1 MiB, between one and two windows at the median. Hermes (message content bytes, 120,000) is not measured: that machine has no Hermes store.

**The cost.** Each call is about a full window (a little under one for Claude Code), the size of the 4-hour run's calls on a long session, and every schedule reads the same bytes once, so the window content costs the same as before. A window trigger adds only the fixed overhead of a call when it splits what one later run would have read in one call, and it saves the idle job's partial calls on a long session. So the cost is about the same as the idle schedule above. The check itself is a stat and a read of `dreamer.json`, about 3 ms a prompt with 5,000 cursors (in the test), no model and no git below the threshold; one dream per transcript cursor (`dream-trigger.json`), none while a dream runs or within 4 hours of a failure.

## Repo-first delivery (2026-10-21)

The question: what should reach an agent without its asking, so it gets the owner's rules for the work in front of it, without more context. The live act-bench (tasks in several repos, the items each task needs, two reps of tacit 0.7.1 with MCP) showed the hooks delivered a minority of the needed items, and that agents almost never searched: the tools are deferred, and nothing told them when a search pays. Six changes, each behind its own setting (SPEC.md, Delivery), measured offline with the shipped binary.

**Method.** `eval/delivery/repo_first.py` runs `tacit hook session-start --mcp`, `tacit hook prompt` and `tacit hook pre-tool` for each case, in a throwaway HOME and one session, against a copy of the store and its index, for each setting; every switch not named is off, so no switches is release 0.7.1 (replayed byte for byte). No model, except a Sonnet 5.5 judge, cached per case and line: for the design set it grades each pushed line needed, useful or noise for the request; for the holdout it says whether a line states the truth fact (yes, partial, no) and grades its use.

- **Design set**: the act-bench, its prompts in fresh clones of their repos (with their history and public remotes), the needed items with the store facts that carry each (full or partial), and the cells' own tool calls for the PreToolUse hook. The changes were built and tuned on it.
- **Holdout**: the older A/B bench's tasks with real checkouts, and the truth situations, one truth fact each. A situation's prompt is its intent, command and paths (its query for pull items), its cwd its session's checkout when it still exists, else a fresh `git init` named after the repo (no history, no remote); its command and paths are its tool calls. Nothing was tuned on it, except one parameter the design set could not tell apart (below).

"Reached" counts items whose full carrier is in the SessionStart or prompt block (design), or cases where a pushed line states the truth fact (holdout); "+tool" those reached only at a tool call. Characters and lines are per case, the SessionStart and prompt blocks together. Noise is the judge's share of pushed lines graded noise.

**Each change alone, on release 0.7.1.** The SessionStart repo block (1) alone reaches clearly more design items with fewer characters and less noise, and holds the holdout level with far fewer characters. Repo aliases with the curator's repo rule (2), the prompt metadata line (3) and the prompt action line (4) each add an item or a few holdout facts at about the same size. The instruction line (5) adds nothing by itself. The PreToolUse push (6) adds items only at the tool call. A prompt threshold of 0.7 with a ceiling of 5 adds the most holdout facts of any single change, at more characters.

**Together.** Changes 1 to 4 reach more design items and more holdout facts than the release, with far fewer characters and a much lower share of noise; 5 and 6 add the tool-call items. The shipped setting, 1 to 6 with the prompt threshold 0.7 and ceiling 5, reaches the most on both sets, with about a fifth fewer characters than the release on both and a lower share of noise. The PreToolUse push adds well under one line a session on the design cells (the judge: mostly noise, a few needed) and fewer on the holdout.

**The SessionStart block (1).** The release block ranks every fact by how well its words match the repo name, so the lines went to facts that say the repo name most (host notes, account notes, one-off remarks). The new block takes the facts tied to the repo by metadata (`applies_to.repos` or the project scope), of two tiers: rules and standards, then decisions and past mistakes; history, references and host notes never. Inside a tier the order was measured four ways, all with the same filter and ceiling 6: BM25 of the repo's names against the fact (shipped); kind (rules, rulings in their task, standards; newest first); the words of the repo's last 50 commit messages; the same, rules and standards first. BM25 reaches the most design items alone, in the shipped combination and at ceiling 8. On the holdout the four orders tie within a couple of cases either way, and the block matters little there (it carries few of the holdout facts; the rest come from the prompt, since a holdout prompt names its topic and most holdout cwds have no history), so the order rests on the design set. Read as what it measures inside the filter, the repo-name score puts a fact about the whole repo (a sign-off rule for every commit) before one about a part of it; the type filter, not the score, is what keeps host notes out. One-off owner requests stored as rulings (a section to add, a one-time task) are rules to the hook: in one repo they take a third of the lines. That is the store's wording, not the hook's.

**The ceilings and the prompt threshold (b).** Each count of the release is now a threshold with a hard ceiling, or a ceiling set by a sweep, on the combination 1-6. Swept: SessionStart ceilings of 3, 4, 6, 8 and 10; the prompt block with no threshold and with a line needing 0.5, 0.6, 0.7 or 0.8 of the best score, at ceilings 3 and 5.

The SessionStart ceiling stays 6: 8 adds a few holdout facts and one design item for more characters on both sets and more noise, and 6 is where both sets stop losing items as the ceiling falls. The prompt block takes up to 5 lines that each score at least 0.7 of the best one. The design set cannot tell the thresholds apart (the same count at every one with ceiling 5), so for this one parameter the holdout chose: 0.7 is the highest share that keeps the holdout's gain, for fewer characters than 0.5 or 0.6, and the design set confirms it loses nothing (it reaches more than the release's cap of 3). The threshold is relative, so it follows the scores of any store; the floors (15, 20) stay as they were. The metadata line's ceiling stays 1: 2 adds one design item and a couple of holdout facts, and many more tool-call lines, and the PreToolUse push is bounded at one line.

**Repo aliases (2).** A checkout answers to the names its own data gives it: every remote's repository name and its root manifest's package name, when that shares a word with a name it has. On the design set this finds the old name of one republished repo (its `package.json` name), whose general rule was already delivered under the new name, so it adds nothing there; on the holdout it adds one fact. The other rename in the design set, a repo republished under a new name, is not in either repo's data: the new repo's history starts fresh, its remotes and manifests never name the old repo, and the facts and the store's history hold no rename either (no fact moves scope, no supersession crosses the two). So the design item filed only under the old name stays out of reach: the analysis reached it with a hand-written alias list, which a generic mechanism cannot reproduce. Recording, at dream time, the remote of the checkout a note came from would make such a rename visible from then on; not built.

**The curator's repo rule (2).** Some curated facts were tied to the repo `memory`, a notes directory a session ran in, and so never delivered. The curator now drops a note's folder name from a fact's repos when the folder is not a known repository (a project scope of curated facts, or a checkout under `$TACIT_PROJECTS`), and gives the fact the known repos the note names instead; and it cuts `org/name` forms to `name`. The rule is the curator's for new facts; for this measurement it was applied to the store copy's curated facts as re-curation would write them: most of the `memory` facts gained their repo, many facts lost a folder name such as a two-letter word or a URL and became repo-free, and some had an `org/name` cut. It costs the design set nothing in all: it ties more facts to one repo, which take two SessionStart lines from its build facts, and those then arrive at the tool call that builds instead. Holdout: one fact more. With the tree store (one repo identity, metadata checks at write time) the rule is not the curator's own any more: the dreamer files a note only under a real git root, so no notes directory becomes a project, and a split entry naming a folder that is no repository, or an `org/name`, is refused and goes back to the model once; the repaired store copy stands for what that re-curation writes.

**The metadata line (3)** reads the facts that carry `applies_to.paths` or `commands`, which no hook read before: a fact of the repo whose paths cover a path the prompt names, or whose command the prompt names (the whole command, or its last word: "commit" for `git commit`). It adds one design item (a commit sign-off standard, through `git commit`) and a couple of holdout facts. It names no action: what a prompt can trigger is whatever commands the store's facts carry.

**The action line (4)** cannot be generic with an action detector: telling "commit it" from "explain the commit" needs a list of verbs, or of actions, and delivery keeps no such dictionaries. What is generic is the line itself: when the prompt block holds none of the repo's rules, standards, decisions or past mistakes, the best one for the prompt by BM25, without the coherence gate (general rules rarely pass it against task words), at the rule slot's floor of 10. It fires on any request; the floor and the no-backfill rule keep it to one line. Alone it adds a few holdout facts and nothing on the design set; in the combination it holds the design set's commit items. The analysis's version, a fixed list of actions (commit, release, dependencies, CI) each with a standing query, reached one more design item (through the dependencies action); that item is not reached now.

**The instruction line (5)**, one sentence in the SessionStart title and the MCP server's instructions: "tacit holds this owner's rules, decisions and past mistakes. Before an action that changes something, run one `mcp__tacit__tacit_search` for it." (144 characters; 130 in the server's instructions, which name the tool as the server does.) It costs that sentence's characters on every task and delivers nothing by itself; whether agents follow it needs a live run.

**The PreToolUse push (6).** At an edit or a shell command, at most one rule, standard, decision or past mistake of the repo whose `applies_to` paths cover the file or whose command starts the command line, once per session, within 400 ms. Alone, on the design cells it reaches items at the moment they matter (a config rule at the write of the config file, an output-format rule at the build, the sign-off at `git commit`), and a few holdout facts; in the shipped combination the sign-off is already in the SessionStart block, and the push reaches the two build items. A version that pushes the next unseen match when the best one was already delivered reaches one more design item, no more holdout facts, and about half again as many tool-call lines on the holdout; not shipped.

**Against the analysis.** The analysis estimated more design items for changes 1 to 4 than the generic implementation reaches, and more again with the push; the generic implementation lands an item or two below its estimate in every setting: with the release's prompt cap, with the measured threshold and with the push. The difference is the two hand-written parts the analysis used: an alias list (the renamed repo's old name, and `memory` mapped to every repo) and a per-action vocabulary for the action line. The `memory` facts are reached now through the curator's rule.

**Search and the store's tree.** `tacit_search` now takes filters (`scope`, `type`, `rulings_only`, `path`, `command`; the query is optional with one, and `scope` with no query lists a scope's facts, 20 a page), `tacit_tree` opens with the session's scopes and their facts by type, and the search answers one line per fact, paged (it used to return descriptions and bodies). Measured: what one such call at the agent's first edit (its file) or first commit (its command) would return, on the design cells and, for the holdout, the situation's own path and command, for six calls: `tacit_search(scope=projects/<repo>, path=<file>)`; `tacit_search(scope=projects/<repo>, command=<command>)`; `tacit_search(path=<file>, command=<command>)` over the eligible scopes; `tacit_search(scope=projects/<repo>, type=design_decision)` and `type=user_standard` with no query; and `tacit_search(<path> <the request's first sentence>)`.

A path or command filter is the cheapest call that adds items the hooks did not push, at about 1k characters; the path-and-command call over the eligible scopes adds the most. A listing by type costs two to three times that and adds little. A word search with the request reaches the most holdout facts because the holdout prompt is the situation itself, and it adds some beyond the hooks.

**On the tree store.** With the repo identity of the tree store (repoid: a real git root, a worktree's main repository; the hooks' aliases from it, no `git remote` process), the one read rule of `tacit_tree` and `tacit_search`, and their one instructions string, the replay of the shipped setting on the same cases gives byte for byte the same blocks as before. None of the replay's cwds is a linked worktree or a folder whose name the old walk took for a repository, which is where the two identities differ; the server's instructions are not in a hook's block. The two listing calls above were measured with `tacit_list(scope, type)`, which is gone; `tacit_search` with that scope and type and no query runs the same code (the scope's facts and those tied to it, kind order, 20 a page), so those results stand.

**Limits.** Both sets come from one owner's store and sessions; the design set is small and its carriers are one person's mapping, and the act-bench cells' tool calls were made with the old pushes, so an agent given the new lines might call other tools. The holdout's cwds mostly have no history or remotes, which underrates the SessionStart block and aliases there. The judge grades relevance, not whether an agent acts on a line. What agents do with the instruction line, and with the tree tools, needs a live run.

## Search, the push and the tree (2026-10-21)

The live act-bench on release 0.8.0 (its tasks, two reps, the hooks `tacit install claude` writes minus PreCompact, the MCP read tools) found four things: agents call `tacit_search` (in about two cells of three) but most of its 8 lines are machine notes unrelated to the task; the PreToolUse hook fired hundreds of times and showed a line rarely, every time before a shell command and never at an edit, and the judge graded most of those lines noise; no agent called `tacit_tree`; and two needed facts reached no agent by any route. Each was traced in the cells' hook logs and transcripts and replayed offline: the cells' hook calls in order against a copy of the bench store (byte for byte the logged output with the 0.8.0 binary), the tacit tool calls the agents made through `tacit mcp` (byte for byte the transcripts), the held-out replay of "Repo-first delivery", and `eval/delivery/search_replay.py`, which asks `tacit_search` each replay case's request as the query and grades the lines with the same judge and cache (holdout: a line states the truth fact; design: an item's carrier among the lines).

**Search.** The ranking is BM25 over every eligible scope, an OR of the query's terms, filling the 8-line page whatever the scores. On a store where the session's machine scope holds more than half of the curated facts, a query of task words ("widget README plugin section") fills the page with machine notes that share one or two of them ("plugin", "README"), and project and machine facts get the same 1.1 weight. Two-letter words were dropped from every query, as from the prompt hook's, so short names such as "pi" and "PR" never reached the index. For the agents' searches the needed facts were mostly not lexically reachable: in some tasks no needed fact is in the top 50 of any of their searches (an owner rule such as "keep the public API backward compatible" shares no word with a request to rename an export handler's flags); where one was further down, common words had ranked it well below the first page. Measured on the held-out replay (the requests as the query) and the act-bench requests, for these variants: non-repo facts need the prompt's coherence gate; the session's repo first, then other coherent facts; the session's repo first, all of it; keep lines at 0.5 or 0.7 of the best score; two-letter words kept; and two-letter words kept with the repo's facts weighing 1.25, 1.5, 1.75, 2, 2.5 or 3.

The session's repository is no reliable proxy for relevance on the holdout: its truth facts are often host notes that the repo's own facts (many of them host notes tied to the repo) crowd out when the repo comes first. A score cut lowers lines and noise but loses facts. Shipped: two-letter words in explicit search only (`Situation.ShortTerms`; the hooks' prompt is prose, where they are grammar and would pass its coverage gate) and the session's repository's facts weighing 1.5 over every candidate: the middle of the range where the holdout stays level (from 1 to 2, falling from 2.5), where the act-bench gains. On the searches the agents made, more return a needed fact and the share of noise lines falls. With no `scope`, `path` or `command` filter the answer's last line is the tree call for the repository's folder (below).

**The edit push.** Most of the edits touch a file no fact of the repo of tiers 0 and 1 covers (the facts whose paths cover them are references, structure notes or host notes, tier 2, or a user-scope fact with a repo-relative path and no `applies_to.repos`, which is tied to no repo). Many touch a file whose one covering fact SessionStart or the prompt had already printed, and a couple touch a file whose best covering fact had been printed while a second, unseen one existed: the no-backfill rule (the stash item below). The paths themselves are fine for matching: most `applies_to.paths` are plain repo-relative paths or globs; `~/` and absolute ones never match a checkout's file, by design. A backfill for files (the best unseen fact the first time a file is edited, nothing at later edits of it) reaches the stash item on the design cells and adds tool lines on the holdout, most of them noise, and no fact; not shipped, as for the plain backfill before.

**The command push.** Every line it showed was a command match. Of those the judge graded noise (it grades a line against the request, not the call), some were a past mistake about `git stash` shown before commands that do run `git stash` (the comparison's excerpt showed only a command's first 80 characters, a Python heredoc); some a past mistake whose `applies_to.commands` name `git show`, the check it recommends, next to the `git reset` it is about; one an inline `python3 -I -c` mistake about escaped quotes the command did not have. The fact metadata, not the match, decides these; a word-overlap gate between the fact and the request or the call does not separate them from the useful `npm ci` line (which shares only the repo's words with its request). Left as is. One gap was the matcher's: a fact on `vitest` did not match `npx vitest` (the program is npx). A part now also matches when it goes on with the fact's command after its first word and its second word is no flag: `npx vitest`, `sudo make lint`, a loop's `do make lint`, with no list of runners. Holdout unchanged; the act-bench cells' calls get one more needed line (a build rule at `npx tsup`) and one noise line (`do python3 -I -c` in a loop).

**The tree.** The SessionStart block shows at most 6 of a repo's facts and nothing said there were more; the instruction line names only the search, and a deferred tool is listed by name only, so no agent had a reason to load `tacit_tree`. With the block showing fewer facts than are tied to the repo, its last line now says how many and the call that lists them by folder (`tree_pointer`, default on), and the search answer ends with the same line. Holdout and design facts reached are unchanged; characters a case grow by a few percent.

**The two facts no route reached.** A repository's move (the moved-repository item) is filed as `history` with no paths or commands, so no repo-first line or push can carry it, and its subject is a two-letter word the prompt hook and the search dropped: the curator's choice of type and metadata, and the two-letter rule, together. With two-letter search words it is near the top of the answer to the agents' query when the query has "docs" in it, and far down without it. A past mistake about stashing only the source files (the stash item) has `paths: src/**` and `commands: git stash, vitest`. At the edit of a file under `src/` the push's best match is a decision about that very file, which the prompt's metadata line had printed, and at `npx vitest` (matched only with the runner rule) the best is the repo's pre-upload standard on `npx vitest`, printed at SessionStart; with no backfill nothing follows. Only the backfill reaches it, at the measured cost above.

**Live, the same bench with these changes** (binary at da27305, a copy of the same store with `tacit index` run by it, no `_index.md` changed; same tasks, reps, judge, hooks minus PreCompact, `tacit_add` disallowed). Scored per arm: found, right and acted (the bench's grades), the cells' cost, `tacit_search` calls and those that returned a needed fact, search lines graded needed, useful or noise, tree calls, and PreToolUse fires and lines shown.

Found, right and acted all rise, at about the same cost. Agents searched more and with other words, more of their searches returned a needed fact, and they called `tacit_tree` after the pointer. The moved-repository item went from half to full: both reps found the move through search. The stash item reached no cell again. Replayed through the 0.8.0 binary, the new cells' hook calls give the same prompt blocks and pushes byte for byte, and the SessionStart block differs only by the tree line, so the extra noise pushes come from the agents' other commands (more `git show` and `git stash`), and the runner rule did not fire live. Each search answer carries more characters (the tree line, a page count over every candidate, more lines when they asked for them). One item regressed, and that is the agents': both reps had the rule it needs in the same SessionStart line and broke it anyway.

**Limits.** One owner's store; few cells, so a task's mean moves by a whole rep; the act-bench requests were in the design set of the search weight, chosen on the holdout's level range. The judge grades lines against the request, not the call.

## Workspaces and the session's repositories first (2026-10-26)

A live bench on release 0.9.8 (one real owner task, three cells, Opus 5.5; the hooks `tacit install claude` writes minus PreCompact, the MCP read tools) started each cell in a Brazil workspace root: a folder holding its packages under `src/`, each a git checkout, the folder itself none. It found two things. SessionStart printed nothing: repoid found no repository at the cwd, so the session had none. And the facts that decide the task (above all an owner rule on which package a kind of code goes in, filed under one package's folder and tied to two) were in the store but never delivered: the prompt hook, with no repository, used the repo-less floor over the user and machine scopes and pushed unrelated machine notes in every cell. By the bench's own memory judge most pushed items were noise, and few were used.

**Method.** The cells' hook calls (SessionStart, the prompt, and dozens of PreToolUse calls each) replayed in order against a copy of the bench's frozen store, each cell in a fresh HOME, the workspace rebuilt as `git init` checkouts with the packages' remotes and manifests and the hook paths moved to it, and the cells' tacit MCP calls through `tacit mcp` with the workspace root as cwd. The 0.9.8 binary gives byte for byte the logged hook output and MCP answers. Lines are the distinct facts the hooks pushed; "needed" are the bench's needed facts found in them by its own patterns; noise is a Sonnet 5.5 judge's grade of each pushed line against the task (cached by fact). The replay of "Repo-first delivery" (same store copy, cases and judge cache as before, new lines judged the same way) checks the change elsewhere; a few of its held-out cases start in a workspace.

**Workspaces.** With a cwd in no repository, the session's repositories are the git roots at most two levels below it (Delivery's Workspaces). The cap was set from the folders on a real machine that hold checkouts and are none: Brazil workspaces, worktree folders, and general folders of checkouts above them. A workspace is at most 8 repositories and 64 roots: without the roots cap the PreToolUse hook took 350 ms of its 400 ms budget in a folder of several hundred worktree roots on a large store, and with it that folder is no workspace and takes 150 ms; a folder of a few dozen roots takes 250 ms, about what a repository costs. Home, `/` and the folders above home are refused before any read.

**The session's repositories first at the prompt.** Measured on both sets, candidates ranked over 50 before the floor: on the bench cells, the lines and the noise lines; on the replay, design items and held-out facts reached, characters and noise. Variants: the workspace with no ranking; the session's deciding facts boosted by 1.25, 1.5, 1.75 or 2 with every other fact (machine facts included) divided by the same; the boost with no penalty; the penalty with no boost; and the boost with only other projects' facts divided.

The penalty on this machine's facts is what loses held-out facts: the ones lost were machine notes a task needed and facts of a project under its old name in a checkout with no remote. On the bench cells it changed nothing: the boost did all of the change there. So machine facts keep their score (a setting turns the penalty on). The other-project penalty had no measured effect on either set; it stays, as the rule that another project's fact needs a stronger match. The boost holds the held-out level up to 1.5 and loses facts above it, the same knee as the search's repository weight (above). Shipped: deciding facts 1.5, other projects 1/1.5.

**Result, the shipped setting on the bench cells.** SessionStart now prints the workspace's block in every cell, and the deciding rule is its second line; it reached no cell before. The three cells deliver the same blocks, with their own PreToolUse calls: a SessionStart block whose other lines are mostly noise, a prompt block that is mostly noise (the request's words match the owner's notes on unrelated tooling), and PreToolUse lines as before. In all the hooks push more lines than before, with more needed and useful lines among them, and more noise. The MCP answers the agents asked for (the same calls) reach the deciding rule in one more cell, and other needed facts in the cell that got none, at somewhat more characters, because `tacit_tree` and `tacit_search` now read the packages' folders. The prompt block is still mostly noise: the request shares no word with the rules it needs, and that is a matter for the prompt's words, not its ranking.

**Elsewhere.** On the replay the shipped setting reaches what release 0.9.8 did: the same design items, and as many held-out facts lost as won, with slightly fewer characters a design case and a little more held-out noise. With both settings off (`TACIT_DELIVERY_WORKSPACE`, `TACIT_DELIVERY_PROMPT_REPO_RANK`) the replay and the bench cells give release 0.9.8's output byte for byte.

**The action line and the local layer.** The prompt's action line passed over every local fact, the local curator's included, though elsewhere delivery treats those like curated facts; on a read-only clone a machine's own project facts are all local, so the line never fired for them. It now takes the local curator's facts and still never an unreviewed local note.

**Limits.** One owner, one task, three cells that start the same way, so the bench replay is one situation three times; the agents' tool calls were made with the old blocks, and an agent given the deciding rule at SessionStart may call other tools. The judge grades a line against the request, not against what the agent did with it.

## Cost of curation: failed runs, the absorber's content rule, facts already held (2026-10-28)

Measured read-only on a real store's curator log and state (`curator.log`, `curator.json`), a week of its history, and the hand labels of a dedup measurement from the same week (notes a pre-split check would skip, and a random set, each labelled dup, minor or new). The numbers stay with the owner.

**Failed runs.** Over the week a large share of the curator's spend on batches went to runs that wrote no fact and had failed batches. Most of them were quick runs while the rulings pass's judge route was down (HTTP 402, as a paid route answers once its balance runs out): every quick run, every 30 minutes, paid the Opus split of its batches again, failed in the rulings pass and kept nothing. Replayed run by run under the new policy (a run's route taken as down when the real run failed, up otherwise; a probe costs a small fraction of a split batch): the first failed run pays its first batch and a probe, the runs that follow come before their next try and pay nothing, probes find the route still down or back, and the run after the route came back reuses the split it already paid for. On the measured week that saves about a third of the curator's cost. The saving is the outage's: a week with no failure saves nothing, and costs nothing either.

| schedule after n failed runs | 1 | 2 | 3 | 4 and on |
|---|---|---|---|---|
| next try | 30 min | 1 h | 2 h | 4 h |

The first wait is the quick run's own `--min-interval`, so one failure delays nothing; the cap is the full dream's cadence, so a route that comes back costs the notes at most one more period of waiting, which they already spend between full runs.

**The absorber's content rule.** The absorber compared descriptions only. Most written facts of the notes the labels call copies shared too few description terms with any live fact of their scope for it to look. The content rule (SPEC, Near-duplicates) was run, in Go, on every fact the curator wrote in the window, each against the live facts its curation saw (the store replayed commit by commit; the candidates are the 40 live facts sharing most terms with the fact and the 15 sharing most with each sentence). Every fact it absorbs at 0.75 or more was labelled by hand on its own (dup: everything it says is in its covers; minor or new: it adds a detail). Tuning is the curation before the rebuild switch, held out after it. Claim covers of 0.75, 0.80, 0.85 and 0.90 were compared.

At 0.75 one absorbed fact adds a detail (a new wiki entity page next to a covered wiki path); from 0.80 up none does, on the tuning half or the held-out half, and each higher bar absorbs fewer copies. Shipped: 0.80. Before the whole-path tokens, a new log path under a covered directory (`logs/*.stderr.log` against `logs/<service>.stderr.log`) was absorbed at a high cover by both rules; it no longer is. The cover may be in the note's scope (the session's repository): some absorptions need it, all of them copies. Most absorptions are copies outside the labelled set, so the labelled recall understates what it finds; most copies are still paraphrases no term rule reaches (with no guard at all, only a minority of the copy notes' facts have every claim at 0.8 in one visible fact). Every absorption at 0.8 was labelled a copy; one reader's labels. A few facts a day are not written, each a judge pair saved: the store stays cleaner, the money is small. Building the absorber over a large store's live facts takes 2.3 s; 500 checks take 0.3 s.

**Facts already held.** The dreamer writes the same operational facts again in window after window of the long sessions that supervise work (a sync rule, a tool's environment, a machine's heartbeat, an ssh wrapper, a wait helper): most copies the curator pays to split and judge start there. The held list gives each window the curated facts its session would be shown (SPEC, "Facts already held"). Replayed on windows of real sessions, copied read-only: some from the long-running sessions whose notes the labels most often call copies, some from other sessions with copies, and some from sessions picked at random. Each window's held list comes from the store as it was before the window's first line, so nothing dreamed from those lines is in it. Each window was answered by Opus 5.5 on the dream route without the list (v8), with it (v9, 4,000 characters) and with a stricter wording (an addition written alone), and four windows twice without it, for the noise. A blind Opus judge then labelled every note, all variants shuffled together, against the store's six closest live facts and the window's held list: DUP (nothing new), PARTIAL (a held fact again, plus a detail) or NEW.

Two runs of the same prompt on the same windows differ by about as many notes as the list removes: with the list the dreamer writes slightly fewer notes, within one standard deviation, and some of the notes it drops are NEW. Read by hand, the notes of the runs without the list that have no match with it: some restate a held or stored fact, some say one in other words, some lose a minor detail, and the largest group holds something new, most of it of the same order as the run-to-run noise. Copies fall; the partial restatements, the larger share, do not move, and the stricter wording made them no fewer and lost most of the owner's statements. With the list on, a window costs a little more input, and the curation it would save is not shown at this size. So the list ships off (`dream_held_chars`); this release's saving is the failed-run backoff's.

## The rulings answer (2026-10-30)

On a real machine the idle job (`tacit-dream-idle`, dream then `curate --quick`) exited with FAILURE on every quick run that curated: `curate: rulings: invalid model result: curator must return a JSON array`. The newest pending note, a dreamer note with no owner words, was alone in its batch, its rulings answer was refused whole, and a batch of one note cannot be split; a quick run counts no strike, so the same note failed every 30 minutes and would until the full run took it a day later. The same refusal had split a larger batch several times. The job's other failures in the same journal were the server's secret scan, fixed by v0.9.15 (#66), and an unreachable server.

The rulings pass asks for every owner ruling the split missed. For most notes there is none, and asked for "a JSON array (possibly empty)" Opus 5.5 explained the empty answer before giving it: "The note is an agent observation with no quoted owner words, so there are no rulings to extract. []", sometimes with the array in a code fence. `ParseChecked` takes only an answer that is the array, so it refused these whole, and `SplitChecked` sent back only answers refused for their entries.

Measured with `client/tools/envelope` (no store write; every call's session on the dreamer's exclude list): the rulings prompt for one inbox note, alone as a batch with nothing extracted (the shape a quick run's bisection ends in), through the judge route (`claude -p`, Opus 5.5, effort medium). Repeated calls for the note the quick runs failed on; three calls each for a random sample (fixed seed) of the notes the dreamer had just added to the store; and three calls each for a random sample (fixed seed) of the inbox notes of the owner's words (kind user or statement) that quote six words or more, to check the pass still finds what it is for. `-retry` sends a refused answer back the way the curator does. The old prompt's template is the base commit's `-print-template`, the tool copied onto it. Prompts compared: "a JSON array (possibly empty)" (before); the empty answer spelled out, "[] and nothing else" (shipped); the same plus a closing line after the notes.

Before, a large share of the answers held no array, for the failing note and for the random notes alike, and every answer sent back came back clean. With the empty answer spelled out, no answer lacked the array, on either set, so none needed sending back. On the owner-word notes, answers with an entry quoting the note fell slightly. Note by note, nearly all of the owner-word notes got the same count under both prompts. The few that differ hold no words the owner typed: each quotes an instruction from an agent's prompt ("Quoted from the session: ..."), which the pass is told not to list, and the curator's evidence check finds no such quote in the owner's turns. An earlier run of the same calls, counting any entry, gave both prompts the same count. The measurement always sends an empty extracted list, so it does not show the case the pass was made for (D6: the split listed some rulings and missed one). Every prompt costs the same per call.

Both changes ship: the prompt says what the empty answer is, and the rulings pass sends back an answer refused for its envelope (no array, or one that does not parse) once, like one refused for its entries. With the old prompt the retry alone took every refused answer back to a clean one; with the new one none needed it. The closing line added nothing and is not shipped. The split pass does not send its envelope refusals back: its answers are long (up to 45,000 characters of notes in, the whole array out), no whole refusal of one was measured, and its batch splits for one as before. A second refusal still fails the batch: a model that never answers with an array still fails the run.

## Machine facts whose paths are gone (2026-10-30)

Graded deliveries held lines that point to a durable path that is gone or to a deleted `~/.cache` folder, while no fact on the machine had ever been checked: the rotation ran only in `tacit maintain`, which the machine's own curate unit did not run. A fact of this machine that names a path that is not there is most often stale (a moved checkout, a key moved to the keyring, a scratch folder of a finished task), so the rotation takes those first.

The probe is code (`goneProbe`): the paths a fact of this machine names in its description, under the home directory, that a stat does not find. No model. Each of its rules is a kind of false flag the hand-checked samples showed: the clause around the path says it is gone, moved, removed or an example; a command writes it (`-o`, `--target-dir`, `TMPDIR=`, "written to", "goes in"); a run makes it on use (`mkdir -p`, an environment assignment); it is a template (`<id>`, `boxN`), cut short (`...`), a list (`a,b,c`) or a quoted path with a space; the fact is about another machine (`on the build box`, `ssh user@host`, `host:~/path`). The body is not read: its paths are context and history.

Hand-checked, a fact counted stale when the gone path makes what it says no longer true (a detail included), each sample of 30 flagged facts drawn fresh after the rules before it were written. The rules grew in this order: the first version (every machine fact, description and body); home only, templates, outputs, negation near the path; the clause around the path, examples, another host; the description only, made on use, spaces in paths; the Go port; cut and listed paths, a fact that says the path is gone; writes and downloads, `ssh` and `host:~` paths; and the shipped rules (a sentence ends only at ". ", "do not exist", "moved", templates like `boxN`). Each version flagged fewer facts than the one before. Stale facts were a majority of every fresh sample from the first version on, and nearly all of the sample drawn after the last rule change.

Under the shipped rules most flagged facts are stale. The probe costs a stat per path in the rotation's pick; a flag costs at most one rotation verdict, which checks the fact with the stat as proof and stamps it.

**After the review.** The probe's rules were tightened where the review's synthetic cases showed a false flag: letters beyond ASCII in a path, a colon ending a path (`main.go:42`, a list of paths, `host:/path`), a glob after a dot (`run.*`, `cfg.{json,yaml}`, `out.<ext>`, `run[0-9]`, `run?.log`), `%Y`, a Unicode ellipsis, an example marker before a comma (`e.g.,`), a sentence that ends after the path, an environment assignment in capitals only, a quoted path counted whole up to its closing quote. Another machine is one of the store's `machines/<host>` folders (and the part of a hyphenated name that holds a digit, `x9k2` for `gpu-x9k2`), not a list in the code; `applies_to.hosts` is not used for it, since agents put addresses, GPUs and the machine's own nickname there (the machine's own nickname alone suppressed a true flag). On the same store the tightened probe flags about as many facts as before: a few false flags gone (a cut path ending in `…`, another machine's `host:/path`, an example glob), one added (an end-to-end run's scratch folder, borderline). A quoted path cut at a space is looked up and named whole. A code span is a command line when the rest after its first word has a flag or a shell character, or when that word is an existing file; then the path is its first word (a gone program, `run.sh` with arguments, is named as the program). Otherwise the whole span is the path. Every flagged fact now gets its missing paths as proof lines (in the first version the proof's own path regex missed some), and once checked after its last change it takes its turn like any other fact.

**Against the order it replaces.** The first 30 facts each order takes on that store, checked by the curator's model in a dry run (Opus 5.5). The old order (claims first) takes facts that claim the owner's authority without their words, none of them delivered: the model found few stale, a third superseded and most to be reworded as an agent's note. The shipped order (gone paths first) takes delivered facts of this machine that name a path that is gone: the model found most of them stale.

The facts the old order takes first are held back from every hook until they are reworded, so checking them later costs nothing in the meantime; a stale fact of this machine is delivered until it is checked. At 60 facts a run the flagged facts take several runs before the claims come up again.

## Links to what a fact replaced (2026-10-30)

The link step called a link dead when its target had been replaced and the replacement chain had a clear live end. When that end was the linking fact itself, it unwrapped the link to plain text, or, in a ruling, put a `LINK?` line to the owner. Those links are where the fact came from: a ruling the rebuild made from the owner's statements says "Made by code from [[x-said-once]] (date, session)", and each statement's `superseded_by` names the ruling. They are now left as they are (SPEC, Link repair).

Measured on a real store with `tacit links --dry-run` on a clone, the v0.9.14 binary against this one. With v0.9.14 every dead target in a ruling was a link to a fact the ruling replaced, most of them open in Needs you and the rest in replaced rulings. With this build there are none, and no other fact's links change under either.

Nearly all of the review files' `LINK?` lines say the link "is superseded by [[the ruling]], which is this fact". A few propose rewriting a replaced ruling's link to the statement it was made of into a link to the ruling that later replaced it; that rule was not made of that statement, so the rewrite is wrong. One named no fact; its ruling is retired since.

Before this, the step had also unwrapped such links in agents' facts, and it goes on until this ships: `eval/curate/link_history.py` over the store's link commits finds the (fact, target) pairs whose link the step removed, one link each. Most are links to a fact the fact replaced; the rest are names no fact had.

The proposal to rewrite a ruling's link outside the owner's quoted words to the one live fact that replaced its target was built and measured too. On this store every link it rewrites is wrong (the replaced rulings' provenance links above); once those are left as they are it has no link to rewrite. It is not shipped.
